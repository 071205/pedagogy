# 출시 전2 — 한글·REA 근거를 시험지 출력 검증에 적용

- 2026-10-29 · 상태: 적용 계획. 이 문서 자체는 제품 수정·새 한글 실험·REA 재분석의 완료 증거가 아니다.
- 현재 출시 기준: main `1bae434`(PR40). 별도 연구 브랜치 `claude/h1-hwp-research`의 `10a0914`에는 [H1 실험](https://github.com/071205/pedagogy/blob/10a0914/docs/HWP-RESEARCH-RESULTS.md)과 [사이트 적용 설계](https://github.com/071205/pedagogy/blob/10a0914/docs/HWP-WEB-TYPESETTING-DESIGN.md)가 있다. 그 브랜치의 계획·확정 이슈를 현재 출시 코드의 완료 상태로 세지 않는다. 링크는 해당 연구 커밋을 가리키며 브랜치 병합을 뜻하지 않는다.

## 가능한 것과 한계

**적용 가능하다.** REA는 설치된 한글 빌드가 HWPX의 구역·글꼴·수식·배치 값을 읽는 경로를 좁혀, 정상/반례 표본을 어디에 만들지 결정하는 데 쓸 수 있다. 실제 글자 표시·줄바꿈·누락 여부는 같은 입력의 HWPX를 한글에서 열고 PDF로 출력·왕복 저장해 확인해야 한다. REA 정적 추론만으로 제품 출력의 성공을 판정하지 않는다.

기존 실물 근거는 이 구분의 필요성을 보여 준다. 구역 수가 1로 줄어도 파일은 열리지만 둘째 구역 본문이 빠졌고, 긴 수식은 파일·PDF 생성에 성공해도 본문 폭을 넘었다. 머리말과 조합 기호도 파일 열기만으로는 누락을 잡지 못했다. 최근 출시 전2에서는 실제 한글 3쪽에서 전체 쪽수와 과목 제목의 배치 결함을 발견해 수정했다. [HWPX 근거](HWPX-ELEMENT-SPECS.md) · [출력 인계](../reviews/handoffs/2026-10/2026-10-29-mock-hwpx-total-pages.md).

브라우저는 한글과 다른 렌더러다. REA가 웹폰트를 공급하거나 Chrome·Safari의 실제 대체 글꼴을 판정하지는 않는다. `document.fonts.ready`와 `FontFaceSet.check`도 개별 글리프 사용 증명이 아니므로, 출력별 실제 관찰과 미확인 상태를 구분한다. 상용 글꼴을 추출·웹에 재배포하지 않는다.

## 출시 전2에서 실행할 작은 묶음

| 순서 | 작업 | 완료 근거 |
| --- | --- | --- |
| 1. 현 코드 재현 | 연구 브랜치의 `REV-2026-129`(숨은 선지 측정의 폰트 스택·크기·자간·KaTeX 문맥 불일치)·`REV-2026-130`(글꼴 도착 전 HWPX 배치·높이 측정)를 현재 main에서 자체 문항으로 다시 재현한다. 코드 경로의 차이는 현재 소스에서도 확인되지만, 현 버전의 영향 크기와 실제 출력 결함은 재현으로 판정한다. 재현되면 기존 이슈 기록을 현재 리뷰 레일에 충돌 없이 편입한다. | 실제 표시/숨은 측정의 폰트·크기·자간·KaTeX 문맥, 글꼴 도착 전후 `layoutResolved`·`heightMm`과 사용 폰트, 동일 입력/환경 기록. 옛 수치를 현재 환경의 정답으로 고정하지 않음. |
| 2. 준비·측정 수정 | 폰트 준비·실패·시간 제한·취소·세대(generation)를 측정 경계에 묶고, 선지를 실제 출력 CSS 문맥에서 잰다. 그림 바이트 해결은 기존 별도 경계를 유지하되 실패·시간 제한을 확인한다. 현재 버튼의 중복 클릭 차단은 재사용한다. 측정값은 입력·폰트·템플릿·단폭·엔진 정체성이 같을 때만 HWPX payload에 쓴다. | 미준비/대체/미확인을 정상으로 표시하지 않음. 낡은 측정 게시·state 원문 오염·무한 대기 방지. 기존 자동 선지 배치와 변경 후 결과를 대조하고, 옛 동작/고장 주입 RED와 영향 회귀 통과. Sol medium 구현·독립 검토. |
| 3. 출력 보존 검사 | 한글·영문·숫자·기호·원문자, 분수/행렬/큰 괄호, 긴 선지·조건 상자·그림·쪽나눔을 넣은 합성 시험지를 가져오기→수정/구성→저장/재진입→미리보기→HWPX XML→실제 한글 모든 쪽 PDF→다른 이름 저장/재열기 PDF에 대조한다. 실패 안내/복구를 함께 확인하고, 브라우저 인쇄/PDF는 해당 출력 경로의 별도 결과로 대조한다. | 본문/수식/선지 순서·그림 존재, 페이지 수/번호·제목 중심·줄/단/쪽 경계·넘침, 폰트 대체/누락의 근거를 표본별로 기록. 수식은 PDF 텍스트 추출만으로 판정하지 않음. 지원 환경의 실제 결과를 확인하고 Windows/iOS 등 미시험을 통과로 쓰지 않음. |
| 4. 필요한 경우만 REA | 1~3에서 한글 특유의 설명되지 않은 차이가 남으면 F01 글꼴 선택, F02 장평/자간, F03 수식 기준선/폭, F04 줄·단·쪽 경계 중 **하나의 질문**을 고른다. 기존 구역 함수나 수식 후보를 반복 분석하지 않는다. | 설치 빌드·바이너리/폰트 해시·Evidence ID·정적 가설·정상/변형 HWPX·실제 PDF/왕복 결과를 함께 기록. 실물로 확인되지 않은 가설은 validator의 강제 거절 조건으로 승격하지 않음. |

입력 보존과 시각 품질은 따로 판정한다. 같은 글꼴·환경의 반복 결과로 허용 오차를 정하고, 다른 폰트의 픽셀 차이를 임의 보정으로 덮지 않는다. 수정이 Python/JS HWPX 모두에 닿으면 `test:hwpx-browser` 정합과 입력에 대한 독립 기대값, `test:hwpx-exam`·`test:hwpx-parity`·정적/CSP/공개 빌드·`serve.py` 회귀를 영향에 맞게 선택한다. 새 검사는 실패 주입으로 RED를 확인한다. 제품 변경 PR은 필수 CI4개·PR Sonar를 통과한 뒤 병합하고, 같은 revision의 main CI·Pages·공개 파일/실제 출력 경로를 확인한다.

## 출시 판정과 이후

출시 전에는 **실제 제공하기로 한 미리보기·PDF·HWPX 경로**에서 내용 누락·글리프 깨짐·심한 넘침·잘못된 쪽번호를 방치하지 않고, 지원 브라우저/기기와 출력 형식의 실측 및 안내를 맞춘다. 현재 PR40의 공개 PNG HWPX는 그림 데이터 포함까지 확인했지만, 그 새 그림 표본을 한글에서 직접 출력한 증거는 아직 없다. Windows 한글·iPad/iOS·실계정 문서 복귀도 별도 미검증이다. 지원 범위 축소는 자동 결정하지 않고 [통합 레일](DEV-TOKEN-ROADMAP.md)의 전2 완료 기준으로 판단한다.

전2에 필요한 결함/출력 근거가 채워진 뒤에는 여러 한글 버전의 세부 resolver 추적, 전면적인 원본 글꼴 유사화, 자동 수식 분할·축소, 범용 조판기 확장을 출시 후 품질 개선으로 둔다. 새 제품 범위나 상용 폰트 배포를 이 계획만으로 승인하지 않는다. R7 staging·실자료 이관·production 설정은 이 조판 조사와 별개이며 기존 출시 게이트를 유지한다.
