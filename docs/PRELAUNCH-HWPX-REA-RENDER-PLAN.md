# 출시 전2 — 화면·실시간 미리보기·한글 출력에 REA 적용

- 2026-10-30 · 상태: 적용 계획과 자체 화면 관찰. 제품 수정·새 한글 함수 분석·전체 출시 검증의 완료 증거는 아니다.
- 출시 기준: main `1bae434`(PR40). 별도 연구 브랜치 `claude/h1-hwp-research`의 `10a0914`에는 [H1 실험](https://github.com/071205/pedagogy/blob/10a0914/docs/HWP-RESEARCH-RESULTS.md)과 [사이트 조판 설계](https://github.com/071205/pedagogy/blob/10a0914/docs/HWP-WEB-TYPESETTING-DESIGN.md)가 있다. 연구 브랜치를 출시 코드에 병합하거나 그 이슈를 해결한 것으로 세지 않는다.

## 목표와 현재 근거

사용자가 문항을 바꾼 뒤 **화면이 최신 내용으로 갱신되고**, 미리보기·Typst·HWPX·PDF에서 본문/수식/선지/그림이 보존되며, 글꼴 대체·줄/단/쪽 넘침을 알 수 있어야 한다. 실시간 반응성과 지면 품질은 별개로 측정한다.

기존 REA는 HWPX 구역의 내부 조회와 수식 준비/측정 후보 함수를 추적했다. 실제 한글 실험에서는 구역 수를 줄인 파일이 열려도 뒤 본문이 빠졌고, 긴 수식은 PDF 생성에 성공해도 본문 폭을 넘었다. 머리말과 조합 기호도 열기만으로는 누락을 잡지 못했다. 최근 전2 실물 검사는 전체 쪽수·과목 제목의 배치 오류를 찾아 수정했다. [HWPX 요소 근거](HWPX-ELEMENT-SPECS.md) · [출력 인계](../reviews/handoffs/2026-10/2026-10-29-mock-hwpx-total-pages.md).

2026-10-30 자체 30문항 로컬 화면 관찰에서 `serve.py`의 실시간 Typst 이미지의 `src`는 편집 시작 후 **576ms**에 달라졌고 스크린샷 시각 대조에서 새 문구를 확인했다. 실시간을 끄면 HTML 근사 미리보기의 문구도 갱신됐다. 이는 `이 문항` 모드의 한 번 관찰이며 지연 상한·`전체 시험지`·연속 입력의 최신성 보증이 아니다. 실시간 이미지의 실제 사용 폰트와 서버 웹폰트 주입 상태도 이번에는 측정하지 않았다. HTML 선지의 요청 글꼴/크기/자간은 `ExamBody...`/14.5467px/−0.4364px, 숨은 측정은 `Hamchorom`/14.72px이었다. 연구 브랜치의 선지 측정 불일치와 같은 코드 경계이며 현 버전 영향 크기·실제 출력 오류는 추가 재현이 필요하다. 실시간 모드는 글자가 아닌 이미지이므로 DOM 텍스트 검사만으로 갱신을 판정할 수 없다. [화면 관찰](../reviews/audits/2026-10-29/prelaunch-print/mock-live-preview-observation.json).

REA는 한글의 **내부 구현 경로와 원인 후보**를 찾는 데 적극 사용한다. 브라우저의 실제 폰트나 출력 품질을 대신 판정하지는 않는다. 정적 코드, 실행 관찰, 한글 화면/PDF, 브라우저 화면/인쇄를 각기 다른 근거로 기록한다.

## REA 심화 조사 — 출시 전 출력에 직접 닿는 경로

기존 한글 build 6544의 Evidence·분석 스냅샷을 재사용하되, 설치 빌드와 원본/ARM64 분석 사본의 SHA-256이 일치하는지 먼저 확인한다. 옛 함수 주소를 새 바이너리에 적용하지 않는다. 현재 CLI는 REA 6.4.0이고 [GitHub upstream](https://github.com/morluto/rea/releases)은 2026-10-25에 6.8.0을 공개했다. 네이티브 함수 분석과 별도 프로세스의 제한된 호출 관찰 기능은 현재 도구에도 등록돼 있다. 새 버전의 추가 기능이 F01~F05에 필요한지 기능/호환성을 먼저 비교하고, 필요 없으면 6.4.0을 고정한다. 설치 버전·분석 profile·Evidence 정체성을 기록한다. 실제 한글의 hardened runtime/디버그 권한 허용 여부는 조사 시작 때 확인한다. 공급자 앱을 수정하거나 재서명해 피시험체를 바꾸지 않는다.

| 질문 | 깊게 추적할 내부 경로 | 제품에 연결할 결과 |
| --- | --- | --- |
| F01 글자·대체 | 틀의 `hh:fontfaces`/`hh:substFont` 선언과 `charPr`의 `hh:fontRef` ID → 언어별 폰트 선택 → 실제 face/글리프 fallback → 그리기 모듈의 호출 관계. 문자열만 보지 않고 xref·호출자/피호출자·가상 dispatch·값 흐름을 대조 | 어떤 문자가 네모/빈칸/다른 서체가 되는지 표본과 대체 전후 출력으로 판정. 화면과 HWPX의 요청/실사용 상태 표시 |
| F02 줄폭·글자 배치 | 장평·자간·탭·금칙·폰트 치환 값이 문단 폭/line segment를 계산하는 지점과 단/쪽 배치로 넘어가는 경로 | 숨은 선지 측정·한글 줄바꿈의 차이를 출력별 프로필로 설명. `measureCh`/`layoutOf`와 문항 높이가 `hwpxPayload()`의 `layoutResolved`/`heightMm`로 직접 들어가는 경계도 대조. 숫자를 한 엔진에서 다른 엔진으로 무조건 복사하지 않음 |
| F03 수식 | 기존 equation reader→script 준비→측정/width·height·baseLine 기록 후보에서 미해결 간접 호출과 실제 수식 모듈 연결을 추적 | 분수·행렬·긴 수식의 기준선/폭/넘침 진단. 저장 seed와 한글 재계산 실측을 구별 |
| F04 지면·반복 요소 | `linesegarray`/문단/단/쪽/각주/머리말·바탕쪽 필드의 읽기·무효화·반복 조판 경로. 기존 TOTAL_PAGE `num`은 조판 전 캐시이며 실제 쪽수 계산 시점(열기/인쇄/저장)을 구분 | 낡은 `linesegarray` 제거와 제목 CENTER 사본의 실물 근거를 재사용하고, 편집 직후 낡은 배치·쪽번호·머리말 누락을 막는 캐시/출력 정책 |

각 질문에 문자열·xref→함수/어셈블리·의사코드→호출 그래프·값 흐름→미해결 분기 순으로 Evidence ID를 남긴다. 가능하면 **자체 합성 문서만** 넣은 새 한글 프로세스에서 후보 함수의 호출을 제한 시간·이벤트 수로 관찰하고, 한글 화면과 모든 쪽 PDF를 대조한다. 실행 추적이 OS 권한/앱 보호로 불가하면 그 사실을 기록하고 정적 분석을 실행 증거로 꾸미지 않는다. 원본 바이너리·원시 의사코드를 제품 코드에 복사하지 않는다.

각 내부 가설은 한 조건만 바꾼 정상/반례 HWPX(폰트·장평·자간·긴 수식·줄 경계 등), 실제 한글 열기→본문 확인→PDF→다른 이름 저장/재열기→PDF로 판정한다. PDF 텍스트 추출은 수식/일부 글리프의 단독 oracle로 쓰지 않고 모든 쪽 이미지·입력 텍스트/그림·저장 XML을 대조한다. REA가 밝힌 함수라도 실행 확인과 실물 결과 없이 validator의 강제 오류 규칙으로 승격하지 않는다.

## 보이는 화면·실시간 경로 조사

30문항 합성 표본으로 `이 문항`/`전체 시험지`, 데스크톱/좁은 화면, HTML 근사/로컬 실시간 Typst, 줌/맞춤/스크롤·원본/편집/순서 전환을 실제 화면과 스크린샷으로 대조한다. 편집→화면 반영 시간, 연속 입력에서 옛 응답이 최신 화면을 덮는지, 폰트 로드·그림 decode 전후 측정 무효화, 출력 버튼을 누른 순간의 문항 revision, 오류/재시도·대체 상태를 기록한다. 실시간 이미지는 이미지 변경·시각 결과로, HTML은 DOM과 실제 사용 폰트/글리프로 각각 판정한다. Chrome과 Safari, 지원할 기기에서 따로 실측한다.

`document.fonts.ready`/`FontFaceSet.check`는 글리프 사용 증명이 아니다. 개발용 Chromium CDP의 사용 폰트 관찰, 실제 화면/인쇄 PDF의 글리프, 실패/대체 상태를 결합한다. REA의 한글 결과는 브라우저/Typst의 폰트·배치 계보와 비교하되 같은 렌더러라고 가정하지 않는다. 상용 폰트 추출·웹 재배포는 이 계획에 포함하지 않는다.

## 적용 순서와 완료 기준

1. **현 코드 결함 재현:** 연구 브랜치 `REV-2026-129`(숨은 선지 측정의 폰트 스택·크기·자간·KaTeX 문맥)와 `REV-2026-130`(폰트 도착 전 `layoutResolved`·`heightMm` 측정)의 현재 main 영향부터 재현한다. `toHwpx()`가 `resolveFigureBytes()` 뒤 글꼴 준비 확인 없이 `hwpxPayload()`를 호출하는 경로와, 이미지 decode가 필요한 입력에서 실제 높이에 영향이 있는지도 별도 대조한다. 코드 경로 차이는 확인됐고, 현재 출력 영향 크기는 미확인이다. 재현되면 기존 이슈 파일을 현재 리뷰 레일에 충돌 없이 편입한다.
2. **REA·화면 관찰 병행:** 위 F01~F05를 출력에 닿는 순서로 하나씩 심화한다. 화면의 실시간/근사 두 모드와 한글의 읽기/측정/조판을 동일 합성 입력으로 연결하고, 함수/표본/화면의 불일치를 기록한다. 모든 한글 기능을 해독할 때까지 출시를 기다리는 방식으로 넓히지 않는다.
3. **제품에 적용:** 폰트 준비·실패·시간 제한·취소·세대(generation)를 측정 경계에 묶고, 선지를 실제 CSS 문맥에서 재며 낡은 실시간 응답과 배치값을 게시하지 않는다. 그림 바이트 해결은 별도 경계를 유지한다. 기존 버튼 중복 클릭 차단은 재사용한다. HWPX에는 입력·폰트·템플릿·단폭·엔진 정체성이 맞는 값만 보낸다. 공개/무서버 환경은 `LIVE.webfonts`가 없어 폰트가 대체될 수 있으므로, 검증된 fallback 측정·서버 경로 안내·출력 보류 중 실제 결과에 맞는 정책을 전2에서 정하고 대체/미확인을 사용자에게 표시한다. 근거 없는 측정값을 정확한 정본으로 표시하지 않는다. Sol medium 구현·독립 검토.
4. **출력 전체 대조:** 합성 시험지를 가져오기→수정/구성→저장/재진입→두 미리보기→HWPX XML→한글 모든 쪽 PDF→왕복 저장 PDF에 대조하고, 브라우저 인쇄/PDF와 실패 안내/복구도 별도 검증한다. 본문·수식·선지·그림 순서와 쪽수/제목 중심·줄/단/쪽 경계·넘침을 확인한다. 연속 5회 편집 후 마지막 입력 revision과 실시간 이미지/HTML이 일치하고 옛 응답 게시가 0건인지 `이 문항`/`전체 시험지`와 Chrome/Safari에서 확인한다. 화면·HWPX XML·한글 전체 PDF의 문항 순서/본문/선지 배치(1/2/v)/쪽 분배를 같은 합성 입력과 대조하고 의도하지 않은 단폭 초과를 0건으로 판정한다.

새 회귀는 이전 동작/실패 주입으로 RED를 확인하고, 입력 원문과 각 출력의 독립 기대값을 둔다. Python/JS 정합과 `test:hwpx-exam`·`test:hwpx-parity`·정적/CSP/공개 빌드·`serve.py` 회귀를 영향에 맞게 실행한다. 제품 변경 PR은 필수 CI4개·PR Sonar 후 병합하고 동일 revision main CI·Pages·공개 파일/실제 출력 경로를 대조한다.

## 출시 판정과 이후

실제로 제공하기로 한 화면·PDF·HWPX에서 내용 누락·글리프 깨짐·심한 넘침·낡은 미리보기·잘못된 쪽번호를 방치하지 않는다. 현재 PR40 공개 PNG HWPX는 그림 데이터 포함까지 확인했지만 새 그림 표본의 실제 한글 출력은 미검증이다. Windows 한글·iPad/iOS·실계정 문서 복귀도 별도 미검증이며 지원 범위 축소는 자동 결정하지 않는다. [통합 레일](DEV-TOKEN-ROADMAP.md)의 전2 완료 기준을 따른다.

전2에 직접 필요한 내부 경로·화면/출력 결함을 먼저 다루고, 다중 한글 버전의 포괄적 함수 지도·완전한 원본 글꼴 유사화·자동 수식 분할/축소·범용 조판기 확장은 출시 후 품질 개선으로 둔다. 새 제품 범위, production/staging 변경, 도메인 구매, 실자료 이관을 이 문서로 승인하지 않는다.
