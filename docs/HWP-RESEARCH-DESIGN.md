## 1. 목표와 적용 경계

목표는 우리 문서·모의고사가 **내용을 보존하고, 한글에서 열리고, 의도한 모양으로 출력되고,
다시 저장해도 깨지지 않게** 하는 것이다. REA는 원인을 좁히는 분석 수단이다.
분석 결과는 최소 표본과 호환 규칙으로 바꾼 뒤 우리 코드로 구현한다.
한글 설치·상용 바이너리를 브라우저나 운영 서버의 런타임 의존성으로 들이지 않는다.

최초 요청은 분석과 설계였고, 2026-10-15 사용자는 에이전트 협업을 통한 심화 분석과 조판 스킬 개선을 요청했다.
현재 구현 범위는 연구 하네스·표본·스킬 개정과 H1-c 합의에 따른 구역 패키지 진단/출력 차단이다.
새 블록·스키마·UI·저장 이관은 후속 구현 묶음으로 넘긴다.
N제 HWPX, 완전한 WYSIWYG, 한글 전체 기능 재현은 이 설계로 승인되지 않는다.
상자 안 표·그림의 제품 편입은 기존 R2 범위 판단을 따르고, 지문 관계는 REV-108 계약을 따른다.

세 가지 성공 조건을 따로 기록한다:

1. **문서 의미**: 문항·문단·수식·그림·관계가 빠지거나 바뀌지 않는다.
2. **파일 호환**: 패키지·참조·컨트롤이 유효하고 실제 한글에서 열고 저장할 수 있다.
3. **지면 품질**: 줄·단·쪽 경계, 수식 기준선, 표·그림·각주가 의도대로 보인다.

Python↔JS 일치는 1~3의 독립 증명이 아니다. 두 구현이 같은 실수를 할 수 있다.

태그 하나의 차이만으로 결론이 안 나면 최소화와 조합 시험을 함께 한다.

그 다음 수식 크기/기준선이다. 실패 골격을 찾지 못하면 기록으로 재구성한 표본임을 표시한다.
실물 blank 교체는 성과 목표가 아니다. 유효한 골격을 유지하면서 유용한 거절 진단을 얻어도 성공이다.

### REA를 쓰는 구간

1. 공개 규격·정상 문서 XML·기존 ①~④ 실험으로 남은 질문을 한 문장으로 고정한다.
2. 원본·사본·도구 버전을 기록하고 문자열 또는 알려진 함수에서 시작한다.
3. 문자열 → xref → 호출자/호출 대상 → 판정 분기 순으로 좁힌다. 간접 호출 미해결은 미해결로 둔다.
4. 한 질문당 최초 최대 5개 함수만 상세 분석한다. 소득 없으면 표본 최소화로 돌아가고 확장 이유를 기록한다.
5. 얻은 규칙은 실제 한글 정상/실패 표본으로 검증한다.

## 4. 실험 기록과 판정 설계

표본마다 다음 필드를 가진 manifest를 만든다. H1-a 첫 패키지 표본과 열기 관찰은
[실험 결과](HWP-RESEARCH-RESULTS.md)에 있으며 저장/PDF/폰트 필드는 아직 미확인이다:

- `caseId`, 질문, 정상/변형 관계, 입력 JSON·HWPX 해시, 변경한 XML 경로/속성.
- 저장소 commit, 한글 버전/빌드/OS/아키텍처, 폰트 이름·버전·파일 해시, 도구 버전.
- 열기 결과(`pass/fail/skip/unknown`), 저장 결과, PDF 해시/쪽 수, 내용 비교, 전체 쪽 시각 판정.
- 관찰/추론/미확인 구분, REA evidence ID·주소·분석 설정, 반례, 적용 가능한 버전 범위.
- 원문·이미지의 출처와 공개 가능 여부. 공유 표본은 직접 만든 비식별 문서로 한다.

`skip`은 성공에 합산하지 않는다. UI 권한 부재·콜드 스타트·오류 대화상자 잔류는 문서 실패와 분리한다.
정상 대조군도 실패하면 그 실험 전체를 무효로 하고 환경을 복구한다. 기존 사용자 문서 창을 닫지 않는다.
**하네스 선행 조건**: H1-a에서 `check-hwpx-opens.mjs`의 전체 창 닫기를 제거하고
정확한 시험 창만 닫도록 좁혔다(`HANDOFF-189`). Claude가 직접 만든 기존 문서의 보존을 재현하고
접근성 포커스 처리를 수정했다(`2547a1e`). Codex 검토·모호한 창/병합/정리 후 창 감소 반례 보강은 `HANDOFF-190`에 있다. 사용자 작업이 없는 시험 세션을 쓴다.

판정은 다섯 층을 함께 본다:

1. 입력 기준 의미 대조(Q1): 구현끼리만 비교하지 않고 각각 입력과 비교한다. 기존 Q1은 모의고사 payload 중심이며 아래 일반 문서 확장은 아직 구현 전이다.
2. 현재 구조 검사: 필수 파트·manifest·itemCnt·일부 ID/fontRef 참조. 표의 선언 수/격자와 일반 범위·단위는 H1-c에서 별도 명세·구현한다. 현재 경고인 것을 근거 없이 오류로 올리지 않는다.
3. JS/Python parity: 새 기능의 위치·속성·참조·오류까지 대조한다.
4. 실제 한글 열기·저장: 미확인은 따로 남긴다.
5. PDF 모든 쪽: 내용 누락·수식·겹침·넘침·반복 요소·페이지 경계. 텍스트 추출만으로 수식을 판정하지 않는다.

**Q1 일반 문서 확장**: 본문·상자/보기 label, 표 `(행,열)` 셀, 각주와 그 부착 위치,
문서 최상위 머리말·꼬리말을 별도 scope로 비교한다. 원시 입력→정규화 입력의 허용 변화(현재 trim 등)를
명시하고 그 외 손실은 실패시킨다. 생성 코드/validator를 그대로 비교 oracle로 재사용하지 않는다.
본문 공백·탭 접기를 표·수식·레이아웃 신호에 무조건 적용하지 않는다.
수식 개수·위치가 같아도 수식 내용 교체는 통과할 수 있으므로, 의미는 별도 변환 fixture와 실물 시각 판정으로 본다.

시각 비교는 OS/한글/폰트가 같은 기준본을 사용한다. 좌표·줄/쪽 경계를 먼저 보고 픽셀 차이를 보조로 쓴다.
허용 오차는 정상 반복 출력의 변동을 재어 결정한다. 글꼴 대체를 허용 오차로 감추거나 기준본을 자동 승인하지 않는다.
한글이 다시 저장하며 바꾼 타임스탬프·ID 등은 명시한 항목만 정규화한다. 본문 순서와 참조 의미는 보존한다.
Q2 kordoc은 오류 탐지 보조 후보로만 평가하고 한글 호환 판정을 대신하지 않는다.

### 검사가 실제로 잡는지 확인

후속 검사에는 수식 하나 제거, 본문 두 블록 교환, 이미지 바이트 교체, 잘못된 스타일 참조,
머리말을 잘못된 부모에 부착, pageBreak+columnBreak 동시 설정, stale lineseg 삽입을 실패 표본으로 둔다.
각 검사별로 **어떤 변형을 어느 판정 층에서 잡아야 하는지** 먼저 적는다. 구조 검사 하나에 시각 결함 검출을 약속하지 않는다.
`stale lineseg`의 전용 구조 검사는 현재 미구현이다. H1-c에서 캐시 유효성/제거 정책과 담당 층을 정하고,
명백히 낡은 표본 및 정상 캐시 표본 양쪽으로 검사한다. 현재 검사에서 반드시 빨간불이라고 쓰지 않는다.
단순 예외·환경 실패는 red 성공이 아니다. 기대한 결함 신호가 생겨야 한다.
기존 수정의 red는 과거 commit/최소 변형, 새 기능 검사는 해당 기능 전 기준본을 사용한다.

재귀 표 검사 도입 시에는 다음 짝을 H1-d 종료 조건으로 추가한다(현재 구현 완료 주장은 아님):

| 변형/대조군 | 담당 층·기대 결과 |
| --- | --- |
| rowCnt/colCnt와 실제 격자 불일치 | 2층 양쪽 strict validator가 같은 구조 오류로 거절 |
| cellSpan 겹침·cellAddr 범위 초과·빈 구멍 | 2층 점유 격자 검사 거절, 정상 병합 표는 통과 |
| 빈 rows·행 길이 불일치로 엔진 직접 호출 | 엔진 API 거절 + 3층 Python/JS 오류 parity |
| 허용된 빈 셀 1개·전부 빈 행 | 정상 대조군. 입력/구조 통과와 내용 보존 확인, 실물 열기/PDF로 근거 확보 |
| 확정된 scope 안 ID 충돌 | 2층 거절. 다른 scope 재사용은 확정 규칙에 맞는 대조군으로 구별 |


## 5. 우리 엔진으로 옮기는 설계

공통 호환 규칙·fixture를 먼저 만들고 기존 Python/JS 쌍에 같은 의미로 적용한다.
새 조판기 전체 재작성이나 공통 IR 도입을 선행 조건으로 만들지 않는다.

- **지원 능력 표**: 기능별 입력 허용/출력 가능/미리보기 가능/실물 검증 버전을 분리한다.
  실패는 블록 경로·원인·지원하지 않는 속성을 보고한다. 원문을 조용히 버리는 fallback은 금지한다.
  현재 수식 변환 실패 표시·warning 경로를 보존하며, 중단/경고 정책은 기능별 계약에서 정한다.
- **단위·스타일**: mm/pt/HWPUNIT 변환과 반올림 경계를 명시한다. 스타일은 역할로 찾아 ID로 resolve한다.
  재저장한 ID를 제품 의미로 저장하지 않는다. 본문과 표 셀/각주/머리말의 스타일 scope를 나눈다.
- **재귀 요소**: 상자 안 표·그림 채택 시 `text` 호환을 유지할지 version 이관할지 먼저 정한다.
  허용 부모/자식, 최대 깊이·총 노드·셀·텍스트·그림 바이트/픽셀 예산을 함께 정하고 모든 경계가 같은 제한을 검사한다.
  셀 병합은 중복 점유·빈 구멍·범위 초과를 검사한다. 셀 수식과 다문단도 따로 지원 판정한다.
  재귀 writer는 `rowCnt`/`colCnt` 선언과 실제 격자(`cellAddr`/`cellSpan`)를 양쪽 strict validator에서 대조하도록 설계한다.
  엔진 API에서도 빈 rows·행 길이 불일치를 막아 스키마 우회 호출이 잘못된 표를 내지 않게 한다.
  빈 셀 글자와 빈 컨테이너는 구별한다. 허용된 빈 셀을 거절하지 않는다.
  문단·컨트롤 ID의 유일성 범위는 규격/실물로 확정하고 scope별 할당기를 둔다. **zOrder를 전역 고유 ID로 가정하지 않는다.**
  **ID scope가 미확정이면 새 재귀 기능을 지원 완료로 내보내지 않는다.** 기존 검증된 평면 경로는 유지한다.
  가장 좁은 scope를 임의 기본값으로 쓰는 것도 추측이므로 채택하지 않는다. H1-c가 규격/실물 근거와 실패 정책을 확정한다.
  새 제한을 기존 v1 유효 문서에 소급해 조용히 잘라내지 않는다. 호환/버전 이관과 경고·거절 정책을 먼저 정한다.
- **입력 안전성**: 현재 고정 template 사용과 일반 문서 base64 그림 계약을 유지한다.
  임의 HWPX 가져오기를 추가한다면 ZIP 해제 크기/항목 수/중복 경로·경로 탈출·외부 XML 참조·Scripts/OLE/외부 리소스 정책을 먼저 정한다.
  이것을 현재 사용자 업로드 취약점이 재현됐다는 주장으로 쓰지 않는다.
- **UI 후속**: U2 등 해당 제품 묶음에서 미지원·글꼴 대체·출력 차이와 수정할 위치를 보여준다.
  이번에는 UI 코드를 바꾸지 않는다. 원문/권한/삭제 계약과 내보내기 변경을 섞지 않는다.

새 일반 문서 블록은 엔진 Python/JS, block writer Python/JS, Python schema,
브라우저 validate/render, Worker 프롬프트/응답 검증을 모두 갱신한다. image의 AI 제외 예외는 유지한다.
모의고사는 `hwpx-exam.js`/`mock_to_hwpx.py` 및 template·payload를 별도로 확인한다.
새 배포 파일이 생기면 `serve.py STATIC`과 `scripts/build-public.mjs PUBLIC_INPUTS`를 함께 갱신한다.
