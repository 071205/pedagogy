# 저장 계약 — 크기·충돌·부분 실패 (R3 확정)

- 확정: `2026-09-21` · 근거: [문제 투입 설계](PROBLEM-INTAKE-DESIGN.md) §20~§23 (코덱스 왕복 4회)
- 레일 위치: [통합 실행 레일](DEV-TOKEN-ROADMAP.md) R3 → **R4 가 이 문서를 구현한다**

⚠️ **이 문서가 정답표다.** 값이나 판정 지점을 바꿀 때는 여기부터 고치고, 왜 그 자리인지
근거가 없으면 바꾸지 않는다. 설계 과정의 논박은 §20~§23 에 있다.

## 0. 이 계약이 서 있는 전제

⚠️ **정확히 한 번(exactly-once)은 만들 수 없다.** AI 호출 · Firestore 쓰기 · 원장 확정은
서로 다른 시스템이라 한 트랜잭션으로 묶이지 않는다 — `worker/index.js:83` 이 이미 그렇게 적고
있다. 아래 계약은 **그 전제 위에서 손실과 중복을 줄이는 것**이지 없애는 것이 아니다.

⚠️ **한 곳만 고치면 도달하지 않는다**(이 저장소의 반복 실패 2번). 각 묶음의 '함께 고칠 곳' 을
표로 박아 둔다.

## 1. 크기 방어 (§20)

### 1-1. 판정 지점 — **`writeCloudSnapshot()` 의 직렬화 직후 하나뿐이다**

`index.html` 의 `writeCloudSnapshot()` 에서 `setToDoc(s,i)` 를 만들어 깊은 복사한 직후
`ready` / `tooBig` 으로 가른다. **`ready` 만 batch 에 넣는다.**

⚠️ **다른 곳에 두면 안 되는 이유 — 되돌리지 말 것.**

| 후보 | 왜 안 되나 |
|---|---|
| `saveSets()` | **로컬 보존까지 맡는다.** 여기서 거절하면 클라우드 한도 때문에 **로컬 복구본도 못 남긴다** |
| `docToSet()` | **읽기·복구 경로**이고 `lossless:true` 로 기존 자료를 보존한다. 여기서 자르면 **기존 대형 자료를 읽는 순간 손실된다** |
| `newProblem()` | 빈 문항 생성기라 문제집 전체 크기를 모른다 |
| `firestore.rules` | 20,000문항 상한은 **개수 방어**다. `normProblem(lossless)` 은 문자열·블록을 안 자르므로 **개수로 바이트를 보장할 수 없다** |

### 1-2. 값과 함수

- 기준: **UTF-8 바이트 900KiB** = `CLOUD_DOC_MAX`. Firestore 문서 한도 1MiB 의 여유분.
  ⚠️ **문제집과 모의고사가 같은 상수를 쓴다.** 예전 이름 `MOCK_DOC_MAX` 를 되살리지 말 것 —
     갈래 이름이 붙으면 한쪽만 고치게 된다(2026-09-21 에 공용 이름으로 바꿨다).
- 측정: 기존 `docBytes()` 를 **공용화해 그대로 쓴다**(`TextEncoder`, 실패 시 `길이×3`).
  ⚠️ **글자 수로 재지 말 것** — 한글은 3배라 1.4MB 짜리가 한도를 통과한다.
- ⚠️ **새 함수를 만들지 않는다.** 모의고사 경로(`ready`/`tooBig` 분리)와 **같은 함수를 공유**한다.
  베끼면 갈라진다(반복 실패 3번).

### 1-3. 초과 시 동작

- ❌ 작업 전체 거절 · ❌ 자동 분리(**묶음 문항·출처 순서·사용자가 의도한 경계를 끊는다**)
- ✅ **초과한 그 문제집을 이름으로 특정**해 "두 개 이상으로 나눠 주세요" 라고 말한다.
- ✅ **원본도 복제본도 지우지 않는다.** `sets` 와 로컬에 그대로 두고 **클라우드 batch 에서만 뺀다.**
  클라우드 쓰기 전 `flushLocal()` 이 먼저 도는 기존 순서가 이를 뒷받침한다.
- ⚠️ **초과본을 `cloudSynced` 로 표시하지 않는다.** 별도의 '크기 초과 지문' 을 기억해
  무한 재시도·반복 토스트만 막고, 내용이 줄어 **지문이 바뀌면 다시 재어 올린다.**
- 로컬 저장까지 실패하면 기존 계약대로 메모리에 유지하고 **즉시 JSON 내보내기를 안내**한다.

### 1-4. 함께 고칠 곳 · 검증

| 고칠 곳 | 왜 |
|---|---|
| `index.html` (`writeCloudSnapshot`·`docBytes` 공용화) | 본체 |
| 회귀 검사 | 아래 다섯 |

**검증** — ① 한글 포함 900KiB **경계값** ② 정상·초과 **혼합 batch**(정상분은 올라간다)
③ 초과본의 **로컬 잔존과 미동기화 상태** ④ **분할 후 재업로드** ⑤ **원본 불변**.
⚠️ **깨보기**: 글자 수 계산으로 바꾸거나 초과 문서를 batch 에 넣도록 심었을 때
**실제로 빨간불이 나야 한다.**

**호환** — 크기 제한은 **스키마 변경이 아니다.** Rules·정규화·모의고사 저장 계층을 건드릴 이유가
없고 **기존 데이터 호환성에 영향이 없다.**

## 2. 충돌 검출 — 문서별 `revision` + CAS (§21-1)

### 2-1. 계약

- 클라우드 문서에 **정수 `revision`**. 최초 생성 `1`, **수정·재정렬·tombstone 모두 정확히 +1**.
- 저장은 **transaction** 으로: `server.revision === baseRevision` 일 때만 `+1` 로 쓴다.
  - 쓰려던 내용이 **서버와 같으면** 이미 반영된 것으로 **ACK**.
  - 내용이 **다르면 충돌로 중단**.
- 신규 ID 는 **문서 부재**를 기대값으로 삼는다. **tombstone 도 같은 CAS 를 거친다.**

### 2-2. ⚠️ 기준값을 담을 곳이 지금 없다

`cloudSynced` 는 **메모리뿐이라 새로고침에 사라진다.** **owner 별 로컬 동기화 메타데이터**
(`{revision, 내용 해시, order}`)를 새로 만든다.
⚠️ `stampsKey` 의 **시각은 편집·병합 보조값으로만** 남기고 **CAS 근거로 쓰지 않는다.**

**B2 구현 계약**:

- 키는 `PM_SET_SYNC_META_V1:<uid>`. guest에는 쓰지 않고 계정 전환 때 해당 owner 것만 읽는다.
- 값은 `{v:1, entries:[{id, revision, contentHash, order}]}`. B3 전 구형 서버 문서는
  `revision:null`, B3 전환 뒤에는 양의 정수만 허용한다. `0`을 구형 revision처럼 쓰지 않는다.
- `contentHash`는 기존 `setJSON()` 결과의 버전형 짧은 지문이다. 사용자 내보내기 JSON이나
  Firestore 문서에는 들어가지 않으며 비밀·무결성 경계로 쓰지 않는다.
- **현재 관측 서버 상태인 `cloudSynced`와 마지막 ACK 기준을 분리한다.** 성공한 commit 또는
  최종 로컬 내용·order와 실제로 같은 서버본을 채택했을 때만 기준을 전진시킨다. 다른 원격본을
  관측했거나 commit·크기 검사가 실패했을 때는 전진시키지 않는다.
- Firestore의 `metadata.hasPendingWrites:true`인 로컬 지연 보상 snapshot과
  `metadata.fromCache:true`인 cache snapshot은 서버 ACK가 아니다. 이 둘은 `cloudSynced`나
  영속 기준을 전진시키지 않고, 서버 확정 snapshot 또는 성공한 commit만 ACK로 인정한다.
- query snapshot 하나에 pending 로컬 쓰기와 다른 문서의 확정 원격 변경이 함께 올 수 있다.
  비확정 snapshot을 보류했다면 metadata 확정 이벤트를 구독하고, 첫 서버 확정 때 전체 `docs`를
  한 번 적용해 빈 `docChanges()` 때문에 다른 문서 변경·tombstone을 잃지 않는다.
- 본문과 메타데이터 localStorage 쓰기는 원자적이지 않다. B3가 기준을 쓸 때는 현재 로컬의
  `contentHash`와 `order`가 모두 맞아야 하며, 하나라도 다르면 **기준 없음**으로 처리한다.
- 개별 삭제 ACK에서는 해당 항목을 지우고, 모든 문제집·계정 삭제에서는 owner 키를 지운다.

### 2-3. ⚠️ 시각 비교를 충돌 판정에서 뺀다

지금 `watchCloud` 는 `localStamp > d.updatedAt` 으로 덮어쓰고 `mergeSets` 는 `updatedAt` 으로
승자를 고른다. **둘 다 충돌 판정에서 제외한다** — 로드맵이 *"시각만 서버 시각으로 바꾸는 것은
충돌 해결이 아니다"* 라고 못박았다.
▶ **원격 revision 이 전진했는데 로컬이 기준 ACK 와 다르면 덮어쓰지 않고 충돌 상태로 간다.**

### 2-4. Rules 파급과 **배포 순서**

- `hasOnly` 에 `revision` 추가(**양의 정수** 검증).
- 합쳐진 `allow create, update` 를 **분리**: create `revision==1` / update
  `revision == resource.data.revision + 1` / **무 revision 문서의 최초 승격만** `==1` 허용.
- ⚠️ **한 단계 배포는 안전하지 않다.** 구 규칙은 새 필드를 거부한다.
  ▶ **전환 규칙(선택적 수용) → revision 클라이언트 배포 → 엄격 규칙** 순서.
  ▶ ✅ **이 저장소가 두 번 해 본 방식이다** — `service-config.js` 의
  `libraryCloudSchema`·`mockCloudSchema` 단계 플래그를 같은 모양으로 쓴다.
- 사용자용 **내보내기 JSON 에는 `revision` 을 넣지 않는다.**

### 2-5. 충돌 UX

⚠️ **자동 병합하지 않고 어느 쪽도 폐기하지 않는다.**

- 서버 원본은 그대로 둔다.
- **로컬 초안을 새 ID 의 일반 문제집으로 한 번만 복제**해 즉시 로컬 보존한다.
  업로드 ACK 전에는 **"이 기기에만 보존됨"** 으로 표시한다.
- 화면에 보일 것: 원본 이름 · "다른 기기 변경/삭제" · **기준 revision 과 현재 revision** ·
  로컬 사본 위치. ⚠️ **시각은 설명용일 뿐 승자 판정에 쓰지 않는다.**
- 선택지 넷: `두 버전 보기` · `서버본으로 돌아가기` ·
  `로컬본으로 서버 교체`(최신 revision 을 새 기준으로 한 **명시 CAS**) · `로컬본 export`.
- ⚠️ 같은 `{setId, baseRevision, serverRevision, localHash}` 에서 **사본을 반복 생성하지 않는다.**

**B4 구현 계약**(2026-09-25 · Codex Astra high 설계 2회 + Sol medium 검토 2회 · `HANDOFF-2026-169`):

- 충돌 기록 `PM_SET_CONFLICTS_V1:<uid>` 를 **사본보다 먼저** 쓰고, 기록에 **충돌 당시 본문(snapshot)** 을 통째로 담는다.
  사본 쓰기 전에 종료되거나 다른 탭이 `sets` 를 덮어도 같은 copyId 로 다시 만든다. 사용자가 지운 사본은 되살리지 않는다.
  사본은 문제집당 하나다(더 적게 만드는 것은 위 조건을 지킨다). 상한 50건을 넘으면 기록하지 않고 '지금 내보내기' 안내로 떨어진다.
- 기록 키는 `navigator.locks` 안에서 **다시 읽고 합쳐** 쓴다(같은 브라우저 탭끼리).
- 기록이 있는 문제집은 **동결**이다 — 저장 시도·편집기·이름·폴더·삭제에서 빠진다. 기록 생성과 해결 때 되돌리기 기록
  (스택·지연 타이머·`lastSnapshot`)을 비운다. 전체 스냅샷 복원이 해결 경계를 넘으면 버린 초안이 다시 올라간다.
- 비교·내보내기·교체의 '로컬본' 은 **기록의 snapshot** 이다. 사본은 따로 편집되는 일반 문제집이라 그 이후 편집은 교체에 들어가지 않는다.
- 서버본은 충돌 화면이 **서버에서 새로 읽어**(`source:"server"`) 보여 준다. 교체는 그 snapshot 에 결부된 명시 CAS
  (`explicitBase`)이고 부재·동일본문 분기보다 먼저 본다. '서버본으로' 는 그 snapshot 의 모양대로 기준을 세운다
  (살아 있으면 본문·order 가 같을 때만 영속 기준 · tombstone 이면 쓰기 기준만 · 부재면 없음).
- 해제는 둘뿐이다 — 사용자의 선택 성공, 서버 확정본이 충돌 당시 초안·지금 로컬과 본문·**충돌 당시 order·지금 order** 까지 같음.
  hash 가 어긋났다고 풀지 않는다.
- ⚠️ 일반 `sets` 의 같은 브라우저 탭 간 localStorage 덮어쓰기는 B4 이전부터의 **별도** 문제다(B4 는 기록 키만 직렬화한다).

## 3. 부분 실패와 재개 (§21-2 · §22 · §23)

### 3-1. staging — **기존 문제집에는 아무것도 넣지 않는다**

10쪽 중 4쪽 실패 시:

| 대상 | 처리 |
|---|---|
| 1~3쪽 | 결과 + **원본 위치·꼬리표·출처 순서·응답 체크섬**을 staging 에 확정 저장 |
| 4쪽 | 실패 원인 · **quota 차감 영수증/attempt ID** · 실패 상태. ⚠️ **검증 실패한 생성 결과는 채택 결과로 저장하지 않는다** |
| 5~10쪽 | `pending` |
| 버린다 | **재생성 가능한 값만**(임시 렌더 버퍼). 원본 파일·작업 설정·공급자/모델·프롬프트/스키마 버전·파일 해시는 **보존** |

- 채택은 **전체 완료 후**, 또는 사용자가 **`성공한 쪽만 문제집 만들기`** 를 명시적으로 고를 때.
  **원본 문제집은 변경하지 않는다.**
- 중간 저장소는 **작업 전용 IndexedDB**. 쪽 결과와 원본 Blob 은 `localStorage` 에 부적합하다.
  ⚠️ 이것은 **저장 구조의 IndexedDB 일괄 전환이 아니다** — 다중 입력 재개에 한정된 staging 이라
  로드맵의 '일괄 전환 유보' 와 충돌하지 않는다.

### 3-2. 중복 방지 — **쪽 단위**

- 안정 키: `userId + jobId + sourceHash + pageNumber + extractionContractHash`
- ⚠️ **키는 클라이언트가 조립해 보내지 않는다.** 다른 UID 를 주장할 수 있고 원문 식별자가 그대로
  저장된다. **서버가 인증된 UID 와 검증된 값들을 결합해 HMAC**(서버 비밀 · 버전형)으로 만든다.
  평문 SHA-256 은 입력 후보가 좁으면 **추측 공격**이 된다.
- 그 아래 유료 호출마다 **`attemptId`**.
- `success` 인 쪽은 **결과 체크섬과 함께 종결 잠금**하고 '이어서 하기' 대상에서 뺀다.
- ⚠️ **자동 재시도 없음.** 사용자가 **`4쪽 다시 시도 — 1회 추가 차감`** 또는
  **`건너뛰고 5쪽부터`** 를 고른다.

### 3-3. `AttemptLedger` — **별도 Durable Object**

⚠️ **`DailyQuota` 에 얹지 않는다.**

| 왜 | 근거 |
|---|---|
| 날마다 다른 객체가 된다 | `quotaKey()` 가 **UTC 날짜**를 키에 넣는다 → 작업이 자정을 넘기면 다른 객체 |
| 항목마다 48시간이 아니다 | alarm 이 **첫 예약 때 한 번만** 걸리고 `deleteAll()` 한다 → 47시간째 기록은 **1시간 뒤** 삭제 |
| quota 멱등 ≠ 호출 멱등 | 같은 `reservationId` 재예약이 `{ok:true}` 를 주면 **Worker 는 공급자를 그대로 다시 부른다** |

**계약**
- 사용자별 DO 하나: `HMAC(요청 신원) → {state, expiresAt, resultDigest?}`
- 접근할 때마다 **트랜잭션 안에서 만료분 제거.**
- **alarm 은 가장 이른 `expiresAt` 에 맞추고, 실행 시 만료분만 지우고 다음 시각으로 재예약**한다.
  ⚠️ `deleteAll()` 하지 않는다.
- **`pending` 10분 이내 · `completed` 7일.** 무기한 보존하지 않는다.
- **일일 quota 객체는 지금의 48시간·일자별 구조를 그대로 둔다.**
- ⚠️ **계정 삭제 시 파기 계약이 반드시 필요하다.** 삭제 **전** 재인증된 호출이나 Auth 삭제 훅이
  사용자별 ledger DO 를 찾아 지운다. **삭제 후에는 토큰이 없으므로 사후 클라이언트 호출에
  의존할 수 없다.**

### 3-4. 결과 유실 — **(다) 48시간 후 재실행 허용**

해리의 결정(2026-09-21). 세 제약(48시간 파기 · 내용 비보관 · 유실 결과 재전송)은 **동시에
만족할 수 없다**(§22-3). 7일 원장 안에서는 **중복 호출이 완전히 막히고**, 그 뒤에 이어서 하면
**다시 과금된다.**

▶ **내구성 보강: Service Worker outbox.** AI 응답을 **페이지에 넘기기 전에** Service Worker 가
Cache/IndexedDB 에 복제하고, 다음 실행에서 복구해 **기존 클라이언트 권한으로** 올린다.
내용이 **사용자 장치에** 남고 Worker 의 역할이 늘지 않는다.

▶ **하지 않는 것**: 결과를 사용자 Firestore(`users/{uid}/aiJobs`)에 Worker 가 써 넣는 안은
**보류**한다. ⚠️ `users/{uid}` 는 **사용자 소유의 별도 Firebase 가 아니라 우리 프로젝트 안의
UID 격리**라 "서비스가 보관하지 않는다" 가 성립하지 않고, 클라이언트가 위조할 수 있어
**과금 원장의 권위 근거가 될 수 없다.** 교차 기기 복구가 **실측으로** 필요해질 때만,
그때도 **서비스 계정 없이 사용자 ID 토큰만** 쓰고 **비권위 캐시**로 취급한다.
