# U0 — AI 일괄 구성·채택·지면 UX 계약 초안

- 작성: 2026-09-23 · Codex
- 상태: **계약 초안·연결 시안 작성/독립 검토 완료. D1 방향 선택, 연동 저장 계약·D2/D4 확인 전. U0 전체 완료 아님.**
- 실행 위치·담당은 [통합 레일](DEV-TOKEN-ROADMAP.md), 사용자 요구는 [제품 UX](PRODUCT-UX-DESIGN.md).
- [저장 계약](STORAGE-CONTRACT.md)이 우선한다. 아래 새 데이터 모양과 정책은 구현 제안이며 현재 기능이 아니다.
- 2026-09-23 사용자 D1 답: **"원하는대로 선택할 수 있게"**. 아래 §3~5는 기존 독립 사본
  경로의 초안이며, 공유 경로의 저장·충돌·삭제 계약은 아직 설계/구현되지 않았다.
- D2 작업 종료 시 원문 삭제는 권장 전제일 뿐 **사용자 승인으로 간주하지 않는다.**

## 1. 유지할 계약과 HANDOFF-162 답변

R2 비라우팅·호출당 한 쪽·쪽별 순차·명시 재시도, R3 900KiB 클라우드 방어·로컬 보존·
서버 확정 ACK·revision/CAS·tombstone·owner/epoch 격리·자동 병합 금지를 유지한다.
B1/B2·B3 코드/독립 검토·R4.5 완료 증거는 그대로다. **B3는 전환 Rules·플래그 1 Pages까지
운영 적용(2/3)됐고 엄격 Rules·인증 저장 검증은 남았다.**

| HANDOFF-162 질문 | 이번 답변 | 남은 결정 |
| --- | --- | --- |
| Q1 복제/공용 풀/혼합 | 최초 독립 사본 권장에서 사용자가 **삽입 시 독립/연동 선택**으로 방향을 바꿨다. 기존 문항은 그대로 두고 두 경로를 명시적으로 구별한다 | 연동 경로의 버전·참조·삭제·내보내기 계약은 B4/B6 전에 추가 설계 |
| Q2 B3/B4 순서 | 기존 B3 코드 승인 유지. 전환 Rules와 좁은 플래그 1 Pages는 배포됐고 엄격 Rules는 대기. B4는 B3 실제 배포 완료와 충돌 시안 확정 뒤. B5는 독립 가능 | 연동 저장의 영향 경계만 Astra high가 B4/B6 전에 설계. 완료된 동일 diff를 처음부터 재검토하지 않음 |
| Q3 제품 핵심 | 사용자 요구대로 AI로 문항 편집을 쉽게 하고 원하는 문제를 모아 편집·조판한다. 구성안·편집·전체 지면이 연결된 작업물이 중심 | 조판만 핵심이라는 잠정안을 채택하지 않음. 사람 검토와 직접 만들기 경로 유지 |

## 3. 데이터와 식별자 — 기존 독립 사본 경로의 초안

D1 선택 후 **독립 사본과 수정 연동을 모두 제공**해야 한다. 사용자가 문항을 권에 넣을 때
선택을 드러내고, 연동 문항 수정 전 영향을 받는 권을 보여준다. 기존 문제집/문항은 자동으로
연동 대상으로 바꾸지 않는다. 연동을 끊을 때에는 그 시점 내용을 독립 사본으로 보존해야 한다.

연동 경로는 원본 문항 ID·버전, 문제집별 배치/번호, 동시 수정의 CAS와 충돌 사본,
원본/참조 삭제, 오프라인 읽기·내보내기/복원, 900KiB 측정 지점 및 구버전 클라이언트
호환을 먼저 계약으로 정해야 한다. **B3의 `users/{uid}/sets/{setId}` revision은 현재
문제집 문서에만 적용**된다. 그것을 미래의 공용 문항 원본에 대한 충돌 검출로 오인하지 않는다.
이 새 경계는 B4/B6 전에 Astra high 설계와 독립 검토가 필요하다. 기존 B3 Rules는 새 공용
컬렉션을 만들거나 막는 규칙이 아니므로 현재 문제집 CAS 전환은 독립적으로 유지할 수 있다.

작업 전용 IndexedDB에 `schemaVersion`을 둔다. 라이브러리를 IndexedDB로 일괄 이전하거나
Firestore에 새 문항 풀/영구 PDF 컬렉션을 만드는 안이 아니다. 필드 이름은 구현 전 검토 대상이다.

| 레코드 | 최소 정보·관계 | 보존/역할 |
| --- | --- | --- |
| 작업 `jobId` | owner, 원본 목록, 설정, 공급자/모델·프롬프트/추출 스키마 버전, `draftVersion`, 상태 | owner별 격리. 비동기 처리 시 세션 epoch 검증. 계정 전환으로 다른 owner 작업을 채택하지 않음 |
| 원본 `sourceId` | 파일명·종류·바이트·쪽수·로컬 원본 해시·Blob 참조 또는 기존 문제집의 읽기 시점 사본 | 파일명은 식별자가 아님. 같은 파일 재선택 시 내용 검증. 기존 문제집 원본은 수정하지 않음 |
| 쪽 결과 `(sourceId,pageNumber)` | 순서·검증된 문항·응답 체크섬, pending/processing/success/failed, attemptId·차감 영수증·실패 이유 | 성공 저장 후 재개에서 제외. 검증 실패 원문은 채택 문항으로 등록하지 않음 |
| 초안 문항 `draftProblemId` | 내용·원본 쪽/쪽 내 순서·꼬리표·검토 상태·공통지문 관계 | 순서나 제목 변경에도 같은 ID. AI가 준 ID를 앱 내부 식별자로 신뢰하지 않음 |
| 목적지 `destinationId` | 문제집 이름·순서·선택한 문항 ID, 선택 제외/미분류 처리, 구성 버전 | 이름을 바꿔도 같은 목적지. 사용자 명시 선택 없이 누락·권수 증가 없음 |
| 채택 `adoptionId` | owner+job, 고정된 구성 버전, 목적지→새 `setId`, 문항 배치 항목→새 `problemId`, 초기 내용 지문, 권별 상태 | 라이브러리 쓰기 전에 매핑을 영속화. 재진입은 같은 ID 사용. 의도적인 '다시 복제'는 새 채택으로 명시 |

**독립 사본 경로에서는** 같은 초안 문항을 서로 다른 권에 넣으면 각각 새 문항 ID와 독립 내용 사본을 만든다.
한 권 내 중복 삽입도 명시 복제 항목으로 구분한다. 출처 ID는 자동 수정 전파 키가 아니다.
추출/분류 제안은 `draftVersion`에 결합한다. 적용 전 현재 버전이 달라졌으면 차이를 다시 계산한다.
수동 본문·수식·정답은 분류/재배열로 덮어쓰지 않는다. 적용 전후 변경 범위를 보여주고 한 번에 Undo한다.

### 꼬리표·검토·호환 제안

- 문항 내부에 버전형 `intake` 메타데이터를 제안한다. 단원은 자유 문자열 목록과 AI/user 출처,
  난이도는 값과 AI/user 출처, 배점은 숫자 또는 `null`(원문 없음/확인 불가 구분)을 둔다.
  난이도를 배점으로 대체하지 않는다. 길이·개수·열거값 검증은 B6 스키마에서 명시한다.
- 본문/정답과 분류의 검토 상태를 구분한다. AI 생성은 `unreviewed`, 명시 확인한 해당 버전만
  `reviewed`. 저장·단순 타이핑·높은 AI 확신도는 확인 완료가 아니다. 확인 뒤 내용이 바뀌면
  영향받은 부분은 다시 미확인이다. 메타데이터 없는 기존 문항은 `unknown`이며 소급 검토 완료 금지.
- 내보내기에는 안전한 출처 표시명·쪽/순번·추적 ID와 꼬리표/검토 상태를 포함한다.
  UID·attempt 영수증·인증값·원장 키·로컬 Blob 주소·서버 revision은 넣지 않는다.
  가져온 출처는 외부 표기 정보로 처리하며 로컬 원문 접근 권한이나 새 작업 복구를 부여하지 않는다.
- `normProblem()`은 현재 알려진 필드만 반환하므로 새 필드는 지금 그대로는 소실된다.
  B6에서 AI 입력 검증→정규화→클라우드 변환→JSON 내보내기/복원→복제/Undo까지 함께 연결한다.
  기존 문서 AI 응답 스키마를 일괄 변경하지 말고 task별 추출 스키마를 사용한다.
- 이전 버전 편집기가 새 메타데이터를 지우는 위험을 B6 호환 검토에 포함한다. 지원 버전 안내와
  새 메타데이터를 읽지 못하는 경로의 저장 차단/업데이트 방안을 정하기 전 무손실 호환을 선언하지 않는다.
  기존 메타데이터 없는 JSON은 계속 읽고, 외부 500문항 방어를 `lossless`로 무조건 우회하지 않는다.
- `setToDoc()`의 최상위 필드와 Rules `hasOnly`는 유지할 수 있다. 문항 내부 메타데이터 증가만으로
  Rules 변경을 요구하지 않되 타입 검증·900KiB 실측은 필요하다. ID 재발급 시 문항 간 참조도 함께 바꾼다.
- **공통지문 묶음과 인쇄 배치 묶음은 다르다.** `groupSpan/groupLead/passage` 관계를 보존하며
  `problemGroups()`의 pair/col/page 배치로 지문 의존성을 추론하지 않는다. 초기안은 공통지문 묶음
  단위 이동·채택이며 쪽 경계의 관계가 불명확하면 보류한다. 독립 분리는 필요한 지문 동반을 검증한 뒤만 허용한다.

## 4. 여러 권 채택·부분 저장·재진입

**권별 성공과 전체 성공을 분리한다.** IDB·localStorage·Firestore는 한 트랜잭션이 아니다.
아래는 복구 가능한 기록을 만드는 절차이며 분산 exactly-once 보장이 아니다.

1. 전체 쪽 성공 또는 사용자의 '성공한 쪽만 사용' 선택을 확인한다. 미분류/보류/제외 수를 보여주고
   목적지 처리까지 확정한다. 미처리 쪽·미분류 문항을 생성 결과에 포함한 것처럼 세지 않는다.
2. 채택 버튼 연타와 여러 탭의 같은 작업을 직렬화한다. 고정된 구성·내용과 **모든 결과 ID 매핑**을
   IDB 트랜잭션으로 먼저 기록한다. 실패하면 라이브러리 생성으로 진행하지 않는다.
3. 현재 owner/epoch와 라이브러리 최신 상태를 다시 확인하고 없는 결과를 같은 ID로 추가한다.
   `saveSets()`는 예약일 뿐이다. 실제 `flushLocal()` 성공과 해당 ID/내용 보존을 확인해야
   '이 브라우저에 저장됨'이다. 기존 경로는 전체 배열 한 번 쓰기이므로 권별 원자 저장이라고 주장하지 않는다.
4. 로컬 기록 뒤 채택 장부를 갱신한다. 클라우드는 기존 큐·크기 검사·CAS를 사용한다.
   ACK 전에는 동기화 완료 표시를 하지 않는다. 정상 권은 올라가고 초과 권만 클라우드 대기한다.
5. 재진입 시 매핑의 각 ID와 실제 라이브러리/확정 서버 상태를 대조한다. 이미 있는 권은 재생성하지
   않으며 이후 사용자가 편집한 내용도 초기 사본으로 되돌리지 않는다. 충돌은 B4로 연결한다.
6. 누락된 권만 재개하되 tombstone/삭제 기록이 있으면 자동 부활시키지 않는다. 한 번 저장된 권의
   현재 상태를 오프라인 등으로 알 수 없으면 '확인 필요'로 멈춘다. 새 ID 우회 복제 금지.
   매핑이 사라졌으면 자동으로 재채택했다고 추정하지 않고 라이브러리 확인·복구/새 복제를 명시 선택한다.

잠금만으로 다른 탭의 오래된 전체 배열 저장을 막았다고 보지 않는다. B6는 **채택 및 경쟁하는
라이브러리 쓰기의 조정 범위**를 설계·검증해야 한다. 구형 탭/지원하지 않는 환경에서 안전하게
조정할 수 없으면 다른 편집을 닫고 새로 읽도록 안내하고 채택을 보류한다. 새 저장 계층의 일괄 도입은 별도 설계다.

| 권별 관측 상태 | 화면·복구 계약 |
| --- | --- |
| ID 매핑만 저장 | 만들기 대기. 같은 ID로 재개 |
| 로컬 저장 실패 | 메모리/초안 유지, 실패 권 표시·JSON 내보내기. 만들기 완료와 초안 삭제 금지 |
| 로컬 저장 성공, cloud pending/offline | 이 브라우저에 저장됨 / 동기화 대기. 편집 가능 |
| cloud tooBig/error/conflict | 크기 초과·저장 오류·충돌을 구별. 다른 권 ACK 유지, 해당 권 보존/분할 또는 B4 선택 |
| 실제 서버 ACK | 그 권만 클라우드 동기화됨. 캐시/pending snapshot은 ACK 아님 |
| 이미 저장한 권 삭제/상태 불명 | 삭제됨/확인 필요. 원치 않는 복원·덮어쓰기 금지 |

예: 5권 중 3권 ACK·1권 로컬만·1권 저장 실패면 세 수를 각각 표시한다. '5권 저장 완료' 금지.
채택 중 구성안은 고정한다. 남은 구성을 고치려면 기존 채택을 마무리/중단하고 미채택 항목만
새 구성으로 넘긴다. 이미 만든 권 수정은 편집기에서 한다. 생성 취소가 클라우드 삭제나 AI 환불을 뜻하지 않는다.

## 5. 원문·결과·원장 수명

- D2 권장안: 작업이 진행/보류 중이면 원문 Blob·설정·검증된 결과를 유지한다. 결과를 모두
  로컬에 보존한 뒤 '작업 종료·원문 삭제'를 명시 선택한다. 잔여 실패/미처리/미채택분이 있으면
  버릴 범위를 먼저 보여준다. 뒤로 가기·탭 닫기·일부 채택은 폐기가 아니다.
- 원문 삭제 전에 결과가 사용하는 그림을 독립적으로 지속 보존했는지 확인한다. 임시 Blob URL이나
  원본 PDF 삭제에 종속된 그림이면 종료를 막고 복구/내보내기를 안내한다. 결과·그림은 원문과 함께 지우지 않는다.
- 종료 시 원본 위치 표기는 남지만 '원문 보기'는 이용 불가 이유를 표시한다. 장기 보존은 D2의
  별도 선택이며 숫자 TTL을 임의로 붙이지 않는다. 브라우저 저장소 삭제/회수 시 복구 불가 가능성은 안내한다.
- 계정 전환에는 숨기고 중단한다. 계정 삭제/명시 폐기는 해당 owner staging/outbox를 정리하고
  진행 중 늦은 응답이 복구본을 되살리지 못하게 한다. B5 원장 파기는 인증 삭제 전/서버 훅 계약을 따른다.
- 원장 `pending` 10분 이내 / `completed` 7일, DailyQuota 48시간은 **서로 다른 수명**이다.
  저장 계약 §3-4 제목의 '48시간 후'와 본문의 7일 표현이 다르므로 UI는 §3-3과 본문의
  **7일 성공 잠금**에 맞추고 원문을 조용히 고치지 않는다. B5 검토 때 이 문구 차이를 확인한다.
- 로컬 성공 결과가 없어도 활성 성공 잠금 동안 자동 재호출하지 않는다. B7 outbox 복구를 먼저
  시도하고 실패하면 '처리 성공 기록은 있으나 이 브라우저에서 결과를 찾을 수 없음'을 표시한다.
  jobId를 자동 교체해 잠금을 우회하지 않는다. 원장 만료 후 재처리는 사용자 명시 선택·새 차감 안내가 필요하다.
  원장은 결과 내용 백업이 아니며 다른 기기 복귀/브라우저 종료 후 처리 지속을 약속하지 않는다.

## 6. D3 한도·비용 경계

운영 숫자는 C2 측정→C3 제안→사용자 선택 대기다. 아래 설정이 없으면 일괄 AI 실서비스를 켜지 않는다.

| 단위 | 검증·집행 위치 | 초과/불명일 때 |
| --- | --- | --- |
| 파일 수·파일별/합계 원본 바이트·선택 쪽수 | 파일 파싱 전후 클라이언트, 작업 등록 시 서버 검증 가능한 선언값 | 호출 전 범위 축소 안내. 파일 선택만으로 과금 없음 |
| 실제 쪽 이미지 바이트·해상도·요청 크기 | 렌더 직후 클라이언트 + 공급자 호출 전 서버 | 저해상도/과대 요청 거절. 다른 모델로 자동 우회 없음 |
| 작업 누적 호출/재시도·사용량 예산 | 인증된 작업별 서버 기록 및 quota 예약, 매 호출 직전 | 다음 쪽 중단·성공분 유지. 클라이언트 수치는 과금 권위가 아님 |
| 추출 문항 수·필드/블록 크기 | 응답 검증·쪽 확정 전, 작업 누적 및 채택 전 | 추출 전 미리 알 수 없음. 초과 결과를 조용히 절단해 성공 처리하지 않음. 실패 이유/이미 발생한 차감은 보존 |
| 외부 JSON·채택 결과 | 기존 외부 가져오기 500 방어; B6는 검증된 내부 초안용 명시 한도 경로 | 외부 입력을 무제한 lossless로 우회하지 않음. 초과면 사용자 범위/분할 선택 |
| 클라우드 문서 UTF-8 바이트 | 기존 `writeCloudSnapshot()` 직렬화 직후 900KiB | 클라우드만 제외. 로컬·원본 유지, 자동 분할 없음 |

클라이언트 원본 파일/문항 집계만으로 서버의 경제적 상한을 보장할 수 없다. 원본을 영구 보관하지
않는 구조에서는 서버가 실제 수신한 요청 크기·횟수·인증된 사용량을 집행한다. 새 jobId로 작업 한도를
우회해도 사용자 quota를 넘지 못해야 한다. C3는 원화 예상치와 공급자 토큰/호출 상한의 관계를 명시한다.
정확한 비용을 계산할 수 없으면 범위/상한과 불확실성을 표시하며 확정 요금처럼 말하지 않는다.
필터·순서 변경은 AI 0회. 추가 유료 분류/재추출은 별도 처리 범위·추가 차감 안내 후 시작한다.
로컬 fixture의 작은 한도/모의 차감은 테스트 설정으로만 두며 운영 기본값으로 승격하지 않는다.
