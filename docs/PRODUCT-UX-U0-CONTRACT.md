## 3. 데이터와 식별자

D1 선택 후 **독립 사본과 수정 연동을 모두 제공**해야 한다. 사용자가 문항을 권에 넣을 때
선택을 드러내고, 연동 문항 수정 전 영향을 받는 권을 보여준다. 기존 문제집/문항은 자동으로
연동 대상으로 바꾸지 않는다. 연동을 끊을 때에는 그 시점 내용을 독립 사본으로 보존해야 한다.

**B3의 `users/{uid}/sets/{setId}` revision은 문제집 문서만 보호**한다. 공유 문항은 별도의
revision/CAS가 필요하다(§3-1). 원문 파일의 `sourceId`는 수정 전파 키도 클라우드 접근 권한도 아니다.

작업 전용 IndexedDB와 공통 원문 보관 기반에 `schemaVersion`을 둔다. 라이브러리 전체의
IndexedDB 이전은 하지 않는다. 원문 Blob은 서버에 보관하지 않는다. 필드·경로 이름은 설계 제안이다.

| 레코드 | 최소 정보·관계 | 보존/역할 |
| --- | --- | --- |
| 작업 `jobId` | owner, 원본 목록, 설정, 공급자/모델·프롬프트/추출 스키마 버전, `draftVersion`, 상태 | owner별 격리. 비동기 처리 시 세션 epoch 검증. 계정 전환으로 다른 owner 작업을 채택하지 않음 |
| 원문 `sourceId` | owner·불변 파일 ID·파일명·종류·바이트·쪽수·로컬 해시·Blob. 작업은 §5 공통 보관소를 참조 | 파일명은 식별자가 아님. 기존 문제집 재구성은 읽기 시점 스냅샷이며 살아 있는 권의 수정 권한이 아님 |
| 쪽 결과 `(sourceId,pageNumber)` | 순서·검증된 문항·응답 체크섬, pending/processing/success/failed, attemptId·차감 영수증·실패 이유 | 성공 저장 후 재개에서 제외. 검증 실패 원문은 채택 문항으로 등록하지 않음 |
| 초안 문항 `draftProblemId` | 내용·원본 쪽/쪽 내 순서·꼬리표·검토 상태·공통지문 관계 | 순서나 제목 변경에도 같은 ID. AI가 준 ID를 앱 내부 식별자로 신뢰하지 않음 |
| 목적지 `destinationId` | 문제집 이름·순서·선택한 문항 ID, 선택 제외/미분류 처리, 구성 버전 | 이름을 바꿔도 같은 목적지. 사용자 명시 선택 없이 누락·권수 증가 없음 |
| 채택 `adoptionId` | owner+job, 고정된 구성 버전, 목적지→새 `setId`, 문항 배치 항목→새 `problemId`, 초기 내용 지문, 권별 상태 | 라이브러리 쓰기 전에 매핑을 영속화. 재진입은 같은 ID 사용. 의도적인 '다시 복제'는 새 채택으로 명시 |

**독립 사본 경로에서는** 같은 초안 문항을 서로 다른 권에 넣으면 각각 새 문항 ID와 독립 내용 사본을 만든다.
한 권 내 중복 삽입도 명시 복제 항목으로 구분한다. 출처 ID는 자동 수정 전파 키가 아니다.
추출/분류 제안은 `draftVersion`에 결합한다. 적용 전 현재 버전이 달라졌으면 차이를 다시 계산한다.
수동 본문·수식·정답은 분류/재배열로 덮어쓰지 않는다. 적용 전후 변경 범위를 보여주고 한 번에 Undo한다.

### 꼬리표·검토·호환 제안

- 문항 내부에 버전형 `intake` 메타데이터를 제안한다. 단원은 자유 문자열 목록과 AI/user 출처,
  난이도는 값과 AI/user 출처, 배점은 숫자 또는 `null`(원문 없음/확인 불가 구분)을 둔다.
  난이도를 배점으로 대체하지 않는다. 길이·개수·열거값 검증은 B6 스키마에서 명시한다.
- 문항별 원문 출처는 `intake.sources:[{sourceId,pages:[…]}]`처럼 **문항 메타데이터**에 둔다.
  여러 파일·여러 쪽을 허용하고 문항 ID가 바뀌어도 같은 owner 내 복제·충돌 사본·Undo·백업
  왕복에서 보존한다. 권 연결은 이 출처를 찾기 위한 별도 색인이며 출처 자체를 대신하지 않는다.
  외부 JSON의 출처는 표기만 보존하고 §5-2의 명시 연결 전 로컬 파일 접근에 사용하지 않는다.
- 본문/정답과 분류의 검토 상태를 구분한다. AI 생성은 `unreviewed`, 명시 확인한 해당 버전만
  `reviewed`. 저장·단순 타이핑·높은 AI 확신도는 확인 완료가 아니다. 확인 뒤 내용이 바뀌면
  영향받은 부분은 다시 미확인이다. 메타데이터 없는 기존 문항은 `unknown`이며 소급 검토 완료 금지.
- 내보내기에는 안전한 출처 표시명·쪽/순번·추적 ID와 꼬리표/검토 상태를 포함한다.
  UID·attempt 영수증·인증값·원장 키·로컬 Blob 주소·서버 revision은 넣지 않는다.
  가져온 출처는 외부 표기 정보로 처리하며 로컬 원문 접근 권한이나 새 작업 복구를 부여하지 않는다.
- `normProblem()`은 현재 알려진 필드만 반환하므로 새 필드는 지금 그대로는 소실된다.
  `lossless`는 길이·개수 제한만 풀며 모르는 필드를 보존하지 않는다.
  B6에서 AI 입력 검증→정규화→클라우드 변환→JSON 내보내기/복원→복제/Undo까지 함께 연결한다.
  기존 문서 AI 응답 스키마를 일괄 변경하지 말고 task별 추출 스키마를 사용한다.
- 이전 버전 편집기가 새 메타데이터를 지우는 위험을 B6 호환 검토에 포함한다. 지원 버전 안내와
  새 메타데이터를 읽지 못하는 경로의 저장 차단/업데이트 방안을 정하기 전 무손실 호환을 선언하지 않는다.
  기존 메타데이터 없는 JSON은 계속 읽고, 외부 500문항 방어를 `lossless`로 무조건 우회하지 않는다.
- `setToDoc()`의 최상위 필드와 Rules `hasOnly`는 유지할 수 있다. 문항 내부 메타데이터 증가만으로
  Rules 변경을 요구하지 않되 타입 검증·900KiB 실측은 필요하다. ID 재발급 시 문항 간 참조도 함께 바꾼다.
- **공통지문 묶음과 인쇄 배치 묶음은 다르다.** `groupSpan/groupLead/passage` 관계를 보존하며
  `problemGroups()`의 pair/col/page 배치로 지문 의존성을 추론하지 않는다. 초기안은 공통지문 묶음
  단위 이동·채택이며 쪽 경계의 관계가 불명확하면 보류한다. 독립 분리는 필요한 지문 동반을 검증한 뒤만 허용한다.
  이동/제외 후에는 구성원 ID로 목적지의 실제 연속 구성을 검증하고 `groupSpan`을 다시 계산한다.
  무관한 다음 문항 흡수·지문 없는 꼬리 문항 채택은 금지한다. `REV-2026-108`은 별도 코드 수정 전 계속 열린 이슈다.

### 3-1. D1 공유 문항·권별 참조의 저장 경계 — 검토할 확장안

여기의 **공유 원본은 편집 가능한 문항 내용**이다. §5의 **원문은 PDF/이미지 파일**이다.
공유는 동일 owner의 문제집 사이에 한정한다. 타 계정 참조·공개 문항 풀은 만들지 않는다.

| 저장 단위 | 권위·수정 범위 | CAS·삭제·실패 경계 |
| --- | --- | --- |
| 공유 문항 `(owner, sharedProblemId)` | 예: `users/{uid}/sharedProblems/{id}`. 본문·수식·정답·내용 꼬리표/검토 상태·revision·tombstone. 공통지문은 구성원 ID가 있는 묶음 단위 | 독립 문서 CAS: 신규 1, 변경/삭제 +1. 기준 불일치 시 자동 병합·재시도 없이 서버본과 로컬 초안 보존 |
| 권별 배치 `(setId, problemId)` | 기존 `problems` 항목에 `sharedRef:{id, observedRevision}`와 마지막 확인 내용 사본. 번호·순서·풀이 공간·출력 배치는 권별 값 | 기존 B3 set revision/CAS·900KiB 유지. 참조/사본 크기도 직렬화 직후 포함해 잼. 공유 revision을 set revision으로 대체하지 않음 |
| 독립 사본 | 새 `problemId`와 완전한 내용·그림. `sharedRef` 없음 | 기존 문제집 CAS만 사용. 출처 표시는 수정 전파를 일으키지 않음 |

- 연동 편집은 '연동된 문항 수정'과 '여기서만 수정(연동 해제)'를 구별한다. 영향받는 권 목록은
  서버에서 확인한 참조를 기준으로 표시한다. 오프라인/확인 실패이면 전체 범위를 단정하거나
  공유 수정·새 연동을 확정하지 않고 초안/독립 사본만 보존한다. 참조 목록 캐시는 권한 근거가 아니다.
- 공유 내용 저장은 원본 CAS 한 번이다. 다른 권 배열을 순회해 자동 덮어쓰지 않는다. 열린 권은
  새 revision을 감지해 공유 내용만 반영하되 미저장 편집과 만나면 충돌로 보류한다. 닫힌 권은
  다음 읽기 때 갱신한다. 따라서 '모든 권 동기화 완료'는 원본 ACK만으로 표시하지 않는다.
- 화면/출력은 확인한 공유 revision의 스냅샷을 사용한다. 결과물 한 번을 만드는 동안 버전을 고정하고
  새 revision 도착 시 다시 준비하게 한다. 오프라인이면 마지막 확인본과 그 revision을 표시한다.
  권별 사본 갱신은 기존 set CAS를 거치며 충돌/크기 초과 시 이전 사본도 남긴다.
- 공유 원본 생성 → 원본 ACK → set 참조 CAS 순서다. 중간 실패 시 영속화한 ID 매핑으로 같은
  작업을 재개하며 거짓 연동 완료를 표시하지 않는다. 고아 원본을 자동 삭제하거나 새 ID로 우회하지 않는다.
  참조 추가와 원본 tombstone 확인은 하나의 서버 transaction/Rules 검증으로 묶어 삭제와 경쟁하지 않게 한다.
- 권에서 문항/권을 삭제하면 그 참조만 제거한다. 원본을 지우는 별도 동작은 영향 범위를 표시하고
  tombstone으로 새 참조/수정을 막는다. 기존 참조가 읽을 마지막 내용은 보존하며 '원본 삭제됨'으로
  표시해 독립 사본으로 전환할 수 있게 한다. 계정 삭제 외 실제 내용 파기는 참조 없음이 서버에서
  확인되고 새 참조 생성이 차단된 뒤 명시 선택으로만 한다. 원문 파일 수명에는 직접 영향이 없다.
- 연동 해제는 확인한 revision의 내용·그림을 해당 권에 보존하고 `sharedRef` 제거를 같은 set CAS로
  확정한다. 실패하면 연동 상태를 그대로 표시한다. Undo로 공유 내용을 전역 롤백하지 않는다.
  재연동은 원본 생존·현재 revision·영향 범위를 다시 확인하는 새 명시 작업이다.
- 내보내기는 확인한 내용을 완전한 사본으로 담고 **가져오기는 독립 사본**으로 시작한다.
  내부 공유 ID·서버 revision은 내보내지 않는다. 외부 파일이 그런 값을 주장해도 살아 있는 원본을 재연결하지 않는다.
- **구현 게이트**: B6에서 독립 채택/원문 보관과 연동 저장 확장을 분리한다. 연동은 owner Rules,
  원본별 크기 방어, 참조 무결성, 계정 삭제, 지원 버전/구형 쓰기 차단, 전환·롤백을 저장 계약의
  별도 추가안으로 검토한 뒤 활성화한다. 기존 B3 문서 규칙을 약화하거나 승인된 diff를 재작성하지 않는다.
  이 개정의 경계 검토만으로 새 컬렉션 배포까지 승인된 것은 아니다.
- 위 게이트에는 **서버 역참조 색인과 완전성 검증**을 포함한다. 예를 들어 공유 문항 아래
  `refs/{setId}`에 그 권의 배치 ID들을 기록하고 set 참조 추가/제거·복제·삭제와 같은 transaction으로
  갱신하는 안을 검토한다. `problems` 배열 안의 참조만으로 전체 참조 목록을 조회·검증할 수 있다고
  가정하지 않는다. Rules가 원본 생존·양방향 참조 일치를 집행할 수 있는지, 기존 자료 이관·부분 실패·
  누락 색인의 복구·트랜잭션 한계를 검증하기 전 연동 활성화나 '참조 없음'에 근거한 원본 파기를 허용하지 않는다.

## 4. 여러 권 채택·부분 저장·재진입

**권별 성공과 전체 성공을 분리한다.** IDB·localStorage·Firestore는 한 트랜잭션이 아니다.
아래는 복구 가능한 기록을 만드는 절차이며 분산 exactly-once 보장이 아니다.

1. 전체 쪽 성공 또는 사용자의 '성공한 쪽만 사용' 선택을 확인한다. 미분류/보류/제외 수를 보여주고
   목적지 처리까지 확정한다. 미처리 쪽·미분류 문항을 생성 결과에 포함한 것처럼 세지 않는다.
2. 채택 버튼 연타와 여러 탭의 같은 작업을 직렬화한다. 고정된 구성·내용과 **모든 결과 ID 매핑**을
   IDB 트랜잭션으로 먼저 기록한다. 실패하면 라이브러리 생성으로 진행하지 않는다.
3. 현재 owner/epoch와 라이브러리 최신 상태를 다시 확인하고 없는 결과를 같은 ID로 추가한다.
   `saveSets()`는 예약일 뿐이다. 실제 `flushLocal()` 성공과 해당 ID/내용 보존을 확인해야
   '이 브라우저에 저장됨'이다. 기존 경로는 전체 배열 한 번 쓰기이므로 권별 원자 저장이라고 주장하지 않는다.
   한 번의 flush에 포함된 권은 모두 로컬 성공 또는 모두 실패다. 여러 번 나눠 flush했을 때만
   권별 로컬 결과가 갈릴 수 있다. IDB 장부는 실제 flush에 포함된 ID들을 함께 기록한다.
4. 로컬 기록 뒤 채택 장부를 갱신한다. 클라우드는 기존 큐·크기 검사·CAS를 사용한다.
   ACK 전에는 동기화 완료 표시를 하지 않는다. 정상 권은 올라가고 초과 권만 클라우드 대기한다.
5. 재진입 시 매핑의 각 ID와 실제 라이브러리/확정 서버 상태를 대조한다. 이미 있는 권은 재생성하지
   않으며 이후 사용자가 편집한 내용도 초기 사본으로 되돌리지 않는다. 충돌은 B4로 연결한다.
6. 누락된 권만 재개하되 tombstone/삭제 기록이 있으면 자동 부활시키지 않는다. 한 번 저장된 권의
   현재 상태를 오프라인 등으로 알 수 없으면 '확인 필요'로 멈춘다. 새 ID 우회 복제 금지.
   매핑이 사라졌으면 자동으로 재채택했다고 추정하지 않고 라이브러리 확인·복구/새 복제를 명시 선택한다.

잠금만으로 다른 탭의 오래된 전체 배열 저장을 막았다고 보지 않는다. B6는 **채택 및 경쟁하는
라이브러리 쓰기의 조정 범위**를 설계·검증해야 한다. 구형 탭/지원하지 않는 환경에서 안전하게
조정할 수 없으면 다른 편집을 닫고 새로 읽도록 안내하고 채택을 보류한다. 새 저장 계층의 일괄 도입은 별도 설계다.

| 권별 관측 상태 | 화면·복구 계약 |
| --- | --- |
| ID 매핑만 저장 | 만들기 대기. 같은 ID로 재개 |
| 로컬 저장 실패 | 메모리/초안 유지, 실패 권 표시·JSON 내보내기. 만들기 완료와 초안 삭제 금지 |
| 로컬 저장 성공, cloud pending/offline | 이 브라우저에 저장됨 / 동기화 대기. 편집 가능 |
| cloud tooBig/error/conflict | 크기 초과·저장 오류·충돌을 구별. 다른 권 ACK 유지, 해당 권 보존/분할 또는 B4 선택 |
| 실제 서버 ACK | 그 권만 클라우드 동기화됨. 캐시/pending snapshot은 ACK 아님 |
| 이미 저장한 권 삭제/상태 불명 | 삭제됨/확인 필요. 원치 않는 복원·덮어쓰기 금지 |

예: 5권 중 3권 ACK·1권 로컬만·1권 저장 실패면 세 수를 각각 표시한다. '5권 저장 완료' 금지.
채택 중 구성안은 고정한다. 남은 구성을 고치려면 기존 채택을 마무리/중단하고 미채택 항목만
새 구성으로 넘긴다. 이미 만든 권 수정은 편집기에서 한다. 생성 취소가 클라우드 삭제나 AI 환불을 뜻하지 않는다.

### 4-1. D4 결과 목록과 편집 직행 기억

- 기본은 한 권도 **권별 결과 목록**을 연다. 아래에 '다음부터 바로 편집기로 가기' 선택을 두고
  계정별·이 브라우저의 버전형 로컬 설정(예: `PM_INTAKE_PREFS_V1:<owner>`)으로 기억한다.
  저장 실패 시 '기억됨'으로 표시하지 않는다. 설정에서 언제든 켜거나 끌 수 있다.
- 기억을 켰어도 생성 목적지가 여러 권이면 목록을 유지한다. 일부만 성공해 현재 성공 권이
  하나인 경우도 여러 권 작업이다. 한 권이며 로컬 보존이 확인된 정상 결과만 편집기로 직행한다.
  미처리/실패/확인 필요·저장 오류·충돌이 있으면 목록에서 복구 범위를 먼저 보여준다.
- 정상 한 권의 cloud pending/offline은 편집을 막지 않되 편집기에 기기 저장/동기화 대기를
  표시하고 결과 목록으로 돌아갈 경로를 둔다. 목록 생략이 미검토 상태나 ACK를 바꾸지 않는다.
- 다른 owner의 값을 읽거나 guest 설정을 계정으로 자동 승계하지 않는다. 계정 전환 시 현재
  owner 값만 로드하고 계정 삭제 시 해당 키를 지운다. 클라우드 prefs와 Rules는 바꾸지 않는다.
  D4 키는 계정 삭제용 정리 목록에 포함하되, `accountLocalKeys()`는 현재 '모든 문제집 삭제'도
  공유하므로 무조건 추가하지 않는다. 문제집만 삭제해도 사용자 설정은 유지되도록 정리 범위를 분리한다.

## 5. 원문·결과·원장 수명

### 5-1. B6·U1.5가 함께 쓰는 기기 내 원문 보관

**D2②: 숫자 TTL 없이 연결된 동안 보존한다. 작업 종료는 원문 삭제가 아니다.** B6의 AI 자료와
U1.5의 수동 연결 PDF/이미지는 같은 저장소·읽기/연결/삭제 경로를 쓴다. U1.5 전용 사본 보관소를
따로 만들지 않는다. 원문 파일의 서버/계정 업로드·기기 간 동기화는 하지 않는다. 이는 보관 범위이며,
사용자가 시작한 기존 AI 처리의 **쪽 이미지 전송**까지 없어진다는 뜻은 아니다.

| 레코드·관계(제안) | 계약 |
| --- | --- |
| `(owner, sourceId)` | owner는 UID 또는 별도 guest 식별자. 무작위 sourceId·schemaVersion·파일 표시명/종류·바이트·쪽수·내용 해시·Blob·삭제 세대·상태. 바이트는 불변이며 다른 파일은 새 ID |
| 작업 연결 `(owner, jobId, sourceId)` | 진행·보류 작업이 보존 근거. 종료/폐기 후 작업 연결을 해제하되 원문 삭제와 분리 |
| 권 연결 `(owner, setId, sourceId)` | AI 채택·수동 연결의 색인. 문항별 출처는 §3의 `intake.sources`에 보존. 문항 쪽 지정 없는 수동 연결은 권 연결만으로 자유 탐색 |
| 원문 상태 | `available` / `unlinked`(선택 대기·명시 보관) / `deleting` / `deleted` / `missing`. 결과의 저장/ACK·미검토 상태와 독립 |

- 같은 owner 안에서 해시·바이트·종류를 검증해 기존 파일을 재사용할 수 있지만 파일명만으로
  같은 원문으로 보지 않는다. 다른 owner와 Blob/연결을 공유하지 않는다. 다른 내용으로 기존
  sourceId를 덮어쓰지 않으며 문항 쪽 번호의 범위를 검사한다.
- IDB 트랜잭션으로 Blob 저장과 첫 연결 기록이 성공한 뒤만 '이 브라우저에 보관됨'이다.
  AI 호출은 필요한 원문/작업 보존 성공 뒤 시작한다. 수동 연결 실패는 기존 문제집 내용을 바꾸지 않는다.
  채택 전 권 연결을 예정 상태로 기록하고 §4 ID 매핑과 실제 로컬 보존을 대조해 확정한다.
  도중 종료·다른 탭 갱신 때 예정 연결을 미참조로 오판해 원문을 지우지 않는다.
- **보존·삭제 영향 판단은 연결 색인만 믿지 않는다.** 같은 owner의 실제 로컬 문제집 문항 출처,
  충돌 기록 snapshot, 진행·보류 작업과 예정 연결을 합쳐 확인한다. 복제·충돌 사본 생성·백업 복구·
  Undo 때 색인을 맞추고, 색인 갱신 전 중단돼도 이 합집합으로 누락을 찾아 보존한다. 백업·Undo/Redo의
  복구 가능한 출처도 삭제 영향에 포함하되 현재 사용 중인 권과 구분해서 표시한다.
  원문 삭제 직전 같은 owner/epoch·최신 자료 세대를 다시 대조한다. 다른 탭 쓰기와 조정할 수 없거나
  일부 기록을 읽지 못하면 '확인 필요'로 보존하며 참조가 없다고 판정하지 않는다.
- **문제집 삭제(단일·선택·전체·원격 삭제)는 원문 삭제 질문을 띄우거나 Blob을 지우지 않는다.**
  다른 현재 연결이 있으면 그대로 유지하고, 마지막 현재 연결이 없어졌으면 `unlinked`로 보존하고
  원문 관리 안내만 한다. 작업 종료·중단 역시 원문 파기를 결합하지 않는다. 숫자 TTL·자동 GC는 없다.
  Undo/백업 복구로 권이 돌아오면 출처를 다시 대조해 색인을 보충하고, Blob이 남아 있는 경우에만
  `available`로 돌린다. 이미 명시 삭제/유실된 원문은 `deleted/missing`을 유지하며 자동 재생성하지 않는다.
- **마지막 연결의 명시 해제**와 **설정의 원문 관리**에서 파일·용량·현재 사용 권/작업·복구본까지
  영향을 표시하고 '원문도 삭제' / '원문만 이 브라우저에 보관'을 고르게 한다. 취소는 현 상태 유지다.
  이때 문항 출처와 권 연결 색인도 함께 맞추되 다른 문항/권/작업의 연결을 끊지 않는다. 연결 해제 Undo는
  살아 있는 Blob만 다시 연결하며, 별도로 선택한 원문 삭제는 Undo/백업으로 되돌릴 수 없음을 먼저 알린다.
- 설정에는 owner별 원문 목록·연결된 권/작업·사용 용량·원문 삭제·다시 연결을 제공한다.
  저장 전 파일/합계 바이트를 검사하고 저장소 여유는 추정치로 표시한다. 실제 쓰기 실패를 처리하며
  공간 확보를 위해 다른 원문을 자동 삭제하지 않는다. 구체적 운영 상한은 D3/C3에서 정한다.
- 원문 관리·삭제 작업은 파일 단위다. 남은 연결이 있어도 사용자가 그 범위를 확인해 **원문만 삭제**할
  수 있다. 결과 문항/그림은 유지한다. 연관 진행 작업은 먼저 멈추고 남은 쪽은 '원문 없음'으로 보류한다.
  결과 그림이 임시 Blob URL/원본 PDF에 의존하면 독립 보존을 확인하기 전 원문 삭제를 막는다.

### 5-2. 삭제·계정 경계·유실·재연결

- 원문 삭제는 먼저 같은 owner/sourceId의 삭제 세대를 올려 `deleting`으로 기록하고 모든 생산자
  (렌더·AI 응답 처리·outbox 복구·다른 탭)의 이전 세대 쓰기를 차단한다. Blob·썸네일·쪽 이미지
  캐시와 object URL을 정리한 뒤 `deleted`를 확정한다. 실패는 삭제 중/재시도로 남기며 완료로 표시하지 않는다.
  최소 삭제 기록은 오래된 작업/백업으로부터의 자동 부활을 막는 동안 유지하며 숫자 TTL로 지우지 않는다.
- 원문 삭제와 결과 채택 취소는 다르다. 늦은 응답은 원문/캐시/연결을 재생성하지 못한다.
  유효한 결과만 §4의 owner·작업 세대 확인 후 보존할 수 있으며 폐기한 작업의 결과는 자동 채택하지 않는다.
  B7은 원문 Blob을 outbox에 복제하지 않고 결과 복구만 담당한다. 원문 참조가 없으면 `missing/deleted`로 남긴다.
- 계정 전환/로그아웃은 읽기·진행 중 작업을 중단하고 epoch를 바꾸며 뷰어·object URL·메모리를 비운다.
  이전 owner의 로컬 원문은 숨겨 보존하고 같은 owner로 돌아왔을 때만 다시 읽는다. guest와 계정 간
  자동 이동은 없다. 계정 삭제에는 새 원문 저장소·연결·staging/outbox·D4 설정을 모두 포함하며,
  삭제 fence를 세워 늦은 쓰기를 막고 인증 삭제 전 로컬 정리와 B5 파기를 확인한다. 실패 시 완료 처리 금지.
- 원문이 없어도 문제집/결과는 유지한다. 다른 기기나 브라우저에는
  '이 브라우저에 연결된 원본이 없습니다 · 원본은 기기 간 동기화되지 않습니다 · 다시 연결'을 표시한다.
  명시 삭제·저장소 유실은 가능한 경우 원인을 구별한다. 출처 ID/쪽은 남겨도 Blob 접근 권한은 되살리지 않는다.
- 재연결은 파일 내용을 검증해 같은 파일의 쪽 대응만 재사용한다. 다른 내용이면 새 sourceId와
  명시적인 새 쪽 연결을 만들고 옛 대응을 자동 이식하지 않는다. 삭제된 원문은 같은 파일이라도
  새 보관 세대로 명시 등록하며, 오래된 작업 재시작은 별도로 확인한다. JSON 가져오기는 원문을 포함하지 않는다.
- 브라우저 저장소 삭제/회수·기기 고장은 보존을 보장할 수 없다. 저장소 전체가 사라지면 삭제 기록도
  없을 수 있으므로 백업/외부 JSON만 보고 파일을 자동 복원하지 않는다. 새 명시 연결을 요구한다.
  로컬 원문 보관 성공과 클라우드 문제집 ACK를 섞어 '원문 백업 완료'라고 표시하지 않는다.
- 장기 보관을 시작할 때 지원 여부를 확인해 `navigator.storage.persisted()`로 상태를 확인하고
  필요하면 `persist()`를 요청한다. 허용·거절·미지원·실패를 구분해 설정에 표시하며 거절 시에도
  실제 저장에 성공한 자료는 사용하되 브라우저가 회수할 수 있다고 알린다. 허용을 영구 보관/백업 보장으로
  표시하지 않는다. [WebKit 저장 정책](https://webkit.org/blog/14403/updates-to-storage-policy/)은
  용량 압박·장기간 상호작용 부재 등에 따른 회수와 영속 저장 요청을 설명한다. 고정 '며칠 뒤 삭제'는
  제품 계약으로 쓰지 않으며, 지원 브라우저·iPad 실측과 거절/회수 후 복구 검증은 B6/U1.5에 남긴다.

### 5-3. 결과와 서버 원장은 별도 수명

- 원장 `pending` 10분 이내 / `completed` 7일, DailyQuota 48시간은 **서로 다른 수명**이다.
  저장 계약 §3-4 제목의 '48시간 후'와 본문의 7일 표현이 다르므로 UI는 §3-3과 본문의
  **7일 성공 잠금**에 맞춘다. B5 검토 기록도 7일과 일치한다. 이 문구 차이는 원문 파일 TTL이 아니다.
- 로컬 성공 결과가 없어도 활성 성공 잠금 동안 자동 재호출하지 않는다. B7 outbox 복구를 먼저
  시도하고 실패하면 '처리 성공 기록은 있으나 이 브라우저에서 결과를 찾을 수 없음'을 표시한다.
  jobId를 자동 교체해 잠금을 우회하지 않는다. 원장 만료 후 재처리는 사용자 명시 선택·새 차감 안내가 필요하다.
  원장은 결과 내용 백업이 아니며 다른 기기 복귀/브라우저 종료 후 처리 지속을 약속하지 않는다.
