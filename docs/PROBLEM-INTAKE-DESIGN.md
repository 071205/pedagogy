# 문제를 어떻게 받아들일 것인가 — 투입 경로 설계

작성: 2026-09-19 · 작성자: `Claude` · 상태: **설계 제안 · 구현 0줄**
논의 상대: `Codex` — 이 문서는 **결정을 내리기 위한 것이 아니라 결정할 것을 분명히 하려고** 쓴다.

2026-09-20: 검토 순서·모델 배정은 [통합 레일 R2](DEV-TOKEN-ROADMAP.md)에 편입했다.
제품 갈래·입력 상한·요금 단위는 미확정이며 이 문서의 구현 보류는 유지한다.

⚠️ **아무것도 구현하지 않았다.** 사용자의 지시가 "새로 만들지 말고 문제를 남겨 두라" 였다.

## 왜 이 문서가 있나

사용자(해리)의 말 그대로 옮긴다:

> 우리 프로그램 구조 상 **한 문제에 사진 넣고 그 문제가 변환되도록** 하게 되어 있잖아.
> 근데 이게 **너무 비효율적인 것 같애**. 여러 pdf 때려넣고 "이렇게 문제 배치해서 이렇게
> 만들어줘" 하면 그걸로 json 만들어서 하면 훨 편할텐데 지금 포멧으로는 그게 안 되잖아.
> … 즉, **프로그램의 정체성**을 제대로 찾아야 된다고나 할까.

이건 결함 보고가 아니라 **제품이 무엇인가에 대한 질문**이다. 그래서 `issues/` 가 아니라
`docs/` 에 둔다(`reviews/README.md` — "새 설계를 내놓을 때만 새 파일을 만든다").

## 1. 지금 실제로 되는 것과 안 되는 것 — 코드로 확인했다

추측이 아니라 읽어서 적는다.

| | 지금 | 근거 |
|---|---|---|
| 한 번에 넣는 파일 | **하나** | `index.html` 파일 선택 `files[0]` · 드래그앤드롭도 `find(f=>f.type.startsWith("image/"))` 로 **첫 이미지 하나** |
| 받는 형식 | **이미지만** | `worker/index.js` 화이트리스트 `image/jpeg·png·webp·gif` — **PDF 없음** |
| 사용자 지시 | **없음** | 이미지 경로는 고정 문구 하나만 보낸다("이 이미지의 문제를 지정된 JSON 구조로 변환해 줘"). 사용자가 "이렇게 배치해" 라고 말할 채널이 없다 |
| 한 장에 여러 문항 | **된다** | 시스템 프롬프트가 "한 개(또는 여러 개)" 이고, 응답이 `problems[]`, 클라이언트가 `set.problems.push(...newQs)` 로 전부 넣는다 |
| 결과 배치 | **현재 문제집 끝에 덧붙임** | 같은 곳. 분류·순서·쪽 배치를 정할 수 없다 |

⚠️ **'한 문제에 사진 한 장' 은 계약이 아니라 UI 다.** 조판기도 AI 계약도 여러 문항을
이미 감당한다. 막힌 것은 넷뿐이다 — **① 여러 파일 ② PDF ③ 지시 ④ 배치.**

한편 **문서 경로**(`mode:"document"`)는 사용자 지시를 받는다. 다만 산출물이 **문서 블록
13종**이지 문제집이 아니다(`docs/AI-DOCUMENT-SCOPE.md` 에서 화면 입구까지 뺐다).
즉 "지시를 받아 구조를 만든다" 는 경험은 이미 저장소 안에 있고, **문제집 쪽에만 없다.**

## 2. 비용이 이 설계에 개입한다 (2026-09-19 측정)

- Claude Haiku 4.5 = 입력 $1 / 출력 $5 per 1M. **호출 1회 ≈ 10원**(입력의 대부분이 이미지).
- **한 장에 문항이 여럿이면 문항당 원가가 나뉜다.** 지금 구조(한 장 = 보통 한 문항)가
  **원가 면에서도 가장 비싼 방식**이다. 묶어 받는 것은 편의만이 아니라 비용 문제다.
- ⚠️ 그런데 반대 방향의 위험이 있다 — **PDF 한 권은 호출 한 번이 수만 토큰**이다.
  지금 한도는 **호출 수**로 센다(`DailyQuota` · `DAILY_LIMIT=50`/사용자/일).
  **묶어 받기 시작하면 '호출 1회' 의 원가가 10원에서 수백~수천원으로 벌어져 한도 모델이
  무너진다.** 이것이 이 설계의 가장 큰 충돌점이다.

## 3. 지금 구조가 거는 물리적 제약

| 제약 | 값 | 어디 |
|---|---|---|
| Worker 요청 본문 | 8MiB | `worker/index.js` `MAX_BODY_BYTES` |
| 로컬 서버 본문 | 4MiB | `serve.py` `MAX_BODY` |
| 이미지 업로드(Storage) | 5MB | `index.html` `MAX_UPLOAD_BYTES`(= `storage.rules`) |
| **AI 로 보내는 원본** | **20MB** | `index.html` `AI_MAX_INPUT_BYTES` ⚠️ 위 5MB 와 **다른 값**이다(코덱스가 지적) |
| 가져오기 문항 수 | 500 | `normSet` 기본 `maxProblems`(신뢰 경계) |
| 사용자 한도 | 50회/일 | `wrangler.toml` |

PDF 여러 개는 이 숫자들과 **정면으로 부딪힌다.** 교재 한 권이 수십 MB다.

## 4. 갈래 — 이 제품은 무엇인가

**A. 옮겨 적기 도구 (지금)**
사진을 찍으면 문항이 된다. 배치·분류는 사람이 한다.
· 장점: 원가 예측 가능, 검토 단위가 작다, 신뢰 경계가 단순하다.
· 단점: 자료가 많을수록 사람이 하는 일이 선형으로 늘어난다. 사용자가 느낀 불편이 이것.

**B. 자료 → 문제집 변환기**
PDF 여러 개 + "이렇게 배치해" → 문제집 한 벌.
· 장점: 사용자가 원하는 것. 문항당 원가가 내려간다.
· 단점: 원가·한도 모델을 다시 짜야 한다. **검토 경험이 제품의 핵심 문제가 된다**(200문항이
  한꺼번에 들어오면 무엇을 믿고 쓰나). 부분 실패 처리가 생긴다.

**C. 둘 다 — A 를 남기고 B 를 새 경로로**
· 장점: 지금 동작을 깨지 않는다. 이 저장소가 모의고사·AI 문서에서 이미 쓴 방식이다.
· 단점: 경로가 늘면 갈라진다(이 저장소가 세 번 겪은 실패 방식 3번).

## 5. B 로 갈 때 실제로 걸리는 것들

설계가 답해야 할 것이지, 지금 답이 있는 것이 아니다.

1. **입력 경로** — 본문에 base64 로 실어 보내는 지금 방식은 8MiB 에서 끝난다.
   Files API·청크·브라우저에서 쪽 단위로 쪼개기 중 무엇인가.
2. **PDF 를 누가 읽나** — 공급자에게 그대로 넘기나(Anthropic 은 document 블록으로 PDF 를
   받는다), 브라우저에서 쪽 이미지로 바꿔 보내나. 후자는 지금 이미지 경로를 재사용한다.
3. **한도 모델** — 호출 수 → 토큰/쪽 수로 바꿔야 하나. 바꾸면 `DailyQuota`·`PLAN_DAILY_LIMITS_JSON`
   ·출시 게이트가 함께 움직인다. ⚠️ `check:launch` 의 "유료 플랜별 AI 상한 설정이 없습니다"
   가 이미 열려 있는 항목이다.
4. **"이렇게 배치해" 를 무엇으로 내리나** — 우리 데이터 모델의 열거값이다:
   `paired`·`page`·`col`·`groupSpan`·과목·블록 종류. 자연어를 그 값으로 내리는 계약이 필요하고,
   **신뢰 경계(`normSet`/`normProblem`)를 반드시 지나야 한다.**
5. **검토 경험** — 한 번에 200문항이 들어오면 사용자는 무엇을 보나. 미리보기 후 채택?
   문항별 신뢰도 표시? **이게 B 의 성패를 가른다**(옮겨 적기가 틀리면 사용자가 바로 보지만,
   200개는 안 본다).
6. **부분 실패** — PDF 5개 중 3개만 성공하면 무엇을 저장하나. 재시도는 과금된다.
7. **저작권** ⚠️ — 시중 교재·문제집 PDF 를 통째로 변환하는 기능은 **제품 위험**이다.
   이 저장소는 이미 저작물에 민감하게 굴어 왔다(실물 자료를 `.gitignore`, 규격서 출처 고지).
   "사용자가 가진 자료를 옮겨 적는 것" 과 "남의 문제집을 기계로 복제하는 것" 의 경계를
   **기능을 만들기 전에** 정해야 한다.

## 6. 해리가 정해야 하는 것

코드로 답할 수 없는 것들이다.

1. **제품의 중심** — A / B / C 중 무엇인가.
2. **한 번에 받는 최대** — 파일 몇 개, 쪽 몇 장까지.
3. **검토 방식** — 다 받아 놓고 고치기 vs 미리 보고 채택하기.
4. **요금·한도의 단위** — 호출 수 vs 쪽 수·토큰.
5. **저작권 선** — 어떤 자료의 변환을 허용한다고 말할 것인가.

## 7. 코덱스에게 묻는 것

- 위 5번(검토 경험)이 B 의 진짜 병목이라는 판단에 동의하는가. 다른 병목이 있나.
- 한도를 토큰 기준으로 바꾸는 것과 호출 수를 유지하고 **입력 크기를 제한**하는 것
  (예: 한 번에 쪽 20장) 중 어느 쪽이 이 저장소의 구조에 덜 침습적인가.
- PDF 를 공급자에게 넘기는 것과 브라우저에서 쪽 이미지로 바꾸는 것의 득실.
  후자는 기존 이미지 경로·상한·신뢰 경계를 그대로 쓴다는 이점이 있다.
- C(둘 다)로 갈 때 "베낀 것은 갈라진다" 를 어떻게 막을 것인가 — 새 경로가 기존
  `aiBlocksToProblem`·`normProblem` 을 그대로 지나게 하는 것으로 충분한가.

## 8. 하지 않은 것

- **코드 0줄.** 설계·측정·기록뿐이다.
- 어떤 갈래가 맞는지 **고르지 않았다.** 그건 해리와 코덱스의 논의 결과다.
- 최초 작성 당시 비용 레일과 별도였으며, 2026-09-20 통합 레일 R2와 C3/R9의
  입력·비용·상품 계약에 연결했다. 기능 구현은 아직 시작하지 않았다.

## 9. 코덱스의 답 (2026-09-20) — 클로드가 독립 확인한 것까지

`codex exec --sandbox read-only` 로 §7 의 넷을 물었다(파일 쓰기 없음 · 토큰 67,658).
아래는 코덱스의 답을 옮기고, **클로드가 코드로 확인한 결과**를 함께 적은 것이다.

⚠️ 코덱스가 **이 문서의 오류 둘을 잡았다.** 그 둘은 위 본문에서 이미 고쳤다.

### 1. 검토 경험이 진짜 병목인가 — **부분 동의**

대량 변환의 성패가 "전수 검토 없이 오류를 찾고 **선택적으로 채택**할 수 있는가" 에 달려
있다는 데는 동의하되, **그보다 앞선 출시 차단선은 작업당 비용 상한과 실패 격리**라고 했다.

근거: 지금 Worker 는 **외부 호출 전에 사용량을 1회 확정**하고 **실패도 차감**한다.
✅ **클로드 확인** — 2026-09-18 에 실제로 겪었다. 두 호출 모두 502 로 실패했는데 그날 한도
2/2 가 소진됐다(`reserve`·`consume` 이 provider 응답 전에 끝난다).

그래서 수백 문항 작업에는 **검토 UI 보다 먼저** 쪽별 분할·취소·부분 성공·재시도 중복 방지
계약이 필요하다. 그다음 병목이 추출 품질이다(문항 수·순서·묶음이 틀리면 신뢰도 표시로는
검토량이 안 준다). 권장 경험은 전수 확인이 아니라 **쪽별 미리보기 → 저신뢰 구간 표시 →
구간별 채택**.

### 2. 한도의 단위 — **동의: (나) 호출 수 유지 + 입력 상한**

`PLAN_DAILY_LIMITS_JSON` 이 플랜별 **정수 호출 수**이고 `DailyQuota` 도 예약 하나를
`used += 1` 로 확정한다. 토큰/쪽 가중치로 바꾸면 예약 수량·pending 합계·상태 형식·개인/전역
DO·응답 문구·계약 검사를 **전부** 바꿔야 한다.

⚠️ 더 결정적인 것: **실제 토큰은 호출 뒤에 나오는데 지금 방어는 호출 전 consume** 이라,
토큰제로 가면 **최대치 선예약 + 사후 정산** 계약까지 새로 만들어야 한다. 반면 쪽·파일·크기
상한은 본문 검증처럼 **quota 차감 전에 거절**할 수 있다.

단서: "20쪽 1호출" 이 8MiB 본문 상한 안에 들어가는지는 **따로 재야 한다.**

### 3. PDF 를 누가 읽나 — **부분 동의**

⚠️ **R2 의 "기존 경로 재사용" 을 클로드가 과하게 읽었다.** 그것은 **출력 계약·정규화·반영
경로**를 재사용한다는 뜻이지, PDF 를 반드시 브라우저에서 이미지화한다는 결정이 아니다.

- (나) 브라우저 쪽 이미지화: 공급자 종속이 작고 **쪽별 격리·재시도가 쉽다.** 대신 PDF 파서·
  브라우저 메모리·OCR 화질 책임이 우리에게 온다.
- 기존 `prepImageForAI`(1568px·JPEG)를 쪽별 출발점으로 쓸 수는 있으나 **작은 수식·본문이
  읽히는지 대표 PDF 로 다시 재야 한다.**
- ⚠️ **상한을 그대로 쓸 수 없다** — `MAX_UPLOAD_BYTES` 5MB 는 Storage 용이고 AI 원본은
  20MB, Worker JSON 전체는 8MiB 다. ✅ **클로드 확인** — `AI_MAX_INPUT_BYTES` 가 실제로 있다.
- ⚠️ `normSet` 의 500문항은 **응답·가져오기 방어선**이지 PDF 입력·렌더 메모리 경계가 아니다.

새로 정해야 하는 값: 파일 수 · PDF 바이트 · 쪽 수 · 페이지 픽셀 · 동시 렌더 수 ·
배치 총바이트 · 최대 산출 문항 수.

### 4. C 에서 갈라짐 방지 — **반대. 클로드의 전제가 틀렸다**

"새 경로가 `aiBlocksToProblem`·`normProblem` 을 지나면 충분한가" 라는 질문 자체가 성립하지
않는다. **`aiBlocksToProblem` 은 네 계열 블록만 보존하고**(`statement·boxed` /
`conditions·examples` / `choices`) 나머지를 버린다 — `span`·`groupSpan`·`groupLead`·`answer`·
그림·지문이 전부 사라진다. 반면 `normProblem` 은 그 배치 필드를 **받을 수 있다.**
즉 B 의 계약을 기존 어댑터에 억지로 태우면 **정규화 전에 정보가 유실된다.**

✅ **클로드 확인** — 코드를 읽었다. 사실이다. 그 어댑터는 사진 경로용으로 **일부러 손실적**이다.

코덱스의 처방:
- A·B 가 사본을 갖지 말고 **하나의 raw-AI → canonical-problem 어댑터**를 함께 부른다.
- 같은 `problems[]` fixture 를 두 진입점에 넣어 **ID 를 뺀 결과·순서·개수·배치**가 같은지 대조.
- 지금 실패 주입은 어댑터 **안의** `normProblem` 우회만 잡는다(`check-ai-image.mjs`) —
  **B 진입점 우회·필드 누락 변이**도 빨간불이 나야 한다.

## 11. 해리의 결정 (2026-09-20) — 갈래는 C, 그리고 **문제를 다시 잡았다**

### 11-1. ⚠️ 이것은 '추출' 문제가 아니라 '재배열' 문제다

해리가 원하는 것을 그대로 옮기면 이렇다 — **"문제모음집 1·2·3 을 넣고, 단원별로 분류해
문제집 여러 개로 / 난이도별로 셋으로 / 행렬 문제만 뽑아 순서대로."**

세 예시는 **입력이 같고 배열만 다르다.** 그러면 작업이 셋으로 갈라진다:

| 단계 | 하는 일 | AI | 원가 | 횟수 |
|---|---|---|---|---|
| 1. 추출 | PDF → 문항 N개 | 비전 필요 | 비쌈 | **파일당 한 번** |
| 2. 꼬리표 | 문항마다 단원·난이도·유형 | 글자만 | 쌈 | **문항당 한 번** |
| 3. 재배열 | 거르기·나누기·정렬 | **불필요** | **0원** | **무한** |

⚠️ **해리가 든 세 예시는 전부 3단계다.** 매번 AI 에게 물으면 배열을 바꿀 때마다 과금되지만,
1·2 를 한 번만 하고 3 을 **필터 UI** 로 만들면 재배열은 영구히 공짜다.

이것이 §2 의 비용 충돌을 상당 부분 해소한다 — 묶어 받기의 목적이 '호출당 문항 수를 늘리는
것' 만이 아니라 **'AI 를 다시 부르지 않아도 되게 만드는 것'** 이 된다.

⚠️ **자연어 → 배치 열거값 계약(§5-4)의 범위도 줄어든다.** 흔한 요구는 AI 가 꼬리표만 달고
**UI 가 배열**하면 된다. 자연어를 `paired`·`page`·`col` 로 내리는 위험한 매핑은 그 다음 문제다.

## 13. 형식이 무너진 진짜 이유 — **구조를 강제한 적이 없었다** (2026-09-20)

해리가 §12 의 출력을 보고 "형식이 거지꼴" 이라고 했다. 맞다. 원인을 찾았다.

⚠️ **`worker/gemini.js` 는 `responseMimeType: "application/json"` 만 보내고 `responseSchema`
를 보내지 않는다.** 즉 우리는 "JSON 으로 줘" 라고만 하고 **어떤 구조인지 못박은 적이 없다.**
모델이 매 호출 구조를 새로 지어냈고, 그래서 갈래가 밀리고 §12-4 처럼 회차마다 흔들렸다.

### 13-1. 세 장치를 켜고 다시 쟀다 (호출 2회)

① `responseSchema`(구조 강제) ② 빈 칸 다섯을 스키마 필드로 ③ **갈래를 무엇으로 가르는지**
명시("테두리 상자 안 (가)(나) = conditions, ㄱㄴㄷ = examples, 테두리 없는 흐름 = statement").

| | 스키마 없음(§12) | **스키마 강제** |
|---|---|---|
| 블록 갈래 | 4개 중 **2개 밀림** | **4/4 정확** |
| 정답 | **아예 없음** | **`"2"`·`"③"`·`"①"` 정확** |
| 묶음 안내 | statement 에 뭉침 | **`groupLead` 제자리** |
| 각주 | `boxed` 로 오분류 | **`notes` 제자리, `*` 제거까지** |
| 출처 | 누락 | 읽음(⚠️ `source` 가 아니라 `text` 에 넣는다 — 아직 틀림) |
| 선지 | `"0"` | **`"$0$"`** |
| 별행 수식 | `$` 하나 | **`$$` 정확** |
| **입력 토큰** | 1,516 | **1,504 — 오히려 줄었다** |

⚠️ **더 정확해졌는데 더 싸다.** 스키마가 모델이 헤매는 것을 줄였기 때문으로 보인다.
형식 문제를 돈으로 사지 않아도 된다는 뜻이다.

⚠️ 아직 남은 것 둘 — **`passage` 를 안 고른다**(지문을 `statement` 여럿으로 쪼갠다) ·
**`source` 자리를 안 쓴다.** 프롬프트로 더 좁힐 여지가 있고, 아직 시도하지 않았다.
⚠️ 새로 생긴 미세 오류 하나 — 한 줄 안의 인라인 수식을 `$$` 로 쓴 회차가 있다.

### 13-2. "API 를 학습시킬 수 없나" — **이 경로로는 불가능하다. 그리고 해서도 안 된다**

해리의 질문이다. 사실부터 확인했다 — `models.list` 로 **58개 모델 전부**를 훑었다:

```
파인튜닝(createTunedModel) 가능: 0개
gemini-3.1-flash-lite → generateContent · countTokens · createCachedContent · batchGenerateContent
```

**이 API 키로 파인튜닝할 수 있는 모델은 하나도 없다.** 하려면 Vertex AI 라는 다른 제품으로
가야 한다(훨씬 무겁고, Gemini 3 계열 지원 여부는 따로 확인해야 한다).

⚠️ **되더라도 하지 말아야 할 이유가 셋 있고, 첫째가 결정적이다.**

1. **저작권.** 수학 유형·배치를 가르치려면 **교재 문항 수백~수천 건**이 학습 데이터로 필요하다.
   그것은 "사용자가 가진 자료를 옮겨 적는 것" 이 아니라 **남의 저작물을 모델에 굽는 것**이고,
   §11-4 의 1번("원본을 보관하지 않는다")을 정면으로 어긴다. 변환은 사용자의 행위지만
   **학습은 우리의 행위**라 책임이 이쪽으로 온다. ⚠️ **이 한 가지만으로 배제된다.**
2. **공급자에 묶인다.** 해리는 "중국 쪽이 더 싸고 괜찮으면 갈아타고 싶다" 고 했다.
   튜닝한 모델은 **옮길 수 없다.**
3. **모델이 바뀌면 다시 해야 한다.** `gemini-3.1-flash-lite` 도 언젠가 대체된다.

### 13-3. 대신 쓸 것 — 그리고 **우리는 이미 교재를 갖고 있다**

| 장치 | 상태 | 값 |
|---|---|---|
| `responseSchema` | **안 쓰고 있었다** | 13-1 에서 검증. 정확도 ↑, 비용 ↓ |
| **예시로 가르치기(few-shot)** | 안 써 봤다 | ⚠️ `test-fixtures/` 에 **인쇄 렌더 9장 + 그것을 만든 정답 JSON 9개가 쌍으로** 있다. **우리가 만든 것이라 저작권 문제가 없다.** 파인튜닝이 하려던 일을 프롬프트로 하는 것이다 |
| `createCachedContent` | 지원됨(미사용) | 예시를 길게 넣어도 반복분이 싸진다 |
| `batchGenerateContent` | 지원됨(미사용) | **묶음 경로에 직결** — 여러 쪽을 한꺼번에 |

▶ **순서는 이것이다**: 스키마 → 예시 → 캐싱 → 배치. **파인튜닝은 마지막이 아니라 목록에 없다.**
