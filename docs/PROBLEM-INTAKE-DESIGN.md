# 문제를 어떻게 받아들일 것인가 — 투입 경로 설계

작성: 2026-09-19 · 작성자: `Claude` · 상태: **설계 제안 · 구현 0줄**
논의 상대: `Codex` — 이 문서는 **결정을 내리기 위한 것이 아니라 결정할 것을 분명히 하려고** 쓴다.

2026-09-20: 검토 순서·모델 배정은 [통합 레일 R2](DEV-TOKEN-ROADMAP.md)에 편입했다.
제품 갈래·입력 상한·요금 단위는 미확정이며 이 문서의 구현 보류는 유지한다.

⚠️ **아무것도 구현하지 않았다.** 사용자의 지시가 "새로 만들지 말고 문제를 남겨 두라" 였다.

## 왜 이 문서가 있나

사용자(해리)의 말 그대로 옮긴다:

> 우리 프로그램 구조 상 **한 문제에 사진 넣고 그 문제가 변환되도록** 하게 되어 있잖아.
> 근데 이게 **너무 비효율적인 것 같애**. 여러 pdf 때려넣고 "이렇게 문제 배치해서 이렇게
> 만들어줘" 하면 그걸로 json 만들어서 하면 훨 편할텐데 지금 포멧으로는 그게 안 되잖아.
> … 즉, **프로그램의 정체성**을 제대로 찾아야 된다고나 할까.

이건 결함 보고가 아니라 **제품이 무엇인가에 대한 질문**이다. 그래서 `issues/` 가 아니라
`docs/` 에 둔다(`reviews/README.md` — "새 설계를 내놓을 때만 새 파일을 만든다").

## 1. 지금 실제로 되는 것과 안 되는 것 — 코드로 확인했다

추측이 아니라 읽어서 적는다.

| | 지금 | 근거 |
|---|---|---|
| 한 번에 넣는 파일 | **하나** | `index.html` 파일 선택 `files[0]` · 드래그앤드롭도 `find(f=>f.type.startsWith("image/"))` 로 **첫 이미지 하나** |
| 받는 형식 | **이미지만** | `worker/index.js` 화이트리스트 `image/jpeg·png·webp·gif` — **PDF 없음** |
| 사용자 지시 | **없음** | 이미지 경로는 고정 문구 하나만 보낸다("이 이미지의 문제를 지정된 JSON 구조로 변환해 줘"). 사용자가 "이렇게 배치해" 라고 말할 채널이 없다 |
| 한 장에 여러 문항 | **된다** | 시스템 프롬프트가 "한 개(또는 여러 개)" 이고, 응답이 `problems[]`, 클라이언트가 `set.problems.push(...newQs)` 로 전부 넣는다 |
| 결과 배치 | **현재 문제집 끝에 덧붙임** | 같은 곳. 분류·순서·쪽 배치를 정할 수 없다 |

⚠️ **'한 문제에 사진 한 장' 은 계약이 아니라 UI 다.** 조판기도 AI 계약도 여러 문항을
이미 감당한다. 막힌 것은 넷뿐이다 — **① 여러 파일 ② PDF ③ 지시 ④ 배치.**

한편 **문서 경로**(`mode:"document"`)는 사용자 지시를 받는다. 다만 산출물이 **문서 블록
13종**이지 문제집이 아니다(`docs/AI-DOCUMENT-SCOPE.md` 에서 화면 입구까지 뺐다).
즉 "지시를 받아 구조를 만든다" 는 경험은 이미 저장소 안에 있고, **문제집 쪽에만 없다.**

## 2. 비용이 이 설계에 개입한다 (2026-09-19 측정)

- Claude Haiku 4.5 = 입력 $1 / 출력 $5 per 1M. **호출 1회 ≈ 10원**(입력의 대부분이 이미지).
- **한 장에 문항이 여럿이면 문항당 원가가 나뉜다.** 지금 구조(한 장 = 보통 한 문항)가
  **원가 면에서도 가장 비싼 방식**이다. 묶어 받는 것은 편의만이 아니라 비용 문제다.
- ⚠️ 그런데 반대 방향의 위험이 있다 — **PDF 한 권은 호출 한 번이 수만 토큰**이다.
  지금 한도는 **호출 수**로 센다(`DailyQuota` · `DAILY_LIMIT=50`/사용자/일).
  **묶어 받기 시작하면 '호출 1회' 의 원가가 10원에서 수백~수천원으로 벌어져 한도 모델이
  무너진다.** 이것이 이 설계의 가장 큰 충돌점이다.

## 3. 지금 구조가 거는 물리적 제약

| 제약 | 값 | 어디 |
|---|---|---|
| Worker 요청 본문 | 8MiB | `worker/index.js` `MAX_BODY_BYTES` |
| 로컬 서버 본문 | 4MiB | `serve.py` `MAX_BODY` |
| 이미지 업로드(Storage) | 5MB | `index.html` `MAX_UPLOAD_BYTES`(= `storage.rules`) |
| **AI 로 보내는 원본** | **20MB** | `index.html` `AI_MAX_INPUT_BYTES` ⚠️ 위 5MB 와 **다른 값**이다(코덱스가 지적) |
| 가져오기 문항 수 | 500 | `normSet` 기본 `maxProblems`(신뢰 경계) |
| 사용자 한도 | 50회/일 | `wrangler.toml` |

PDF 여러 개는 이 숫자들과 **정면으로 부딪힌다.** 교재 한 권이 수십 MB다.

## 4. 갈래 — 이 제품은 무엇인가

**A. 옮겨 적기 도구 (지금)**
사진을 찍으면 문항이 된다. 배치·분류는 사람이 한다.
· 장점: 원가 예측 가능, 검토 단위가 작다, 신뢰 경계가 단순하다.
· 단점: 자료가 많을수록 사람이 하는 일이 선형으로 늘어난다. 사용자가 느낀 불편이 이것.

**B. 자료 → 문제집 변환기**
PDF 여러 개 + "이렇게 배치해" → 문제집 한 벌.
· 장점: 사용자가 원하는 것. 문항당 원가가 내려간다.
· 단점: 원가·한도 모델을 다시 짜야 한다. **검토 경험이 제품의 핵심 문제가 된다**(200문항이
  한꺼번에 들어오면 무엇을 믿고 쓰나). 부분 실패 처리가 생긴다.

**C. 둘 다 — A 를 남기고 B 를 새 경로로**
· 장점: 지금 동작을 깨지 않는다. 이 저장소가 모의고사·AI 문서에서 이미 쓴 방식이다.
· 단점: 경로가 늘면 갈라진다(이 저장소가 세 번 겪은 실패 방식 3번).

## 5. B 로 갈 때 실제로 걸리는 것들

설계가 답해야 할 것이지, 지금 답이 있는 것이 아니다.

1. **입력 경로** — 본문에 base64 로 실어 보내는 지금 방식은 8MiB 에서 끝난다.
   Files API·청크·브라우저에서 쪽 단위로 쪼개기 중 무엇인가.
2. **PDF 를 누가 읽나** — 공급자에게 그대로 넘기나(Anthropic 은 document 블록으로 PDF 를
   받는다), 브라우저에서 쪽 이미지로 바꿔 보내나. 후자는 지금 이미지 경로를 재사용한다.
3. **한도 모델** — 호출 수 → 토큰/쪽 수로 바꿔야 하나. 바꾸면 `DailyQuota`·`PLAN_DAILY_LIMITS_JSON`
   ·출시 게이트가 함께 움직인다. ⚠️ `check:launch` 의 "유료 플랜별 AI 상한 설정이 없습니다"
   가 이미 열려 있는 항목이다.
4. **"이렇게 배치해" 를 무엇으로 내리나** — 우리 데이터 모델의 열거값이다:
   `paired`·`page`·`col`·`groupSpan`·과목·블록 종류. 자연어를 그 값으로 내리는 계약이 필요하고,
   **신뢰 경계(`normSet`/`normProblem`)를 반드시 지나야 한다.**
5. **검토 경험** — 한 번에 200문항이 들어오면 사용자는 무엇을 보나. 미리보기 후 채택?
   문항별 신뢰도 표시? **이게 B 의 성패를 가른다**(옮겨 적기가 틀리면 사용자가 바로 보지만,
   200개는 안 본다).
6. **부분 실패** — PDF 5개 중 3개만 성공하면 무엇을 저장하나. 재시도는 과금된다.
7. **저작권** ⚠️ — 시중 교재·문제집 PDF 를 통째로 변환하는 기능은 **제품 위험**이다.
   이 저장소는 이미 저작물에 민감하게 굴어 왔다(실물 자료를 `.gitignore`, 규격서 출처 고지).
   "사용자가 가진 자료를 옮겨 적는 것" 과 "남의 문제집을 기계로 복제하는 것" 의 경계를
   **기능을 만들기 전에** 정해야 한다.

## 6. 해리가 정해야 하는 것

코드로 답할 수 없는 것들이다.

1. **제품의 중심** — A / B / C 중 무엇인가.
2. **한 번에 받는 최대** — 파일 몇 개, 쪽 몇 장까지.
3. **검토 방식** — 다 받아 놓고 고치기 vs 미리 보고 채택하기.
4. **요금·한도의 단위** — 호출 수 vs 쪽 수·토큰.
5. **저작권 선** — 어떤 자료의 변환을 허용한다고 말할 것인가.

## 7. 코덱스에게 묻는 것

- 위 5번(검토 경험)이 B 의 진짜 병목이라는 판단에 동의하는가. 다른 병목이 있나.
- 한도를 토큰 기준으로 바꾸는 것과 호출 수를 유지하고 **입력 크기를 제한**하는 것
  (예: 한 번에 쪽 20장) 중 어느 쪽이 이 저장소의 구조에 덜 침습적인가.
- PDF 를 공급자에게 넘기는 것과 브라우저에서 쪽 이미지로 바꾸는 것의 득실.
  후자는 기존 이미지 경로·상한·신뢰 경계를 그대로 쓴다는 이점이 있다.
- C(둘 다)로 갈 때 "베낀 것은 갈라진다" 를 어떻게 막을 것인가 — 새 경로가 기존
  `aiBlocksToProblem`·`normProblem` 을 그대로 지나게 하는 것으로 충분한가.

## 8. 하지 않은 것

- **코드 0줄.** 설계·측정·기록뿐이다.
- 어떤 갈래가 맞는지 **고르지 않았다.** 그건 해리와 코덱스의 논의 결과다.
- 최초 작성 당시 비용 레일과 별도였으며, 2026-09-20 통합 레일 R2와 C3/R9의
  입력·비용·상품 계약에 연결했다. 기능 구현은 아직 시작하지 않았다.

## 9. 코덱스의 답 (2026-09-20) — 클로드가 독립 확인한 것까지

`codex exec --sandbox read-only` 로 §7 의 넷을 물었다(파일 쓰기 없음 · 토큰 67,658).
아래는 코덱스의 답을 옮기고, **클로드가 코드로 확인한 결과**를 함께 적은 것이다.

⚠️ 코덱스가 **이 문서의 오류 둘을 잡았다.** 그 둘은 위 본문에서 이미 고쳤다.

### 1. 검토 경험이 진짜 병목인가 — **부분 동의**

대량 변환의 성패가 "전수 검토 없이 오류를 찾고 **선택적으로 채택**할 수 있는가" 에 달려
있다는 데는 동의하되, **그보다 앞선 출시 차단선은 작업당 비용 상한과 실패 격리**라고 했다.

근거: 지금 Worker 는 **외부 호출 전에 사용량을 1회 확정**하고 **실패도 차감**한다.
✅ **클로드 확인** — 2026-09-18 에 실제로 겪었다. 두 호출 모두 502 로 실패했는데 그날 한도
2/2 가 소진됐다(`reserve`·`consume` 이 provider 응답 전에 끝난다).

그래서 수백 문항 작업에는 **검토 UI 보다 먼저** 쪽별 분할·취소·부분 성공·재시도 중복 방지
계약이 필요하다. 그다음 병목이 추출 품질이다(문항 수·순서·묶음이 틀리면 신뢰도 표시로는
검토량이 안 준다). 권장 경험은 전수 확인이 아니라 **쪽별 미리보기 → 저신뢰 구간 표시 →
구간별 채택**.

### 2. 한도의 단위 — **동의: (나) 호출 수 유지 + 입력 상한**

`PLAN_DAILY_LIMITS_JSON` 이 플랜별 **정수 호출 수**이고 `DailyQuota` 도 예약 하나를
`used += 1` 로 확정한다. 토큰/쪽 가중치로 바꾸면 예약 수량·pending 합계·상태 형식·개인/전역
DO·응답 문구·계약 검사를 **전부** 바꿔야 한다.

⚠️ 더 결정적인 것: **실제 토큰은 호출 뒤에 나오는데 지금 방어는 호출 전 consume** 이라,
토큰제로 가면 **최대치 선예약 + 사후 정산** 계약까지 새로 만들어야 한다. 반면 쪽·파일·크기
상한은 본문 검증처럼 **quota 차감 전에 거절**할 수 있다.

단서: "20쪽 1호출" 이 8MiB 본문 상한 안에 들어가는지는 **따로 재야 한다.**

### 3. PDF 를 누가 읽나 — **부분 동의**

⚠️ **R2 의 "기존 경로 재사용" 을 클로드가 과하게 읽었다.** 그것은 **출력 계약·정규화·반영
경로**를 재사용한다는 뜻이지, PDF 를 반드시 브라우저에서 이미지화한다는 결정이 아니다.

- (나) 브라우저 쪽 이미지화: 공급자 종속이 작고 **쪽별 격리·재시도가 쉽다.** 대신 PDF 파서·
  브라우저 메모리·OCR 화질 책임이 우리에게 온다.
- 기존 `prepImageForAI`(1568px·JPEG)를 쪽별 출발점으로 쓸 수는 있으나 **작은 수식·본문이
  읽히는지 대표 PDF 로 다시 재야 한다.**
- ⚠️ **상한을 그대로 쓸 수 없다** — `MAX_UPLOAD_BYTES` 5MB 는 Storage 용이고 AI 원본은
  20MB, Worker JSON 전체는 8MiB 다. ✅ **클로드 확인** — `AI_MAX_INPUT_BYTES` 가 실제로 있다.
- ⚠️ `normSet` 의 500문항은 **응답·가져오기 방어선**이지 PDF 입력·렌더 메모리 경계가 아니다.

새로 정해야 하는 값: 파일 수 · PDF 바이트 · 쪽 수 · 페이지 픽셀 · 동시 렌더 수 ·
배치 총바이트 · 최대 산출 문항 수.

### 4. C 에서 갈라짐 방지 — **반대. 클로드의 전제가 틀렸다**

"새 경로가 `aiBlocksToProblem`·`normProblem` 을 지나면 충분한가" 라는 질문 자체가 성립하지
않는다. **`aiBlocksToProblem` 은 네 계열 블록만 보존하고**(`statement·boxed` /
`conditions·examples` / `choices`) 나머지를 버린다 — `span`·`groupSpan`·`groupLead`·`answer`·
그림·지문이 전부 사라진다. 반면 `normProblem` 은 그 배치 필드를 **받을 수 있다.**
즉 B 의 계약을 기존 어댑터에 억지로 태우면 **정규화 전에 정보가 유실된다.**

✅ **클로드 확인** — 코드를 읽었다. 사실이다. 그 어댑터는 사진 경로용으로 **일부러 손실적**이다.

코덱스의 처방:
- A·B 가 사본을 갖지 말고 **하나의 raw-AI → canonical-problem 어댑터**를 함께 부른다.
- 같은 `problems[]` fixture 를 두 진입점에 넣어 **ID 를 뺀 결과·순서·개수·배치**가 같은지 대조.
- 지금 실패 주입은 어댑터 **안의** `normProblem` 우회만 잡는다(`check-ai-image.mjs`) —
  **B 진입점 우회·필드 누락 변이**도 빨간불이 나야 한다.

## 11. 해리의 결정 (2026-09-20) — 갈래는 C, 그리고 **문제를 다시 잡았다**

§6·§10 에 해리가 답했다. 그 과정에서 **이 문서가 문제를 한 겹 잘못 잡고 있었던 것**이
드러났다. 아래 11-1 이 그것이다.

### 11-1. ⚠️ 이것은 '추출' 문제가 아니라 '재배열' 문제다

해리가 원하는 것을 그대로 옮기면 이렇다 — **"문제모음집 1·2·3 을 넣고, 단원별로 분류해
문제집 여러 개로 / 난이도별로 셋으로 / 행렬 문제만 뽑아 순서대로."**

세 예시는 **입력이 같고 배열만 다르다.** 그러면 작업이 셋으로 갈라진다:

| 단계 | 하는 일 | AI | 원가 | 횟수 |
|---|---|---|---|---|
| 1. 추출 | PDF → 문항 N개 | 비전 필요 | 비쌈 | **파일당 한 번** |
| 2. 꼬리표 | 문항마다 단원·난이도·유형 | 글자만 | 쌈 | **문항당 한 번** |
| 3. 재배열 | 거르기·나누기·정렬 | **불필요** | **0원** | **무한** |

⚠️ **해리가 든 세 예시는 전부 3단계다.** 매번 AI 에게 물으면 배열을 바꿀 때마다 과금되지만,
1·2 를 한 번만 하고 3 을 **필터 UI** 로 만들면 재배열은 영구히 공짜다.

이것이 §2 의 비용 충돌을 상당 부분 해소한다 — 묶어 받기의 목적이 '호출당 문항 수를 늘리는
것' 만이 아니라 **'AI 를 다시 부르지 않아도 되게 만드는 것'** 이 된다.

⚠️ **자연어 → 배치 열거값 계약(§5-4)의 범위도 줄어든다.** 흔한 요구는 AI 가 꼬리표만 달고
**UI 가 배열**하면 된다. 자연어를 `paired`·`page`·`col` 로 내리는 위험한 매핑은 그 다음 문제다.

### 11-2. 그런데 지금 문항에는 꼬리표를 담을 자리가 없다

```
newProblem() = { id, title, desc, answer, answerImg, numLabel, paired, blocks }
```
(`index.html:2794` — 단원·난이도·유형 필드가 **없다.** `set.subject`(과목)는 문제집 단위다)

⚠️ 이 필드를 더하는 것이 B 의 **첫 공사**이고, 신뢰 경계(`normProblem`)가 모르는 필드를
버리므로 거기도 함께 고쳐야 한다(`pedagogy-normalize.js:273`).

⚠️ **여기서 내가 `firestore.rules` 의 `hasOnly` 도 함께 고쳐야 한다고 적었는데 틀렸다**
(코덱스 지적 · 코드로 확인). `hasOnly` 는 **문제집 문서의 최상위 키만** 본다 —
`['id','name','header','problems','order','deleted','updatedAt','lineColor','subject','folderId']`
(`firestore.rules:54`). **`problems[]` 안쪽 문항 키는 검사하지 않는다.** 꼬리표를 문항 객체
안에 넣으면 **Rules 를 건드리지 않고 저장된다.** 최상위에 태그 사전·인덱스를 새로 두거나
Rules 가 문항 내부를 검증하게 될 때만 함께 바뀐다.

⚠️ 대신 **코덱스가 진짜 파급을 짚었다** — 꼬리표가 문항마다 붙으면 문제집 **단일 문서가
1MiB 한도에 더 빨리 닿는다.** 모의고사에는 900KiB 선제 방어가 있는데 **문제집에는 없다.**
그래서 이것은 Rules 문제가 아니라 **R3(저장 계약) 문제**다.

### 11-4. 저작권 — 해리가 클로드에게 위임했다("책임 전가가 안 되게 선을 지켜라")

⚠️ **무료 한도로 되는지는 끝내 확인하지 못했다**(결제 뒤 첫 호출이 성공했다).

## 13. 형식이 무너진 진짜 이유 — **구조를 강제한 적이 없었다** (2026-09-20)

해리가 §12 의 출력을 보고 "형식이 거지꼴" 이라고 했다. 맞다. 원인을 찾았다.

⚠️ **`worker/gemini.js` 는 `responseMimeType: "application/json"` 만 보내고 `responseSchema`
를 보내지 않는다.** 즉 우리는 "JSON 으로 줘" 라고만 하고 **어떤 구조인지 못박은 적이 없다.**
모델이 매 호출 구조를 새로 지어냈고, 그래서 갈래가 밀리고 §12-4 처럼 회차마다 흔들렸다.

### 13-1. 세 장치를 켜고 다시 쟀다 (호출 2회)

① `responseSchema`(구조 강제) ② 빈 칸 다섯을 스키마 필드로 ③ **갈래를 무엇으로 가르는지**
명시("테두리 상자 안 (가)(나) = conditions, ㄱㄴㄷ = examples, 테두리 없는 흐름 = statement").

| | 스키마 없음(§12) | **스키마 강제** |
|---|---|---|
| 블록 갈래 | 4개 중 **2개 밀림** | **4/4 정확** |
| 정답 | **아예 없음** | **`"2"`·`"③"`·`"①"` 정확** |
| 묶음 안내 | statement 에 뭉침 | **`groupLead` 제자리** |
| 각주 | `boxed` 로 오분류 | **`notes` 제자리, `*` 제거까지** |
| 출처 | 누락 | 읽음(⚠️ `source` 가 아니라 `text` 에 넣는다 — 아직 틀림) |
| 선지 | `"0"` | **`"$0$"`** |
| 별행 수식 | `$` 하나 | **`$$` 정확** |
| **입력 토큰** | 1,516 | **1,504 — 오히려 줄었다** |

⚠️ **"더 싸다" 는 내가 틀렸다**(코덱스 지적 · 재측정으로 확인). **입력 토큰은 생성 전에
결정되므로** '모델이 덜 헤매서 입력이 줄었다' 는 성립할 수 없다. 실제 원인은 **내가 프롬프트를
더 짧게 썼기 때문**이다 — 제품 프롬프트 893자·409토큰 vs 실험 프롬프트 738자·402토큰(**−7**),
사용자 문구도 줄였다. 1,516 → 1,504 의 **12 토큰은 그것으로 전부 설명된다.**
▶ 정확히 말할 수 있는 것은 **"추가 비용 신호가 보이지 않았다"** 까지다. 비용 절감이 아니다.
▶ 그리고 **정확도 향상도 스키마 단독 효과가 아니다** — 한 번에 셋을 바꿨다(스키마 · 빈 칸
다섯 · 갈래 판별 설명). 무엇이 얼마나 기여했는지 **분리하지 않았다.** 호출도 2회뿐이다.

⚠️ 아직 남은 것 둘 — **`passage` 를 안 고른다**(지문을 `statement` 여럿으로 쪼갠다) ·
**`source` 자리를 안 쓴다.** 프롬프트로 더 좁힐 여지가 있고, 아직 시도하지 않았다.
⚠️ 새로 생긴 미세 오류 하나 — 한 줄 안의 인라인 수식을 `$$` 로 쓴 회차가 있다.

### 13-2. "API 를 학습시킬 수 없나" — **이 경로로는 불가능하다. 그리고 해서도 안 된다**

해리의 질문이다. 사실부터 확인했다 — `models.list` 로 **58개 모델 전부**를 훑었다:

```
파인튜닝(createTunedModel) 가능: 0개
gemini-3.1-flash-lite → generateContent · countTokens · createCachedContent · batchGenerateContent
```

**이 API 키로 파인튜닝할 수 있는 모델은 하나도 없다.** 하려면 Vertex AI 라는 다른 제품으로
가야 한다(훨씬 무겁고, Gemini 3 계열 지원 여부는 따로 확인해야 한다).

⚠️ **되더라도 하지 않는다. 이유 셋 — 결정적인 것은 3번이다.**

1. **저작권.** ⚠️ **처음에 이 항목을 "이것 하나로 배제된다" 고 적었는데 과했다 — 해리가
   지적해 고친다.** 평가원 기출을 활용한 교재는 실제로 널리 유통되고, 평가원이 교육 목적
   이용을 관대하게 허용해 왔다. **실질 위험이 낮다는 해리의 판단이 현실과 맞다.**
   정확히 하면 — 기출에 저작권이 **없는 것은 아니다**(저작권법 제7조의 법령·고시·판결에
   해당하지 않는다). 그리고 진짜 갈리는 곳은 문제가 아니라 **그 안에 인용된 제3자 저작물**
   (국어 지문의 소설·평론, 영어 지문의 원문)과 **시중 N제·사설 문제집**이다.
   다만 학습은 변환과 달리 **우리의 행위**라 책임의 자리가 다르다는 점만 적어 둔다.
   ▶ **해리의 결정(2026-09-20): 저작권은 진행을 막지 않는다.** §11-4 의 구조적 선
   (원본 미보관 · 계정 밖 유출 없음 · 자료 미공급)을 지키는 것으로 충분하다고 보았고,
   그 선은 기출이든 사설이든 관계없이 유효하며 **재배열 기능을 아무것도 막지 않는다.**
2. **공급자에 묶인다.** 해리는 "중국 쪽이 더 싸고 괜찮으면 갈아타고 싶다" 고 했다.
   튜닝한 모델은 **옮길 수 없다.**
3. ⚠️ **순서가 틀렸다 — 이것이 결정적이다.** `responseSchema` 하나를 켰더니 갈래가
   **2/4 → 4/4** 로 올랐고 **비용은 오히려 줄었다**(13-1). few-shot 은 **아직 써 보지도
   않았다.** 파인튜닝은 이것들이 **실패했을 때** 가는 곳이지 먼저 가는 곳이 아니다.
   덧붙여 `gemini-3.1-flash-lite` 도 언젠가 대체되므로 재학습 비용이 따라온다.

### 13-3. 대신 쓸 것 — 그리고 **우리는 이미 교재를 갖고 있다**

| 장치 | 상태 | 값 |
|---|---|---|
| `responseSchema` | **안 쓰고 있었다** | 13-1 에서 검증. 정확도 ↑, 비용 ↓ |
| **예시로 가르치기(few-shot)** | 안 써 봤다 | ⚠️ `test-fixtures/` 에 **인쇄 렌더 9장 + 그것을 만든 정답 JSON 9개가 쌍으로** 있다. **우리가 만든 것이라 저작권 문제가 없다.** 파인튜닝이 하려던 일을 프롬프트로 하는 것이다 |
| `createCachedContent` | 지원됨(미사용) | 예시를 길게 넣어도 반복분이 싸진다 |
| `batchGenerateContent` | 지원됨(미사용) | **묶음 경로에 직결** — 여러 쪽을 한꺼번에 |

▶ **순서는 이것이다**: 스키마 → 예시 → 캐싱 → 배치. **파인튜닝은 마지막이 아니라 목록에 없다.**

## 14. ⚠️ §12-5 의 내 주장은 틀렸다 — 이미지 토큰은 **장당 고정**이다 (2026-09-20)

§12-5 에 "이미지 토큰은 바이트가 아니라 **해상도**로 정해진다" 고 적었다. 근거가 **호출 3회에서
입력 토큰이 모두 1,516 이었던 것**뿐이었는데, 그 세 장은 **해상도가 전부 같았다.** 즉 나는
'바이트와 무관하다' 만 본 것을 '해상도에 비례한다' 로 넘겨 짚었다.

`countTokens`(**과금되지 않는다**)로 제대로 쟀다.

| 해상도 | 픽셀 | KB | 토큰 |
|---|---|---|---|
| 50×71 | 0.004 M | 1 | **1,093** |
| 201×284 | 0.06 M | 6 | **1,093** |
| 794×1123 | 0.89 M | 26 | **1,093** |
| 1813×2564 | 4.65 M | 153 | **1,093** |
| 3176×4492 | 14.3 M | 388 | **1,093** |
| 7253×10259 | **74.4 M** | 1,550 | **1,093** |

기준선 9장(해상도 동일·26~92KB)도 전부 1,093 이었다 — **바이트와 무관**이 먼저 확인됐다.
그리고 **실호출 2회**로 `countTokens` 가 실제 과금과 같은 것을 확인했다(201×284 와 3176×4492 가
**둘 다 promptTokenCount 1,109**). 즉 **`gemini-3.1-flash-lite` 는 이미지 한 장을 해상도·용량과
무관하게 약 1,093 토큰으로 과금한다.**

### 14-1. 무엇이 바뀌나

- ✅ **"한 장에 문항이 많을수록 문항당 원가가 내려간다" 는 그대로다. 오히려 더 강해졌다** —
  장당 비용이 **완전히 고정**이므로 한 장에 담는 문항 수가 원가를 통째로 가른다.
- ✅ **쪽 수가 곧 비용이다.** 쪽 수 상한(§6-2)을 정할 때 `쪽 수 × 약 1,093 토큰` 으로 **정확히**
  계산할 수 있다. 해상도·용량은 계산에 들어가지 않는다.
- ⚠️ **해상도를 낮춰도 비용이 줄지 않는다.** `prepImageForAI()` 의 1568px 축소는 제미나이 경로에서
  **비용 절감이 아니다** — 업로드 시간과 대역폭만 준다(그 값은 여전히 있다).
- ⚠️ **반대로 해상도를 올려도 공짜다.** 다만 **정확도가 오르는지는 모른다** — 토큰이 고정이라는
  것은 모델이 내부에서 **일정 크기로 줄여 본다**는 뜻일 수 있고, 그러면 고해상도는 낭비다.
  **재야 안다. 아직 재지 않았다.**

### 14-2. 이 실수에서 남길 것

⚠️ **한 변수만 바뀐 표본으로 다른 변수의 법칙을 말하지 말 것.** 세 장의 바이트 수가 달랐으므로
'바이트 무관' 은 정당했지만, **해상도는 셋이 같았으므로** 해상도에 대해서는 아무것도 잰 것이
아니었다. 통제하지 않은 변수는 결론에 넣지 않는다.
⚠️ **`countTokens` 는 과금되지 않는다.** 비용 관련 주장은 실호출 전에 이것으로 먼저 재라 —
이번 표 여섯 줄이 **0원**이었다.

## 15. 코덱스의 R2 검토 (2026-09-20) — **내 주장 셋이 반박됐다**

`codex exec --sandbox read-only` 로 넷을 물었다(파일 변경 0 · 138,763 토큰).
아래는 코덱스의 답이고, **클로드가 코드로 확인한 것**을 ✅ 로 표시했다.

⚠️ **§12-5 는 코덱스가 말하기 전에 내가 스스로 재어 틀린 것을 찾았다**(§14). 둘이 독립적으로
같은 결론에 닿았다 — 나는 측정으로, 코덱스는 코드를 읽고서.

### 15-1. R2 판정 — **부분 동의.** 큰 구분은 맞고 "배치" 를 좁혀야 한다

**출시 필수**
- 기존 A 경로 유지
- **여러 이미지 파일**을 한 작업으로 선택
- **파일별 추출 → 검토 → 부분 채택**
- 문항에 **단원·난이도·유형 꼬리표** 저장
- 꼬리표에 따른 **필터·분할·정렬**
- 파일별 **실패·재시도·중복 방지**와 작업 상한

**후속**
- **PDF 원본 직접 입력**
- 자유 서술 지시
- 자연어로 `paired`·`page`·`col` 같은 **조판값까지** 결정
- 제미나이 `batchGenerateContent` 도입

⚠️ **"배치" 는 Gemini Batch API 가 아니라 여러 파일을 안전하게 순차 처리하는 제품 작업**을
뜻해야 한다. 내가 두 뜻을 섞어 쓰고 있었다.

**"재배열을 AI 없이" 는 제한된 범위에서 성립한다.** 다만 계약 다섯이 먼저 필요하다:
1. **단원은 자유 문자열이 아니라 안정적인 ID 또는 통제된 분류체계**여야 한다.
2. **유형은 복수 선택**이 되는가.
3. **난이도는 모델의 주관적 판정**이므로 사용자가 고칠 수 있어야 한다.
4. **"원래 순서대로" 를 위해 출처 순서 필드**(파일 순서·쪽·쪽 안 순번)가 필요하다.
5. **필터 결과를 원본과 연결된 '보기' 로 둘지, 새 문제집으로 '복제' 할지.**
   ⚠️ 복제하면 **이후 수정이 갈라진다.**

### 15-2. ⚠️ `firestore.rules` 에 대한 내 주장이 틀렸다 — ✅ 확인

§11-2 에서 고쳤다. `hasOnly` 는 **최상위 키만** 본다. 진짜 파급은 Rules 가 아니라
**문제집 단일 문서의 1MiB 한도**이고, 그것은 **R3** 의 일이다(모의고사에는 900KiB 선제
방어가 있는데 문제집에는 없다). **R2 와 R3 는 충돌하지 않고 역할이 갈린다** —
R2 가 꼬리표의 의미·형식·재배열 동작을, R3 가 크기·충돌·복구·호환을 정한다.

### 15-3. C1 — **동의. 다만 secret 교체만으로 끝나지 않는다** — ✅ 확인

기술적으로 맞다. Worker 는 키가 어느 GCP 프로젝트에서 왔는지 **확인하지 않는다**
(`geminiApiKey()` 는 공백만 제거 · `providerConfig()` 는 키가 비었는지와 모델 이름만 본다 ·
호출은 `x-goog-api-key` 로 보낼 뿐이다). **Firebase 프로젝트가 `pedagogy-ai-staging` 이고
과금 프로젝트가 `pedagogy-huryul` 이어도 현재 코드상 문제없다.**

⚠️ **그러나 C1 완료 조건은 "키 교체" 가 아니라 "Worker 종단 성공" 이다.** 남는 것:
1. **새 승인**(대상·횟수·최대 비용·재시도 0회) — 기존 승인은 소진됐다.
2. Worker 를 통한 **문서 1회 + 이미지 1회**. ⚠️ **오늘 직접 호출한 것은 Worker 배선 검증이 아니다.**
3. `wrangler tail` 로 telemetry 확인(sampling 을 올릴 필요가 없어 **복원 작업도 안 생긴다**).
4. 임시 계정 정리 · 2026-09-14 익명 사용자 1개도 남아 있다.
5. **production 은 건드리지 않는다.**
6. 성공 증거를 `REV-2026-093` 에 기록해야 닫을 수 있다.

▶ **코덱스의 더 안전한 제안**: 탐침용 일반 키를 재사용하지 말고 **staging Worker 전용 키를
따로 발급해 Generative Language API 로 제한**한 뒤 secret 으로 넣는다. 검증 후 폐기·회전이 명확해진다.

### 15-4. `responseSchema` — **부분 동의.** ⚠️ 그대로 넣으면 **문서 경로가 깨진다**

⚠️ **이미지 경로와 문서 경로가 같은 `buildGeminiRequest()` 를 부른다**(`worker/index.js:878`·`:927`).
출력 계약이 전혀 다른데 스키마 하나를 박으면 문서가 망가진다. **task 별 스키마**가 필요하다.

⚠️ **문항 경로에는 검증이 거의 없다** — ✅ 확인. `problems` 가 **배열인지만** 본다
(`worker/index.js:916`). 문서 쪽에는 `validateDocumentResponse()` 가 있는데 문항 쪽에는 없다.
**`validateProblemsResponse()` 가 필요하다**(문항 수·필드 타입·길이·블록 수·선지 5개…).
▶ **`responseSchema` 는 공급자 기능이지 신뢰 경계의 대체물이 아니다.**

⚠️ **`aiBlocksToProblem` 이 버리는 것** — ✅ 확인(`pedagogy-ai-image.js:32`). `desc:""`,
`answer:""`, `numLabel:""`, `paired:false` 를 **하드코딩**하고 `groupLead`·`passage`·출처·각주는
읽지도 않는다. §12-3 에서 "우리 계약에 자리가 없다" 고 한 것이 **여기서도 한 번 더 막힌다.**

⚠️ **내 탐침 스키마가 계약과 어긋났다** — ✅ 확인. 탐침은 `notes: string[]` 인데
canonical 은 `notes: text(o.notes,1000)` 즉 **문자열**이다(`pedagogy-normalize.js:137`).

⚠️ **앤트로픽 전환 계약** — `responseSchema` 는 제미나이 기능이고 앤트로픽은 tool use 의
`input_schema` 로 해야 한다. **공통 `SYSTEM_PROMPT` 에서 JSON 구조 설명을 지우면 앤트로픽이
구조 지시를 통째로 잃는다.** production 이 아직 앤트로픽 기본값인 상태에서 그렇게 하면
**명백한 회귀**다.
▶ 코덱스 권장: **같은 canonical JSON Schema 를 제미나이 `responseSchema` 와 앤트로픽
`input_schema` 양쪽에 쓰고 envelope 해석만 공급자별로 가른다.**
▶ `AI_PROVIDER` 계약이 요구하는 것은 **기능의 동일성이 아니라 "같은 검증된 canonical 출력
또는 같은 실패"** 다.

### 15-6. 이 검토로 해리가 정할 것

§11-5 의 미정에 더해, **15-1 의 계약 다섯**이 새로 올라왔다. 그중 해리의 결정이 필요한 것:

1. **단원 분류체계를 무엇으로 하나** — 교육과정 단원명을 고정 목록으로 둘지, 사용자가 만들지.
2. **필터 결과를 '보기' 로 둘지 '복제' 로 둘지.** ⚠️ 복제하면 원본과 수정이 갈라진다.
3. **난이도를 모델이 매기게 할지, 사용자만 매기게 할지**(모델 판정은 흔들린다).

## 16. 해리의 결정 (2026-09-20 · §15-6 에 대한 답)

| 항목 | 결정 |
|---|---|
| **단원 분류체계** | ✅ **매번 사용자가 지정한다**(고정 목록을 두지 않는다) |
| **난이도** | ✅ **모델/사용자 중 고를 수 있게** 한다 |
| 필터 결과를 보기/복제 | ⬜ 질문의 뜻을 몰라 되물었다 — 16-2 에 설명을 남긴다 |

### 16-1. ⚠️ 단원을 자유 입력으로 두는 대가 — 완화책을 함께 둔다

코덱스는 §15-1 에서 **"단원은 자유 문자열이 아니라 안정적인 ID 또는 통제된 분류체계여야
한다"** 고 했다. 해리는 **자유 지정**을 택했다. 그 결정을 따르되 대가를 적어 둔다.

⚠️ **`이차함수` 와 `이차 함수` 가 서로 다른 단원이 된다.** 띄어쓰기·표기 차이 하나로 필터가
갈라져 "이차함수만 뽑기" 에서 절반이 빠진다. **모델이 매기면 회차마다 표기가 흔들리므로**
(§12-4 와 같은 성질) 이 위험은 실제로 크다.

▶ **완화책(해리 확인 대기)**: 자유 입력은 유지하고 **이미 쓴 단원 목록을 자동완성으로
제시**한다. 결정(매번 지정)은 그대로이고 갈라짐만 준다. 통제된 분류체계를 강제하지 않는다.
▶ 모델이 붙인 단원도 **사용자가 고칠 수 있어야 한다**(난이도와 같은 이유).

### 16-2. "필터 결과를 보기로 둘지 복제로 둘지" 가 무슨 뜻인가

`문제모음집 1·2·3` 을 넣고 "단원별로 나눠 줘" 해서 문제집 5개가 나왔을 때,
**그 5개가 무엇인가**에 두 답이 있다.

| | **A. 복제** | **B. 보기** |
|---|---|---|
| 정체 | 문항을 복사한 **진짜 문제집 5개** | 원본 하나 + **다섯 가지 보는 방법** |
| 지금 구조 | ✅ **그대로 된다** — 인쇄·한글 내보내기·편집·동기화가 전부 이미 있다 | ❌ **없는 개념이다.** 전부 "문제집 = Firestore 문서 하나" 를 전제로 짜여 있어 인쇄·내보내기·되돌리기·동기화를 전부 손봐야 한다 |
| 수정 | ❌ **갈라진다** — 오타를 고쳐도 그 사본만 고쳐진다 | ✅ 원본 하나만 고치면 전부 반영 |
| 저장 | ❌ 문항이 N배 — ⚠️ **문제집 1MiB 한도(R3)와 직결** | ✅ 안 늘어난다 |
| 해리의 표현과 | ✅ "문제집 여러 개로 만들고 싶다" 와 일치 | 다르다 |

▶ **클로드 추천: A(복제).** B 는 제품 구조를 통째로 바꾸는 일이다.
▶ **갈라짐 완화**: 복제할 때 **출처(어느 파일·몇 쪽·쪽 안 순번)를 문항에 함께 적는다.**
그러면 "원본 고쳐서 다시 뽑기" 가 가능하고, 코덱스도 §15-1 에서 **"원래 순서대로" 를 위해
그 필드가 필요하다**고 했으므로 **어차피 있어야 하는 것**이다.

## 17. ⚠️ 저해상도는 "못 읽겠다" 가 아니라 **딴 문제를 지어낸다** (2026-09-20)

§14 에서 **토큰이 해상도와 무관하다**는 것을 알고, "그러면 해상도를 낮춰 본문 8MiB 안에 더
많은 쪽을 넣으면 되지 않나" 를 확인하려고 쟀다. **안 된다.** 그리고 실패 방식이 나쁘다.

같은 문항(§12 의 `math-print`)을 가로 400 / 794 / 1588px 로 넣었다(스키마 강제 상태).

| | 실제 | **400px** |
|---|---|---|
| 본문 | `\frac{x^2-4}{x-2}=x+2` | 1회 `\frac{a_n}{n}=a+2` ❌ · 2회 `\frac{a_n}{n}=n+3` ❌ · 3회 ✅ |
| 상자 | `\int_0^1(x^2+1)dx=\frac43` | 1회 `\int_0^a(x^2+2)dx=\frac{28}{3}` ❌ · 2회 `\int_0^1(x^2+2)dx=\frac73` ❌ · 3회 `\int_0^x t^2-2t\,dt=\frac43` ❌ |
| 정답 | `2` | 1회 **누락** |

⚠️ **3회 모두, 매번 다르게 지어냈다.** "읽을 수 없다" 고 말하지 않는다.

⚠️ **그런데 쉬운 것은 세 번 다 맞았다** — 선지 `$0$~$4$` 와 조건 `a_n=2n-1`·`\sum a_k=n^2` 은
전부 정확했다. **복잡한 수식만 조용히 바뀐다.** 이것이 **가장 나쁜 실패 방식**이다 —
훑어보면 맞아 보이고, 틀린 곳이 하필 검산이 제일 어려운 곳이다.

794px 는 정확했다. 1588px 는 수식은 맞았으나 **`statement` 블록이 사라지고 발문에 섞였다** —
**해상도를 올린다고 좋아지지도 않는다.**

### 17-1. 무엇이 따라 나오나

1. **입력 품질 게이트가 필요하다.** 사용자가 찍은 흐릿하거나 작은 사진에서 같은 일이 난다.
   최소 해상도 기준을 두고 **미달이면 거절**해야 한다(⚠️ 경계값은 아직 재지 않았다 —
   400 은 안 되고 794 는 된다는 것만 안다).
2. **본문 8MiB 한계를 해상도 낮추기로 우회할 수 없다.** 쪽 수 상한이 실제로 빡빡하다.
3. ✅ **§10-1 의 "초안 생성" 결정이 한 번 더 굳었다.** 조용한 환각은 검토 없이 못 잡는다.
4. ⚠️ **검토 UI 설계가 어려워졌다.** "저신뢰 구간 표시"(§9-1 코덱스 권장)가 잘 안 통할 수 있다 —
   **모델이 자신 있게 틀린다.** 쉬운 부분이 맞아서 신뢰도 신호가 높게 나올 가능성이 있다.

### 17-2. 1회 최대 쪽 수 — ⚠️ **출력 상한이 먼저 걸린다**

§14 로 입력은 정확히 계산된다: **입력 = 프롬프트 약 410 + 쪽 수 × 1,093.**
출력은 관측상 **쪽당 약 400~660 토큰**(내용에 비례한다).

| 쪽 수 | 입력 토큰 | 출력 토큰(추정) | 원가(추정) | 본문 크기 |
|---|---|---|---|---|
| 5 | 5,875 | ~2,750 | 약 8원 | 약 0.6MB |
| 10 | 11,340 | ~5,500 | 약 16원 | 약 1.2MB |
| 20 | 22,270 | ~11,000 | 약 31원 | 약 2.4MB |

⚠️ **본문 8MiB 는 20쪽에서도 여유가 있다. 진짜 벽은 `maxOutputTokens: 4096` 이다**
(`worker/gemini.js:17`). 쪽당 약 550 토큰이면 **약 7쪽에서 출력이 잘린다.**
▶ **지금 설정 그대로면 1회 상한은 약 7쪽이다.** 더 받으려면 `maxOutputTokens` 를 올려야 하고,
그것은 레일의 **C3/R9** 항목이다(로드맵이 "4096 상한은 현재 값 유지" 로 묶어 두었다).
▶ ⚠️ **이 표는 추정이다.** 여러 쪽을 한 호출에 넣어 본 적이 **없다**(§15-5 에서 코덱스가
지적한 미검증 항목이 정확히 이것이다). 상한을 확정하기 전에 2·5·10쪽을 실제로 재야 한다.

## 18. 우리가 쓰는 모델은 계열 **최하위**다 — 올리면 남은 구멍 둘이 닫힌다 (2026-09-20)

해리가 "지금 쓰는 제미나이가 정확히 어떤 모델이냐" 고 물어 확인했다.

**`gemini-3.1-flash-lite`** 다(`worker/gemini.js:4` 에 상수로 못박혀 있고 `providerConfig()` 가
**정확히 이 이름이 아니면 거절**한다 — staging 검증용 고정이다). 제미나이 3 계열에서
**가장 오래되고 가장 싼 등급**이다. 같은 키로 쓸 수 있는 것은 `3.5-flash-lite`,
`3.5/3.6/3.7/3.8-flash` 이고 전부 입력 1,048,576 · 출력 **65,536** 토큰이다.

⚠️ **§17-2 의 "7쪽 벽" 은 모델 한계가 아니라 우리 설정이다.** 모델은 출력 65,536 을 받는데
`worker/gemini.js:17` 이 **4,096** 으로 묶어 두었다.

### 18-1. 400px(환각 났던 이미지) — 상위 모델도 **완전히는 못 고친다**

▶ **§17-1 의 "입력 품질 게이트가 필요하다" 는 그대로다.** 모델을 올려도 저해상도는 위험하다.

### 18-2. 정상 해상도(794px) — **3.8 이 §13 의 남은 구멍 둘을 닫았다**

| | `3.1-flash-lite`(지금) | **`3.8-flash`** |

올리는 것만으로 해결됐다.** 프롬프트를 더 손보지 않았다.

### 18-3. ⚠️ 결정에 필요한 칸을 내가 못 메운다 — **단가**

토큰 사용량은 두 모델이 **거의 같다.** 그러므로 비용 차이는 **전적으로 토큰당 단가**다.
`3.1-flash-lite` 는 입력 $0.25 / 출력 $1.50 per 1M 로 알고 있으나,
**`3.8-flash` 의 단가는 확인하지 못했다** — `models.list` 는 가격을 주지 않는다.
⚠️ **추정해서 쓰지 말 것.** 공식 가격표를 봐야 한다.

### 18-4. 이것이 바꾸는 결정

- **§6-2(1회 최대 쪽 수)**: 4,096 이 우리 값이므로 **정책 결정**이지 기술 한계가 아니다.
  올리면 쪽 수가 늘고 비용 상한도 함께 는다 — C3/R9 와 같이 정해야 한다.
- **공급자/모델 선택이 두 갈래로 갈렸다**: "제미나이" 를 고른 것으로 끝이 아니라
  **어느 등급인가**가 남았다. 품질 차이가 실측으로 확인됐으므로 **단가만 확인되면 정할 수 있다.**
- ⚠️ **`providerConfig()` 가 모델 이름 하나를 못박고 있어**(`GEMINI_STAGING_MODEL`)
  등급을 바꾸려면 그 계약도 함께 바꿔야 한다. staging 고정이 production 선택까지
  묶고 있는 상태다.

## 19. 라우팅 판정 (2026-09-20 · 코덱스 검토) — **라우팅하지 않는다**

해리가 제안했다: *"3.8 이 나을 것 같다. 아니면 앤트로픽도 붙어 있으니 — **각 문항은 싼 모델,
간단한 것도 싼 모델, 대용량은 앤트로픽**으로 붙일까?"* 코덱스에 붙였다(읽기 전용 · 84,604 토큰).

> **결론: 자동 라우팅을 도입하지 말고 출시 초기에는 검증된 단일 모델 하나를 모든 정상 입력에
> 적용한다. 저해상도는 상위 모델로 보내지 말고 호출 전에 거절한다.**

### 19-1. "대용량 → 앤트로픽" — **비용 축이 거꾸로이고, 게다가 잘림도 안 고친다**

⚠️ **앤트로픽도 `max_tokens: 4096` 이다** — ✅ 확인(`worker/index.js:890`). §17-2 의 잘림 벽은
공급자를 바꿔도 **똑같이 남는다.** 대용량을 앤트로픽으로 보내는 목적이 잘림 회피였다면
**그 목적을 달성하지 못한다.**

그리고 앤트로픽이 더 비싸다면 **가장 토큰이 많은 작업에 가장 높은 단가를 곱하는 정책**이 된다.
⚠️ 단 "3.5배" 는 §12-5 에서 표시했듯 **가격표 추산**이라, 방향만 조건부로 말할 수 있다.

### 19-2. 실패의 축은 둘이고 **서로 다른 대응**을 부른다

| 축 | 위험 | 대응 |
|---|---|---|
| 입력 품질·내용 복잡도 | **인식 정확도**(§17 의 조용한 환각) | **호출 전 거절**(게이트) |
| 쪽 수·출력량 | **잘림·비용·부분 실패** | **호출 분할** |

⚠️ 내가 "실패는 양과 무관하다" 고 한 것은 **과했다**(코덱스 지적). 양에는 별개의 결정적 실패가
있다 — `finishReason !== "STOP"` 이면 **결과 전체를 버린다**(✅ 확인 `worker/index.js:867`).
`MAX_TOKENS` 로 잘리면 **부분 저장도 없다.**

▶ **쪽 수는 공급자 선택 기준이 아니라 호출 분할 기준이다.**

### 19-3. 난이도 라우팅 — **구조적으로 불가능하다** (✅ 코드로 확인)

호출 전에 Worker 가 보는 것은 **본문 크기·MIME·공급자 설정**뿐이다. 순서가 코드에 주석으로
박혀 있다 — 공급자 선택(`providerConfig(env)`, `:380`) → `reserve` → **`consume`** → **공급자 호출**.
게다가 `providerConfig(env)` 는 **`env` 만 받아** 요청 내용을 볼 수조차 없다.

호출 전에 알 수 있는 것: **해상도 · 쪽 수 · 파일 크기 · 사용자가 고른 '정밀 변환' 모드.**
알 수 없는 것: **수식 복잡도 · 문항 난이도.**

⚠️ **해상도는 '상위 모델로 보낼 신호' 가 아니라 '거절 신호' 다** — **3.8 도 400px 에서 정답을
틀렸다**(§18-1).

### 19-4. "싼 것 먼저 → 저신뢰면 비싼 것" — **반대. 계약을 보존한 채로는 못 만든다**

✅ 확인 — 재시도·fallback 금지가 **붉은 탐침**으로 박혀 있다:
`assert.equal(fetches, 1, "HTTP failure must not retry or fall back to another provider")`
(`worker/gemini.test.mjs:322` · 같은 취지가 `:173`). 실패도 차감하는 계약도 검사로 고정돼 있다.

가능한 형태는 둘뿐이고 **둘 다 계약을 깬다** — ① 한 번 차감에 내부 두 호출(호출 수 상한 계약이
깨지고 비용 차단기가 부정확해진다) ② 두 번째도 별도 차감(자동 재시도 금지가 깨지고 사용자
한도를 2회 쓴다).

▶ **계약을 지키는 유일한 형태는 사용자가 결과를 보고 '정밀 모델로 다시 변환' 을 직접 누르는
별도 요청**이다. 그것은 자동 2단이 아니라 **새 유료 호출**이다.

⚠️ **'저신뢰' 자동 판정도 지금은 성립하지 않는다.** 판별 가능한 것은 HTTP 오류 · JSON 오류 ·
`MAX_TOKENS` · 필수 필드 오류뿐이고, **그럴듯하지만 틀린 수식 · 틀린 정답 · 잘못 읽은 한 단어**는
판별할 수 없다. §17 에서 모델은 **자신 있게 틀렸다.** 두 모델의 일치 여부도 정답의 증거가 아니다.

### 19-5. 앤트로픽 혼용 vs 제미나이 내부 등급 — **제미나이 내부가 훨씬 작고 안전하다**

제미나이 등급 간에는 **같은 envelope · decoder · telemetry · 오류 처리**를 재사용한다.
앤트로픽을 상시 혼용하면 **출력 보증 기제가 영구 이원화**된다(제미나이 `responseSchema` ↔
앤트로픽 tool use `input_schema`). ⚠️ **현재 앤트로픽 경로는 tool use 조차 아니고 자유 텍스트를
`JSON.parse` 한다.** 이 저장소의 반복 실패 방식 3번과 정확히 맞물린다.

⚠️ **코덱스의 중요한 경계 짓기**: **제품 코드에는 아직 `responseSchema` 가 없다**
(`responseMimeType` 만 있다). **§13·§18 의 스키마 실측은 탐침이지 제품 구현이 아니다.**
그 표를 제품의 현재 동작으로 읽지 말 것.

▶ 권장: **출시 경로는 제미나이 한 공급자·한 등급.** 앤트로픽은 요청별 자동 fallback 이 아니라
**장애 시 배포 설정을 되돌리는 비상 복귀 경로**로 남긴다.

### 19-6. **R2 를 이렇게 닫는다**

- **자동 모델 라우팅 없음**
- **저해상도는 호출 전 거절**(⚠️ 최소값 미정 — 400 은 안 되고 794 는 됐다는 것만 안다.
  400~794 사이와 흐림·기울어짐 표본을 재야 한다. 지금 클라이언트는 **상한 1568px 만 있고
  하한이 없다** — ✅ 확인 `pedagogy-ai-image.js:17`)
- **공급자 호출당 한 쪽**
- 여러 쪽 작업은 **쪽별 순차 호출 + 부분 성공**
- 사용자가 **명시적으로 다시 요청한 호출만** 별도 quota 차감

▶ 이렇게 하면 **"1회 최대 쪽 수" 가 라우팅 결정에 종속되지 않는다.**
⚠️ **§17-2 의 "약 7쪽" 을 확정값으로 쓰지 말 것** — 4,096 × 쪽당 출력량의 **추정**이고
**다쪽 호출 자체가 미실측**이다.

### 19-7. C3 로 넘기는 것

- **모델 등급 확정** — `3.8-flash` **공식 단가** 확인 + 대표 자료 평가 뒤.
  · 추가 비용 허용 + 정상 해상도 우세 → **전부 `3.8-flash`**
  · 예산 초과 또는 품질 우위 미재현 → **전부 `3.1-flash-lite`** + 프롬프트·검증·검토 강화
  · 앤트로픽은 **동일 입력 비교에서 비용을 상쇄할 품질 우위**가 확인될 때만 재검토
- **작업당 총 쪽 수의 비용 상한**

- ⚠️ 등급을 바꾸려면 `GEMINI_STAGING_MODEL` 상수 계약도 함께 바꿔야 한다(§18-4).

## 20. R3 1차 — 크기 방어 (2026-09-21 · 코덱스 검토)

보냈다. 120초 · 최종 답변 4.9KB · **내 컨텍스트에 실린 것은 그 파일 하나**다.
⚠️ 서브에이전트 경로는 같은 종류의 한 왕복에 **74,145 토큰**을 실었다 — 갱신된 `CLAUDE.md` 의
비용 계약이 겨냥한 차이가 이것이다.

### 20-1. ⚠️ 지금 존재하는 결함 — **초과 문서 하나가 batch 전체를 실패시킨다**

✅ 코드로 확인. **모의고사에는 완성된 방어가 있고 문제집에는 통째로 없다.**

| | 모의고사 | **문제집** |

| 초과 시 안내 | 부수를 세어 토스트 + "이 기기에는 저장돼 있습니다" (`:5177`) | **없다** |

`MOCK_DOC_MAX = 900*1024`(`:5095`), `docBytes()` 는 `TextEncoder` 로 **UTF-8 바이트**를 잰다

`CLAUDE.md` 가 이미 적어 둔 함정이고 모의고사는 그것을 지켰다.

⚠️ **Firestore batch 는 원자적이다.** 초과 문서 하나가 섞이면 **그 flush 의 다른 문제집도 함께
못 올라간다.** 이것은 B 작업과 무관하게 **오늘 이미 있는 위험**이다.
⚠️ **재현하지 않았다 — 코드를 읽어 확인한 것이다.** 그래서 `reviews/issues/` 에 등록하지 않고
여기 적는다(이 저장소는 **재현한 결함만** 이슈로 올린다). 재현 절차를 만드는 것이 다음 사람 몫이다.

### 20-2. 판정 지점 — `saveSets` 도 `docToSet` 도 아니다

**`writeCloudSnapshot()` 에서 `setToDoc(s,i)` 를 만들어 깊은 복사한 직후**(`index.html:3509`).

- ❌ `saveSets()`(`:4443`) — 히스토리·수정 시각·**로컬 보존**까지 맡는다. 여기서 거절하면
  **클라우드 한도 때문에 로컬 복구본도 못 남긴다.**
- ❌ `docToSet()`(`:3016`) — **클라우드 읽기·복구 경로**이고 `lossless:true` 로 기존 자료를
  보존한다. 여기서 자르면 **기존 대형 자료를 읽는 순간 손실된다.**
- ❌ `newProblem()`(`:2794`) — 빈 문항 생성기라 문제집 전체 크기를 알 수 없다.

▶ **변경 대상은 `index.html` 과 회귀 검사뿐이다.** 크기 제한은 스키마 변경이 아니라
`mock-library-store.js`·`firestore.rules`·`pedagogy-normalize.js` 를 건드릴 이유가 없고,
**기존 데이터 호환성에도 영향이 없다.**

### 20-3. 한도 초과가 예상될 때 — **사용자 주도 분할, 원본·복제본 모두 보존**

## 21. R3 2차 — 충돌 검출과 부분 실패 (2026-09-21 · 코덱스 검토)

래퍼 · foreground · 질문 2개. 144초 · 최종 답변 7.2KB. **1차 합의는 다시 보내지 않았다.**

### 21-1. 최소 충돌 검출 — **문서별 정수 `revision` + transaction CAS**

- 최초 생성 `1`, 수정·재정렬·**tombstone 모두 정확히 +1**.
- 저장 transaction 은 `server.revision === baseRevision` 일 때만 `+1` 로 쓴다.
  다르면 — **내용이 서버와 같으면 이미 반영된 것으로 ACK**, 다르면 **충돌로 중단.**
- 신규 ID 는 **문서 부재**를 기대값으로 삼는다.

⚠️ **여기서 빠진 것이 드러났다 — ✅ 코드로 확인.** `let cloudSynced = new Map()`
(`index.html:2982`)은 **메모리뿐이라 새로고침에 사라진다.** CAS 기준값을 담을 곳이 없으므로
**owner 별 로컬 동기화 메타데이터(`{revision, 내용 해시, order}`)를 새로 만들어야 한다.**
`stampsKey` 의 시각은 **편집·병합 보조값으로만** 남기고 CAS 근거로 쓰지 않는다.

⚠️ **지금은 시각으로 덮어쓴다 — ✅ 확인.** `watchCloud` 가 `localStamp > d.updatedAt` 으로
가른다(`index.html:3189`). 로드맵이 **"시각만 서버 시각으로 바꾸는 것은 충돌 해결이 아니다"**
라고 못박은 그것이다. `mergeSets` 의 `updatedAt` 승자 선택(`:3029`)과 함께 **충돌 판정에서
제외**하고, 원격 revision 이 전진했는데 로컬이 기준 ACK 와 다르면 **덮어쓰지 않고 충돌 상태**로 간다.

**Rules 파급** — `hasOnly` 에 `revision` 추가(양의 정수) · **합쳐진 `allow create, update`
(`firestore.rules:92`)를 분리**해야 한다(create: `revision==1` / update: `revision==resource+1` /
무 revision 문서의 최초 승격만 `==1` 허용).
⚠️ **한 단계 배포는 안전하지 않다** — 구 규칙은 새 필드를 거부한다. 전환 규칙 → revision
클라이언트 배포 → 엄격 규칙 순서가 필요하다.
▶ ✅ **이 저장소에 선례가 있다**: `service-config.js` 의 `libraryCloudSchema`·`mockCloudSchema`
로 **이미 두 번 한 방식**이다(`CLAUDE.md` 가 "구형 Rules 배포에는 0 으로 내려라" 를 적어 둔 그것).

**충돌 UX** — ⚠️ **자동 병합하지 않고 어느 쪽도 폐기하지 않는다.**
서버 원본은 그대로 두고, **로컬 초안을 새 ID 의 일반 문제집으로 한 번만 복제**해 즉시 로컬 보존한다
(ACK 전에는 "이 기기에만 보존됨"). 화면에는 원본 이름 · "다른 기기 변경/삭제" · **기준 revision 과
현재 revision** · 사본 위치를 보인다(**시각은 설명용일 뿐 승자 판정에 쓰지 않는다**).
선택지 넷: `두 버전 보기` · `서버본으로 돌아가기` · `로컬본으로 서버 교체`(최신 revision 기준 명시
CAS) · `로컬본 export`. 같은 `{setId, baseRevision, serverRevision, localHash}` 에서 **사본을
반복 생성하지 않는다.**

### 21-2. 부분 실패 — **staging 에 두고, 기존 문제집에는 아무것도 안 넣는다**

10쪽 중 4쪽 실패 시:

| 대상 | 처리 |
|---|---|
| 1~3쪽 | 결과 + **원본 위치·꼬리표·출처 순서·응답 체크섬**을 staging 에 확정 저장 |
| 4쪽 | 실패 원인 · **quota 차감 영수증/attempt ID** · 실패 상태. ⚠️ **검증 실패한 생성 결과는 채택 결과로 저장하지 않는다** |
| 5~10쪽 | `pending` |
| 버리는 것 | **재생성 가능한 값만**(임시 렌더 버퍼). 원본 파일·작업 설정·공급자/모델·프롬프트/스키마 버전·파일 해시는 보존 |

⚠️ **기존 문제집에는 아무것도 넣지 않는다.** 전체 완료 후 채택하거나, 사용자가
**`성공한 쪽만 문제집 만들기`** 를 명시적으로 고를 때만 새 복제본을 만든다. **원본 불변.**

▶ 중간 저장소는 **작업 전용 IndexedDB**. 쪽 결과와 원본 Blob 은 `localStorage` 에 부적합하다.
⚠️ 이것은 **저장 구조의 IndexedDB 일괄 전환이 아니라** 다중 입력 재개에 한정된 staging 이라,
로드맵의 "IndexedDB 일괄 전환 유보" 와 충돌하지 않는다.

**중복 방지는 작업 단위가 아니라 쪽 단위**:
`userId + jobId + sourceHash + pageNumber + extractionContractHash`, 그 아래 유료 호출마다 `attemptId`.
`success` 인 쪽은 **체크섬과 함께 종결 잠금**하고 '이어서 하기' 대상에서 뺀다.
자동 재시도 없음 — 사용자가 **`4쪽 다시 시도 — 1회 추가 차감`** 또는 **`건너뛰고 5쪽부터`** 를 고른다.

### 21-3. ⚠️ **미합의 — 여기가 이번 왕복의 핵심이다**

> **서버 attempt ledger 없이 "성공한 쪽을 절대 재호출하지 않음" 을 보장할 수 없다.**

클라이언트 IndexedDB 만으로는 **"공급자는 성공했는데 응답을 저장하기 전에 탭이 종료된"** 구간을
덮지 못한다. 보장하려면 **서버가 공급자 호출 전에 attempt 를 기록하고, 결과를 서버 ledger 에
확정한 뒤 클라이언트에 응답**해야 한다. quota 차감과 attempt 생성이 **서버에서 원자적**이어야 하고,
같은 attempt ID 가 다시 오면 **재호출도 재차감도 없이 기존 결과를 돌려주어야** 한다.

▶ 그 장치가 없다면 모호한 `in_flight` 쪽은 **자동 재호출하지 않고 사용자에게 비용 중복 가능성을
알린다.** 로드맵의 "중복·재시도 비용을 사전에 고정하라" 가 이 경계를 포함한다.
▶ **이것은 제품 비용·복잡도 결정이다** — '이어서 하기' 를 정확히 하려면 브라우저 상태만으로는
안 되고 **서버 상태가 필요하다**(Durable Object 또는 Firestore).

### 21-4. R3 종결

- **합의** — 문서별 `revision` CAS · 충돌 사본·export · 쪽별 staging · 사용자 주도 재개.
- **미합의** — 서버 attempt ledger 없이 재호출 방지를 보장한다는 주장은 성립하지 않는다.
- **근거** — 현재 구현은 `updatedAt` 승자 병합과 구독 덮어쓰기이고(`:3029`·`:3189`),
  `cloudSynced` 는 메모리뿐이며(`:2982`), Rules 는 create/update 가 합쳐져 있다(`:92`).
- **다음 행동** — R3 계약에 **revision 전환 순서 · 충돌 UX · IndexedDB 작업 스키마 ·
  쪽/attempt 상태 전이 · quota 원자성**을 명시한다. **(구현은 아직 0줄)**
