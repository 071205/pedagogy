# 운영·보안 런북

## 매일 확인

- Cloudflare Worker 4xx/5xx, AI 공급자 오류, Durable Object 오류, AI 요청량
- Cloudflare Workers Logs의 `event=ai_usage`: `task`별(`problem_image`·`document`) 성공률,
  `input_tokens`·`output_tokens`, `stop_reason`, `duration_ms`, `http_status`. 현재 로그는 10% 표본이라
  장애·품질 추세에 쓰고, 전체 Anthropic 과금과 일치한다고 가정하지 않는다.
- Firebase Firestore read/write/delete, Storage 용량·전송량, Authentication 신규 가입량
- Anthropic 사용량·한도·결제 상태
- 고객지원 메일과 권리자/개인정보 요청

## AI 비용 급증 또는 악용 의심

우선 `AI_KILL_SWITCH=1`을 반영하고 **새 AI 요청이 503이며 공급자 호출이 없는지** 확인한다.
설정 전파·진행 중 요청은 남을 수 있다. 이 스위치는 Firebase·Worker 요청 자체·저장 비용을
멈추지 않는다. 비용원별 차단은 [보안 운영 체크리스트](SECURITY-OPERATIONS-CHECKLIST.md)를 따른다.

1. Cloudflare Worker의 `DAILY_LIMIT` 또는 `PLAN_DAILY_LIMITS_JSON`을 임시로 낮추고 배포한다.
   Worker는 코드상 하루 10,000회를 절대 상한으로 두므로, 그보다 큰 값은 설정 오류로 기본값이
   적용된다. 더 큰 계약 한도가 필요하면 코드·비용 알림·승인을 함께 갱신한다.
2. Firebase App Check enforcement와 Firebase Auth 승인 도메인을 확인한다.
3. 표본 로그에서 `task`별 `http_error`·`json_parse_error`와 `max_tokens` 중단이 급증했는지 확인한다.
   이미지·프롬프트·AI 응답 원문·사용자 UID를 검색하거나 기록하지 않는다.
4. 개별 계정 정지는 F3a/F3c 서버 계정 상태·운영 도구 구현 후 가능한 절차다(현재 미구현).
   그 전 개별 차단 완료를 약속하지 않으며 기존 전체 AI 차단의 영향 범위를 안내한다. Worker에 UID
   블랙리스트를 하드코딩하지 않는다.
5. Anthropic key 노출이 의심되면 즉시 폐기·재발급하고 배포한다.
6. 원인, 시각, 영향 계정, 조치, 재발 방지를 인시던트 기록에 남긴다.

## 개인정보·계정 삭제 요청

1. 서비스의 계정 삭제 기능을 먼저 안내한다. AI quota는 일반 사용자 DELETE로 초기화하지
   않으며 최초 예약 시 설정한 48시간 alarm으로 별도 파기한다. 실제 사용자 데이터 삭제와
   비용 카운터 만료를 구분해 설명한다.
2. 실패하면 운영 계정에서 임의로 사용자 문서를 열지 않는다. 별도 테스트 계정으로 재현하고,
   필요한 경우 수탁자 콘솔의 권한 있는 절차를 사용한다.
3. Anthropic API의 기본 30일 보존 및 안전·법적 예외, 백업·법정 보존 예외를 안내한다.
4. 요청·본인 확인·처리 범위·완료 시각을 접근 제한된 티켓에 기록한다.

## 데이터 손실/복구

1. 먼저 사용자의 전체 JSON 내보내기와 브라우저 백업 존재 여부를 확인한다.
2. Firestore 복구는 사전에 정의한 백업/PITR 절차와 승인자 두 명의 검토 후 수행한다.
3. 복구는 원본을 덮어쓰지 말고 격리 프로젝트/경로에서 검증한 뒤 진행한다.
4. 복구 완료 후 사용자의 권한·이미지 참조·문제집 수·인쇄 결과를 확인한다.

## 배포

1. PR CI, `npm run test:worker`, `npm run check:static`, `npm run check:rules`(JDK 21 필요),
   브라우저 회귀 테스트를 통과한다.
2. staging에 먼저 배포하고 로그인·저장·AI·계정 삭제를 테스트 계정으로 확인한다.
3. Worker 배포 후 `/health`가 `{"ok":true}`인지 확인하고 Cloudflare binding·migration을 검토한다.
4. production Firebase Rules 배포 전 Emulator 테스트와 diff 검토를 한다.
5. 배포 커밋, Worker version ID, 규칙 버전, 롤백 방법을 인계 기록에 남긴다.

## 결제·계정·지원 운영 절차 초안 — F3/F4/L4 구현 후 활성화

아래는 [서비스 준비 설계](SERVICE-READINESS-DESIGN.md) §3~§9의 예정 절차다.
명령/담당/연락처·중단 설정 전파·실제 RPO/RTO가 검증될 때 실행 가능한 런북으로 확정한다.
현재 없는 Billing API/도구를 실행할 수 있다고 안내하지 않는다.

| 상황 | 예정 조치 | 완료로 판단할 증거 |
| --- | --- | --- |
| 오청구/중복 의심 | 새 주문·자동 갱신을 각각 중단, 기존 조회/검증 수신·해지 유지. 동일 cycle/주문을 PG와 대조 | 진행 중 결과 불명 수, 중복/환불 확인, 승인된 조정 감사; 새 주문으로 재청구 금지 |
| PG/알람 장기 장애 | 영속 미완료 작업과 색인 대조, 재시도 소진 건을 운영 확인으로 전환 | 원 상태/현재 PG 상태 확인 뒤 동일 작업 재개; 키 유효 기간 경과 뒤 새 키 청구 금지 |
| claim/메일 장애 | 권한 장부·최신 revision 확인, 작업 재시도/수신 실패 안내 | 최신 claim 대조·전달 상태, 메일 수신을 동의로 오인하지 않음 |
| 탈퇴 일부 실패 | fence 유지, 서버 개인자료·PG/키·현재 기기 정리를 독립 추적, 필요한 증빙만 보존 | 서버/기기/B5 단계별 확인과 Auth 처리; 다른 기기 로컬 삭제 완료로 표시 금지 |
| 장부/자료 복구 | 청구 중단, 격리 복구, 삭제 기록 우선 적용, PG/키/색인 대조, 독립 승인 후 재개 | 이미 처리한 결제/환불 재실행 없음, 삭제 자료/권한 부활 없음, 사용자 참조/출력 확인 |
| 개인정보/권리 침해 신고 | 제한된 티켓·본인/권리 확인, 필요한 기능/접근 제한·증거 보존, 담당자 이관 | D13/L2에서 정한 조사·통지/신고 기한·담당·처리 기록; 공개 로그에 원문 첨부 금지 |

당직/대체 연락처·지원 운영 시간·복구 승인자는 L4에서 실제 지정한다. 고객 안내는 확인된 영향·처리
상태·다음 안내 시각을 적으며 완료되지 않은 복구를 약속하지 않는다. 테스트 계정으로 경보 수신,
지원 접수/에스컬레이션, PG 장애 및 복구 후 재개를 리허설하고 비공개 증거의 위치만 인계에 남긴다.
