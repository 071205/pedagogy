작성: 2026-09-13. 사용자 목적 정정에 따른 기본 진행 기준. 기준 코드: `e9711cb`.

개발 효율 개선 후 서비스 AI의 측정 배포·실환경 검증·비용 판단까지 이 문서 한 곳에서 끝낸다.

## DEV-1 — 필요한 코드로 바로 들어가기

AGENTS.md, reviews/README.md, INDEX의 열린 이슈와 관련 파일부터 읽는다. 지난 인계를 전부 읽지 않는다.
기존 구조 설계의 수치는 과거 기록이므로 현 코드의 script 연결·전역 의존성·수정 이력으로 대조한다.

산출물은 [CODE-MAP.md](CODE-MAP.md)다(DEV-1 완료). 파일 목록을 복제하지 말고 다음을 담는다.

- 주요 사용자 기능별 진입 파일·대표 함수/검색어·외부 모듈·직접 관련 회귀 명령.
- 로딩 순서, window에 공개된 이름, 저장/인증 상태처럼 옮기기 전 확인할 경계.
- 최근 관련 변경 이력과 읽어야 하는 코드 범위에서 뽑은 후보 최대 3개: 수정 빈도, 전역/DOM 의존,
  예상 탐색량 감소, 검사 부담. 낮은 위험의 자주 수정되는 기능을 우선하되 후보가 없으면 없다고 기록한다.
- 대표 유지보수 질문 2개를 고정하고, 현재 답을 찾는 파일·함수·읽은 범위와 기준 커밋을 짧게 남긴다.
  합성 탐색 과제임을 밝히며, 절감 효과를 만들기 위한 불필요한 제품 수정은 하지 않는다.

지도는 핵심 표 위주로 약 100줄 이내를 목표로 하되 필요한 맥락을 자르지는 않는다.
줄 번호만 믿지 않도록 함수·검색어를 함께 둔다. 변경한 기능의 항목만 이후 갱신한다.
074(Git 아이콘)·075(실계정 복귀 로그인)는 열린 상태를 보존하고 해당 작업에 영향을 줄 때만 조사한다.

## DEV-2 — 구현자가 다시 설계하지 않아도 되는 경계

DEV-1 지도를 확인하며 이 레일의 진행 기록에 연결할 짧은 분리 설계 문서를 만든다.
대상 함수·변경 파일, 상태 읽기/쓰기, DOM 접근, 이벤트 등록·초기화 순서, window/lexical 계약,
입출력과 오류 처리, 기존 호출부와의 연결, 공개 빌드 목록/CSP/인라인 스크립트 추출에 미치는 영향을 고정한다.
저장 데이터 형식과 계정 격리 동작을 유지한다. 구현 단계가 임의로 공개 표면을 바꾸지 못하게 한다.

관련 회귀 명령과 재현 시나리오, 실패 주입 위치·기대 실패, 추출만 되돌릴 수 있는 파일 묶음을 명시한다.
통과한 과거 검사 중 재사용 가능한 것은 커밋·환경과 함께 구분한다. 새 코드의 필수 검증을 과거 결과로 대체하지 않는다.
후보가 너무 얽혔거나 탐색량 감소가 불명확하면 **지도 유지·분리 보류**도 유효한 종료다. 이때 DEV-5로 이동한다.

## DEV-3·4 — 구현과 독립 검토

DEV-3은 설계한 한 경계만 추출한다. 새로운 전역 연결을 늘려 파일 간 왕복이 증가하지 않는지 확인한다.
설계 문서의 검사와 기존 필수 검증을 실행한다. 구조 추출에는 기존 check:fast 완료 조건을 유지하고,
serve.py로 regression-test.html, Chromium·Firefox·WebKit의 영향 경로와 기존 file:// 지원 범위를 확인한다.
공개 빌드에 새 파일이 실제 포함되고 로딩 순서·CSP가 유지되는지도 확인한다.
추가·변경 회귀는 의도적 결함에서 실제 실패해야 한다. 검사가 파일 위치에 의존했다면 검사 위치를 고치되
동작 단언을 없애거나 약화시키지 않는다. 미실행 검사가 있으면 완료로 넘기지 않고 환경·남은 명령을 인계한다.

DEV-4는 구현자와 다른 검토 주체가 실제 diff·관련 소스·증거를 대조한다. 모델 이름 변경만으로 독립성이 생기지 않는다.
동일 구현자가 다시 확인한 결과는 자체 검증으로 기록하고 독립 승인이라고 쓰지 않는다.
기존 성공 검사를 무조건 재실행하지 않되, 의심 경계는 직접 재현한다. 결함이면 이슈를 등록하고 DEV-3으로 반환한다.
수정자는 같은 이슈에 해결 근거를 남기고, 검토자는 수정 영향 범위만 재검토한다. 승인한 동일 diff를 반복 심사하지 않는다.
새 구현 인계가 필요하며 지도는 해당 항목만 갱신한다. 사용자 변경과 무관한 정리는 섞지 않는다.

## DEV-5 — 효과가 있을 때만 더 분리하기

DEV-1의 두 질문을 새 구조에서 찾아 비교한다. 모델·추론·커밋, 읽은 파일/범위, 재탐색, 수정·검증 부담을 기록한다.
이미 답을 아는 재탐색은 실제 업무와 다르므로 합성 비교의 한계를 밝힌다. 이후 실제 수정 한 건의 관찰을 더하면 좋지만,
그 일이 없다고 만들거나 기다리며 계속 토큰을 쓰지 않는다. 실제 작업 증거가 없으면 탐색 비교와 자료 대기를 구분한다.
분리 구현·검사·인계에 든 일회성 비용도 함께 판단한다. 정확한 토큰 통계가 없으면 대리 지표라고 명시한다.
계정 전체 사용량을 이 작업만의 비용으로 간주하지 않는다. 90% 절감 같은 보장이나 임의 바이트→요금 환산을 하지 않는다.

- 탐색 경로가 짧아지고 재작업·검증 부담이 수용 가능하면 현재 분리를 유지하고 다음 후보 근거를 기록한다.
- 효과가 불분명하면 분리를 더 하지 않고 지도·탐색 규칙만 유지한다. 되돌리기도 비용이므로 자동 되돌리지 않는다.
- 추가 분리 후보는 후속 목록에만 남기고 이번 레일에서는 첫 경계의 검증을 마친 후 OPS-6으로 간다.
  모호한 효과 판단은 Astra high에 좁게 인계한다. 분리를 무한 반복해 서비스 작업이 밀리지 않게 한다.
- 실제 업무 증거가 없으면 효과 확인의 한계를 적고 OPS-6으로 이동할 수 있다. 실제 절감 입증이라고 쓰지 않는다.

## OPS-6 — 기존 C에서 필요한 배포 준비 흡수

기존 C는 문서 탐색까지만 했고 준비 묶음은 미완료다. [운영 런북](OPERATIONS-RUNBOOK.md)과
[운영 증적](SECURITY-OPERATIONS-CHECKLIST.md)의 배포 요구를 확인하고 그 요구를 이행한다.
실제 배포본과 로컬 코드의 차이, 함께 나가는 과거 보안 변경, staging/production 대상, bindings·migration,
모델·샘플률, secret 연결 여부(값은 출력하지 않음), 유효한 검사 커밋·환경, 롤백 버전을 확인한다.
운영 상태를 읽을 권한이나 정확한 대상이 없으면 확인된 범위와 미확인 항목을 구분하고 OPS-6 대기로 둔다.
테스트 환경·계정·키를 임의 생성하지 않는다. 승인 질문 전에 읽기 전용 확인과 준비 가능한 자료를 완성한다.

합성 테스트 자료, 호출 횟수 상한, 현재 가격과 입력/출력 한도를 근거로 한 예상 최대 비용을 적고
대상 배포·실호출·로그 관찰·설정 복원 범위를 한 번에 승인받는다. 이미 받은 해당 승인은 재사용한다.
요청 이미지·프롬프트·응답 원문·UID·인증 토큰을 증적이나 로그에 복사하지 않는다.

## OPS-7 — 측정이 실제 환경에서도 동작하는지 확인

승인된 테스트 환경에서 개인정보 없는 합성 이미지와 문서로 두 경로를 확인한다.
인증 거절·quota·실패 처리와 event=ai_usage의 task, input_tokens, output_tokens, stop_reason,
duration_ms, outcome, http_status를 검증한다. 로컬에서 이미 주입한 실패를 실제 유료 호출로 불필요하게 반복하지 않는다.
생산 배포는 별도 대상 승인 후 실행한다. 승인 환경의 검증을 생산 전체 검증으로 표현하지 않는다.

현재 저장소의 관찰 설정은 head_sampling_rate=0.1이다. 로컬 이벤트 1회와 플랫폼 저장 표본을 구별한다.
한두 번 로그가 없다고 호출을 반복하지 않는다. 실시간 로그 또는 staging 임시 샘플률 조정은 도구가 수집하는
원문·헤더 경계를 먼저 확인하고 OPS-6 승인 묶음에 포함한다. 운영 100% 수집으로 몰래 바꾸지 않는다.
검증한 배포 버전·설정 복원·결과와 미확인 사항을 기록한다. 필요한 검증이 끝나지 않으면 OPS-7 대기다.

## OPS-8 — 실제 서비스 비용·품질 근거 모으기

개인 식별자 없는 메타데이터에서 작업별 총 표본 수·성공/실패 수·토큰 미확인 건수, 입출력 토큰 중앙값/p95,
max_tokens 중단 비율, 응답 시간, 관찰 기간·모델·샘플률을 정리한다. 실패 표본도 포함한다.
표본 수가 적으면 p95나 낮은 실패율을 신뢰할 수 없음을 밝힌다. 30~50건을 충분성 기준으로 고정하지 않는다.
표본 총합을 청구액으로 쓰거나 누락 토큰을 0으로 간주하지 않는다. 실제 절감은 검증 전까지 주장하지 않는다.
현재 Worker는 자동 재시도와 재시도 연결 ID가 없으므로 사용자 재시도별 비용을 직접 계산할 수 없다.

일부 관측이 있어 한계를 분석할 수 있으면 자료 부족에 따른 유지 판단을 OPS-9에 넘길 수 있다.
관측 데이터가 전혀 없거나 접근할 수 없으면 OPS-8 데이터 대기다. 요약기·대시보드·추적 ID를 임의 추가하지 않는다.
데이터를 채우려 유료 호출을 늘리거나 사용자 요청 없이 모니터링을 예약하지 않는다.

## OPS-9 — 출력 한도는 이익이 있을 때만 변경

Astra high가 OPS-8 자료로 판단한다. 출력 상한은 선결제 토큰이 아니므로 같은 길이의 응답에는 절약이 없을 수 있다.
관측 근거가 부족하거나 순이익이 없으면 **두 경로 4096 유지**를 결정하고 이 단계는 완료한다.
이는 절감 성공 선언이 아니다. 자료가 없다며 OPS-7의 필수 실환경 검증을 생략해서도 안 된다.

변경 근거가 있으면 같은 합성 표본의 문항·수식 정확도, 출력 완전성, JSON 성공률, 실패 포함 비용과
잘림·재시도 위험의 비교 기준 및 허용 한도를 먼저 고정한다. Terra medium은 두 작업의 max_tokens만
분리·변경하고 quota·프롬프트·공급자를 동시에 바꾸지 않는다. 실호출은 승인 예산 안에서만 실행한다.
관련 Worker 회귀·실패 주입과 Sol medium의 독립 검토를 마친 뒤 기록한다. 이익이 사라지면 유지로 판단한다.

## OPS-10 — 공급자 확대는 필요성 판단으로 먼저 끝내기

Astra high가 현재 품질·비용·운영 부담으로 현 공급자 유지 여부를 판단한다.
**기본 종료는 Anthropic 유지, 비교·어댑터 미도입**이다. 다른 공급자 연결을 완주 조건으로 만들지 않는다.
현재 공급자로 해결하기 어려운 품질·비용 문제가 입증된 경우에만 아래 하위 순서로 진행한다.

1. Astra high가 후보별 현재 계약·입력 보존·학습 이용·삭제·처리 위치 등 개인정보 적격성과 이미지 입력 지원을
   확인하고 동일한 합성/권리 확보 표본·정답·채점법·모델 ID·비교 예산을 설계한다. 적격 판정 전 개인 자료를 전송하지 않는다.
2. 후보/예산 승인 후 Terra medium이 정확도·JSON 성공률·속도·실패 포함 비용을 비교한다.
   가입·계약·키 발급·실호출을 승인 없이 수행하지 않는다. 채택 이득이 없으면 현 공급자 유지로 완료한다.
3. 이득과 적격성이 확인되고 사용자가 연결을 승인하면 Astra high가 Worker 내부 어댑터 하나의 경계를 설계하고
   Sol medium이 구현한다. 외부 JSON·인증·quota·안전 로그 계약 및 Anthropic 복귀 경로를 유지한다.
   자동 재시도·자동 fallback으로 복수 공급자 비용이 생기는 기능은 포함하지 않는다.
4. 구현자와 다른 검토 주체(Astra high 권장)가 관련 회귀·실패 주입과 복귀 경로를 독립 검토한다.
   실제 배포가 필요한 변경은 OPS-6·7의 대상 승인·검증 기준을 같은 레일에서 적용한 뒤 마감한다.

## 통합 완료·대기 기준

- 개발: 탐색 지도와 첫 경계의 구현·검토 또는 근거 있는 분리 보류 결정, 효과 비교·한계를 기록했다.
- 서비스: 승인된 환경에서 측정 검증과 설정 복원을 완료했고, 표본 분석과 출력 한도·공급자 유지/변경 판단이 끝났다.
- 선택한 변경은 필요한 회귀·독립 검토·승인된 배포 검증까지 끝나야 한다. 후보를 검토하지 않고 채택 완료라고 쓰지 않는다.
- 승인·환경·데이터가 없으면 **통합 완료가 아닌 해당 단계 대기**다. 완료한 부분·남은 조건·담당 모델을 현재 위치에 적는다.
  대기 중 독립적으로 준비 가능한 문서·분석만 진행하며, 뒤 단계의 선행 조건을 건너뛰지 않는다.
- 두 목표를 모두 판단·검증하면 통합 레일 완료다. 추가 분리·공급자 확대를 무한 반복하지 않는다.
  이 완료는 전체 서비스 출시 또는 실제 비용 절감률 보장을 뜻하지 않는다.
