## 이전 위치 — R3 왕복 2회

아래는 당시 기록이다. 크기 방어·메타데이터는 B1/B2에서 완료했고 최종 계약은 `STORAGE-CONTRACT.md`다.

- ⚠️ **지금 존재하는 결함**: 문제집 클라우드 저장에 **크기 선제 방어가 없다.** 모의고사에는
  `ready`/`tooBig` 분리가 있는데(`index.html:5174`) 문제집은 `dirty` 를 전부 batch 에 넣는다
  (`:3514`). Firestore batch 는 원자적이라 **초과 문서 하나가 그 flush 전체를 실패시킨다.**
  ⚠️ **재현하지 않았다**(코드 확인) — 그래서 이슈로 등록하지 않았다. 재현 절차가 다음 몫이다.
- ⚠️ **`cloudSynced` 가 메모리뿐이다**(`index.html:2982`). revision CAS 의 기준값을 담을 곳이
  없으므로 **owner 별 로컬 동기화 메타데이터가 새로 필요하다.**
- ⚠️ **Rules 전환은 한 단계로 못 한다.** `revision` 추가 + `allow create, update` 분리가
  필요하고 구 규칙은 새 필드를 거부한다. **`libraryCloudSchema`·`mockCloudSchema` 선례**대로
  전환 규칙 → 클라이언트 배포 → 엄격 규칙 순서로 간다.
- ⚠️ **미합의 하나**: **서버 attempt ledger 없이 "성공한 쪽을 재호출하지 않음" 을 보장할 수 없다.**
  '이어서 하기' 를 정확히 하려면 브라우저 상태로는 부족하고 **서버 상태가 필요하다.**
  이것은 제품 비용·복잡도 결정이라 사용자 판단이 필요하다.

헤더는 확인하되 나머지 진행 로그는 실패 분석 때만 읽는다. 처음 더했을 때 `parseArgs` 가 옵션을

- 사용자가 모델을 전환한다. 자동으로 다른 작업/에이전트를 만들지 않는다.
- 한 요청의 기본 단위는 **현재 단계의 한 작업 묶음**이다. 권장 모델 차이만으로 진행을 막지는 않되,
  다음 단계에서 더 싼 모델로 충분하면 현재 단계 인계를 끝내고 전환 문구를 준다.

- 관련 검사는 변경 묶음 뒤 1회. 성공 결과에는 커밋·환경·실행/skip을 기록하고 변경 없는 검사는 재사용한다.
  같은 실패를 새 가설 없이 재시도하지 않는다. 출력은 로그에서 종료 코드·실패 주변만 읽는다.
- 필요 이상의 테스트를 새로 만들지 않는다. 기능 수정은 AGENTS의 regression-test.html 의무를 지키고,
  추가·수정 회귀에는 실제 실패 주입을 수행한다.
- 계정 사용량을 시작과 단계 경계에서 확인한다. **잔여 20%부터 범위를 고정, 10%부터 기록·검증 정리,
  5% 도달 전 종료**를 목표로 한다. 소진을 기다리거나 실패한 외부 상태를 반복 조회하지 않는다.
  이는 운영 기준이며 토큰 소모를 정확히 보장하는 한도 장치는 아니다.
- 독립 검토는 구현자와 다른 검토 주체가 맡는다. 사용자에게 다른 검토 작업을 넘길 문구를 제공하고,
  승인한 동일 diff를 다시 심사하지 않는다. 자기검증은 자기검증으로 기록한다.
  앞으로는 역할 계약대로 Codex 구현 → Claude 검토, Claude 구현 → Codex 검토다.
  기존 B1/B2의 독립 Astra 승인은 유효하며 새 역할 규칙 때문에 다시 검토하지 않는다.
  예산 소진·중단은 검토 대기이지 승인이나 단계 완료가 아니다.

## 주 실행 순서

외부 조건으로 막힌 행은 대기 이유를 기록하고, 선행 조건을 충족한 다음 행의 독립 작업을 선택한다.
완료 구간 R1(자기검증)→R2→R3→R4/B1~B3 코드·검토→R4.5는 재실행하지 않는다.
현재 재개 순서는 **B3 최종 증거 검토·B5 독립 검토 → B5 배포 순서 확인 → U0 남은 결정·계약 → B6 → B7 → U1 → U2 → R5 → R6 → R7 → R8 → R9 → R10**이다.
U0~U2는 기존 R4 안의 작업 묶음이며 별도 실행 레일이 아니다. 각 구현 뒤 비구현자 검토를 끼운다.
이 순서는 현 저장 계약을 유지하는 기준안이다. D1은 독립 사본/수정 연동을 삽입 시 선택하는
방향으로 답했다. 연동 저장의 영향받는 선행 조건과 계약만 B4/B6 전에 확정하고, 미결 정책은
사용자 확정으로 취급하지 않는다.
B6는 B5 독립 검토와 U0 데이터 계약, B7은 B6가 선행이다.
U1은 U0 시안·B4가 완료되면 B5~B7/C1 대기 중에도 진행 가능하다. U2는 U1·B4~B7을 모두 요구한다.
이 예외는 한 번에 한 구현자 규칙을 바꾸지 않는다. **R5를 B4의 선행 조건으로 두지 않는다.**
R7의 실제 환경 전환 대기 중에는 R8의 로컬 검증을 진행할 수 있지만 운영 검증 완료로 표시하지 않는다.

### R1 — 완료 증거 대조 기준(구현 재실행 목록 아님)

시작 자료: HANDOFF-150·151, `serve.py`, `.sonarcloud.properties`,
`scripts/build-public.mjs`, CSP 관련 HTML·검사. 전체 저장소 재감사는 하지 않는다.

1. 최신 Sonar 분석의 revision·미해결 ID·Quality Gate 실패 조건을 확보한다.
   Standard BUG/CODE_SMELL과 MQR 품질 impact를 같은 감소율로 비교하지 않는다.
2. 실제 Pages/호스트의 배포 source와 응답 정책을 확인한다. 루트 HTML을 서비스하면
   `dist/public`의 강화된 script CSP가 적용됐다고 주장할 수 없다.
3. `Handler._send`의 모든 호출부와 taint flow에서 MIME·헤더·응답 종류를 대조한다.
   ZIP 응답에는 attachment와 nosniff를 보존하며, HTML 문자열 escape로 바이너리를 손상시키지 않는다.
4. CSP 7건의 unsafe-inline과 wildcard를 실제 필요한 script/style/connect 출처와 대조한다.
   script와 style, 로컬 HTML과 공개 산출물을 구분하고 로그인·App Check·iframe·인쇄를 보존한다.
5. HTTP 3건은 loopback과 LAN을 나눠 전제·노출·실제 사용 경로를 평가한다.
   위험을 확인하면 수정하고 의도된 설계는 근거를 기록한다.
6. `experiments/hwp-export` 중 `serve.py`가 실행하는 변환기와 로컬 CLI/test를 구분해
   분석 범위를 보완한다. 새 이슈가 생기면 중요도별로 이 레일에 반영한다.
7. 완료: 각 보안 finding이 수정/근거 있는 오탐/수용 위험/미해결 중 어디에 속하는지
   코드·검증 근거를 갖춘다. 전수 재현 없이 ‘93% 오탐 제거’라고 쓰지 않는다.
   Sonar 상태 변경은 근거와 대상 ID를 기록하며 `NOSONAR`나 폴더 제외로 해결을 대신하지 않는다.

관련 검증은 보안 표적·public/CSP·필수 회귀를 선택한다. 변경 없으면 기존 성공 검사를 재사용한다.
원격 반영은 하나의 변경 묶음으로 마친 뒤 분석 완료를 확인한다. 반복 push로 분석을 다시 시작하지 않는다.
이미 push한 커밋의 문서 후속은 **새 커밋**으로 남긴다. published commit amend/force push를 기본 절차로 삼지 않는다.

  실물 XML·한글 열기·PDF 시각 검증과 JS/Python 대조를 따른다. 새 요소를 매번 재발견하지 않는다.
- **`subitems` 전용 블록**: 새 블록 하나는 생성·정규화·편집·렌더·내용 판정·발췌를 함께
  바꾸는 제품 기능이다. 현 출시 레일에 편입하지 않고, 사용자가 우선순위를 명시할 때
  별도 범위·호환·검증 계약을 먼저 정한다.
- **이미지 자유 폭**: ⚠️ **원시 CSS 문자열을 저장하지 않는다.** 채택 시 숫자 전용
  `widthPct` 를 `normBlock` 에서 **유한 정수 10..100** 으로 고정하고 기존
  `size` 를 계속 읽는 호환 계약을 먼저 확정한 뒤 구현·독립 검토한다.
- ESM 전환·프레임워크·IndexedDB/PWA·새 agent 실시간 협의 시스템은 독립 필요성이 확인될 때 후속 설계한다.
  지금의 보안·저장·출시 레일을 위한 필수 재작성으로 추가하지 않는다.
