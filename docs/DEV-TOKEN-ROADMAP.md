## DEV-1 — 필요한 코드로 바로 들어가기

AGENTS.md, reviews/README.md, INDEX의 열린 이슈와 관련 파일부터 읽는다. 지난 인계를 전부 읽지 않는다.
기존 구조 설계의 수치는 과거 기록이므로 현 코드의 script 연결·전역 의존성·수정 이력으로 대조한다.

산출물은 [CODE-MAP.md](CODE-MAP.md)다(DEV-1 완료). 파일 목록을 복제하지 말고 다음을 담는다.

- 주요 사용자 기능별 진입 파일·대표 함수/검색어·외부 모듈·직접 관련 회귀 명령.
- 로딩 순서, window에 공개된 이름, 저장/인증 상태처럼 옮기기 전 확인할 경계.
- 최근 관련 변경 이력과 읽어야 하는 코드 범위에서 뽑은 후보 최대 3개: 수정 빈도, 전역/DOM 의존,
  예상 탐색량 감소, 검사 부담. 낮은 위험의 자주 수정되는 기능을 우선하되 후보가 없으면 없다고 기록한다.
- 대표 유지보수 질문 2개를 고정하고, 현재 답을 찾는 파일·함수·읽은 범위와 기준 커밋을 짧게 남긴다.
  합성 탐색 과제임을 밝히며, 절감 효과를 만들기 위한 불필요한 제품 수정은 하지 않는다.

지도는 핵심 표 위주로 약 100줄 이내를 목표로 하되 필요한 맥락을 자르지는 않는다.
줄 번호만 믿지 않도록 함수·검색어를 함께 둔다. 변경한 기능의 항목만 이후 갱신한다.

## DEV-2 — 구현자가 다시 설계하지 않아도 되는 경계

DEV-1 지도를 확인하며 이 레일의 진행 기록에 연결할 짧은 분리 설계 문서를 만든다.
대상 함수·변경 파일, 상태 읽기/쓰기, DOM 접근, 이벤트 등록·초기화 순서, window/lexical 계약,
입출력과 오류 처리, 기존 호출부와의 연결, 공개 빌드 목록/CSP/인라인 스크립트 추출에 미치는 영향을 고정한다.
저장 데이터 형식과 계정 격리 동작을 유지한다. 구현 단계가 임의로 공개 표면을 바꾸지 못하게 한다.

관련 회귀 명령과 재현 시나리오, 실패 주입 위치·기대 실패, 추출만 되돌릴 수 있는 파일 묶음을 명시한다.
통과한 과거 검사 중 재사용 가능한 것은 커밋·환경과 함께 구분한다. 새 코드의 필수 검증을 과거 결과로 대체하지 않는다.
후보가 너무 얽혔거나 탐색량 감소가 불명확하면 **지도 유지·분리 보류**도 유효한 종료다. 이때 DEV-5로 이동한다.

## DEV-3·4 — 구현과 독립 검토

DEV-3은 설계한 한 경계만 추출한다. 새로운 전역 연결을 늘려 파일 간 왕복이 증가하지 않는지 확인한다.
설계 문서의 검사와 기존 필수 검증을 실행한다. 구조 추출에는 기존 check:fast 완료 조건을 유지하고,
serve.py로 regression-test.html, Chromium·Firefox·WebKit의 영향 경로와 기존 file:// 지원 범위를 확인한다.
공개 빌드에 새 파일이 실제 포함되고 로딩 순서·CSP가 유지되는지도 확인한다.
추가·변경 회귀는 의도적 결함에서 실제 실패해야 한다. 검사가 파일 위치에 의존했다면 검사 위치를 고치되
동작 단언을 없애거나 약화시키지 않는다. 미실행 검사가 있으면 완료로 넘기지 않고 환경·남은 명령을 인계한다.

DEV-4는 구현자와 다른 검토 주체가 실제 diff·관련 소스·증거를 대조한다. 모델 이름 변경만으로 독립성이 생기지 않는다.
동일 구현자가 다시 확인한 결과는 자체 검증으로 기록하고 독립 승인이라고 쓰지 않는다.
기존 성공 검사를 무조건 재실행하지 않되, 의심 경계는 직접 재현한다. 결함이면 이슈를 등록하고 DEV-3으로 반환한다.
수정자는 같은 이슈에 해결 근거를 남기고, 검토자는 수정 영향 범위만 재검토한다. 승인한 동일 diff를 반복 심사하지 않는다.
새 구현 인계가 필요하며 지도는 해당 항목만 갱신한다. 사용자 변경과 무관한 정리는 섞지 않는다.

## DEV-5 — 효과가 있을 때만 더 분리하기

DEV-1의 두 질문을 새 구조에서 찾아 비교한다. 모델·추론·커밋, 읽은 파일/범위, 재탐색, 수정·검증 부담을 기록한다.
이미 답을 아는 재탐색은 실제 업무와 다르므로 합성 비교의 한계를 밝힌다. 이후 실제 수정 한 건의 관찰을 더하면 좋지만,
그 일이 없다고 만들거나 기다리며 계속 토큰을 쓰지 않는다. 실제 작업 증거가 없으면 탐색 비교와 자료 대기를 구분한다.
분리 구현·검사·인계에 든 일회성 비용도 함께 판단한다. 정확한 토큰 통계가 없으면 대리 지표라고 명시한다.
계정 전체 사용량을 이 작업만의 비용으로 간주하지 않는다. 90% 절감 같은 보장이나 임의 바이트→요금 환산을 하지 않는다.

- 탐색 경로가 짧아지고 재작업·검증 부담이 수용 가능하면 현재 분리를 유지하고 다음 후보 근거를 기록한다.
- 효과가 불분명하면 분리를 더 하지 않고 지도·탐색 규칙만 유지한다. 되돌리기도 비용이므로 자동 되돌리지 않는다.
- 추가 분리 후보는 후속 목록에만 남기고 이번 레일에서는 첫 경계의 검증을 마친 후 OPS-6으로 간다.
  모호한 효과 판단은 Astra high에 좁게 인계한다. 분리를 무한 반복해 서비스 작업이 밀리지 않게 한다.
- 실제 업무 증거가 없으면 효과 확인의 한계를 적고 OPS-6으로 이동할 수 있다. 실제 절감 입증이라고 쓰지 않는다.

## OPS-6A — Gemini 후보를 배포 전에 검증 가능한 계약으로 만들기

2026-09-14 Astra 설계 및 Terra 구현 산출물: [GEMINI-STAGING-ADAPTER-DESIGN.md](GEMINI-STAGING-ADAPTER-DESIGN.md),
`worker/gemini.js`, `worker/gemini.test.mjs`. Gemini MIME 차이, thinking_tokens, 실패/잘림 처리와
test:worker 연결을 구현했다. Sol의 실제 diff·가짜 외부 경계·실패 주입 대조에서 재현된 REV-091·092는
Terra가 수정했고, Sol이 별도 probe와 Chromium regression 158/158로 독립 승인했다.
구현 완료를 연결 성공이나 production 채택으로 바꾸지 않는다.

사용자는 Gemini 사용 방향을 요청했으나 기존 레일은 OPS-10까지 Anthropic 유지였다. 이 불일치를
해소하기 위해 공급자 설계만 앞으로 이동한다. Gemini가 더 싸고 정확하다고 미리 결론 내리지 않는다.

- 현재 `worker/index.js`의 `anthropicResponse`·`aiTelemetry`와 `ANTHROPIC_KEY` 선행 검사를 대조한다.
  secret만 추가해도 전환된다고 보지 않는다. 외부 JSON, 인증·App Check, quota 예약/소비/반납,
  입력 한도, 안전 오류·로그를 유지하는 명시적 공급자 선택 경계를 설계한다.
- 정확한 Gemini 모델 ID·접근 가능성·입력/출력/생각 토큰 과금·데이터 처리 조건을 실행 시 공식 자료로
  재확인한다. 현재 4096과 새 공급자의 출력 예산 의미가 같은지 확인하고 금액 상한을 재산정한다.
  무료 티어를 보안·보존 조건까지 충족한 것으로 간주하지 않는다. 개인 자료 전송은 금지한다.
- 구현을 선택하면 응답 스키마, 잘림/안전 차단, usage 누락·생각 토큰, HTTP/네트워크 실패를 오프라인
  fixture로 검증하고 기존 Worker 회귀·실패 주입·독립 검토를 마친다. 자동 재시도·자동 fallback은 금지한다.
- Gemini 부적격/접근 불가 시 비용을 쓰지 않고 이유를 기록한다. 다른 공급자로 실호출 대상을 몰래 바꾸지 않는다.
  승인된 대안이 없으면 대기한다. Anthropic 코드는 복귀 가능하게 유지하되 이중 호출하지 않는다.

종료: 계약 설계와 선택한 구현의 검증, 정확한 호출 대상과 비용 근거가 준비됐을 때만 6B로 간다.

## OPS-6B — 배포 준비와 기존 승인 범위 재확인

기존 C/OPS-6의 승인 묶음과 일부 staging 생성은 있으나 실행 준비는 미완료다. [운영 런북](OPERATIONS-RUNBOOK.md)과
[운영 증적](SECURITY-OPERATIONS-CHECKLIST.md)의 배포 요구를 확인하고 그 요구를 이행한다.
실제 배포본과 로컬 코드의 차이, 함께 나가는 과거 보안 변경, staging/production 대상, bindings·migration,
모델·샘플률, secret 연결 여부(값은 출력하지 않음), 유효한 검사 커밋·환경, 롤백 버전을 확인한다.
운영 상태를 읽을 권한이나 정확한 대상이 없으면 확인된 범위와 미확인 항목을 구분하고 OPS-6 대기로 둔다.
Worker verifier가 의존하는 Google 프로젝트/API 접근·실제 토큰 발급 조건도 배포 전에 확인한다.
이미 생성한 staging을 먼저 재확인하고 중복 생성하지 않는다. 새 유료 가입·billing 연결·production
변경은 기존 승인에 포함되지 않는다. 승인 질문 전에 읽기 전용 확인과 준비 가능한 자료를 완성한다.

합성 테스트 자료, 호출 횟수 상한, 현재 가격과 입력/출력 한도를 근거로 한 예상 최대 비용을 적고
대상 배포·실호출·로그 관찰·설정 복원 범위를 한 번에 승인받는다. 이미 받은 해당 승인은 재사용한다.
기존 승인은 이미지 1회+문서 1회, **누적 2회·총 $1**이다. 날짜·작업·모델 전환으로 초기화하지 않는다.
실제 공급자에 보낸 실패 요청도 횟수에 포함하며 재시도하지 않는다. 호출 전 잔여 횟수와 최대 비용을
확인할 수 없으면 호출하지 않는다. 예산 알림·일일 호출 quota를 달러 단위 강제 상한으로 간주하지 않는다.
요청 이미지·프롬프트·응답 원문·UID·인증 토큰을 증적이나 로그에 복사하지 않는다.

## OPS-7 — 측정이 실제 환경에서도 동작하는지 확인

승인된 테스트 환경에서 개인정보 없는 합성 이미지와 문서로 두 경로를 확인한다.
두 호출은 연결·측정 smoke 검증이며 Gemini/Claude 품질 비교 실험이 아니다. 문서 경로 검증은
제거된 AI 문서 진입 UI의 복구를 뜻하지 않는다([제품 범위](AI-DOCUMENT-SCOPE.md)).
인증 거절·quota·실패 처리와 event=ai_usage의 task, input_tokens, output_tokens, stop_reason,
duration_ms, outcome, http_status를 검증한다. 로컬에서 이미 주입한 실패를 실제 유료 호출로 불필요하게 반복하지 않는다.
생산 배포는 별도 대상 승인 후 실행한다. 승인 환경의 검증을 생산 전체 검증으로 표현하지 않는다.

현재 저장소의 관찰 설정은 head_sampling_rate=0.1이다. 로컬 이벤트 1회와 플랫폼 저장 표본을 구별한다.
한두 번 로그가 없다고 호출을 반복하지 않는다. 실시간 로그 또는 staging 임시 샘플률 조정은 도구가 수집하는
원문·헤더 경계를 먼저 확인하고 OPS-6 승인 묶음에 포함한다. 운영 100% 수집으로 몰래 바꾸지 않는다.
검증한 배포 버전·설정 복원·결과와 미확인 사항을 기록한다. 필요한 검증이 끝나지 않으면 OPS-7 대기다.

2026-09-14 실환경 실행에서는 staging `32c03142-05f8-4647-89bb-8307d0009f89`에만 100% 로그를
적용했다. 무효 Firebase 토큰은 401로 거절됐고, 유효한 임시 익명 토큰 요청은 App Check
`monitor` 실패를 기록한 뒤 quota를 각각 reserve·consume했다. 합성 이미지와 문서 provider 시도는
각 1회였으며 둘 다 `ai_usage`의 `outcome=request_error`, 토큰·HTTP 상태 미확인으로 502가 됐다.
재시도하지 않았고 `eeb668aa-1f81-4fc4-bb6b-a8546176613c`에서 10% 로그를 복원했다. 성공 표본과
provider HTTP 응답이 없으므로 OPS-8로 넘기지 않는다. 다음 작업은 secret 원문이나 요청을 출력하지 않는
오프라인/설정 진단이며, 원인이 고쳐져도 새 실호출 승인을 받기 전에는 호출하지 않는다.

2026-09-14 Terra medium은 이 실패를 특정 credential이나 Google 장애로 단정하지 않았다. 대신 Worker가
secret 저장/입력에서 생길 수 있는 끝 공백·줄바꿈을 API header 전에 제거하고, provider redirect를
`follow`하지 않는 `manual`로 바꿨다. 따라서 redirect는 API key를 다른 origin에 전달하지 않고 안전한
`http_error` 상태로 기록된다. whitespace-only key는 quota 전에 503으로 거절한다. 새 회귀는 padded key,
302 redirect, 두 설정을 각각 약화시키는 red mutation을 포함한다. 실제 Gemini 호출은 0회 추가했고 다음은
Sol medium의 독립 검토다.

Sol medium은 구현 테스트와 별도로 trim 제거 변이를 주입해 whitespace-only key가 quota 전 503 대신
provider 경로 502로 깨지는 것을 확인했다. 현 구현에서는 padded key 정규화, manual redirect의 단일
fetch와 302 `http_error`, telemetry·URL의 key/원문 비노출, Worker 전체 계약이 통과했다. 수정 자체는
승인하되 실환경 성공 증거가 없으므로 `REV-2026-093`은 `in-progress`로 유지한다. 다음 Terra medium은
staging 이미지 1회·문서 1회, 재시도 0회, 합계 최대 $1의 새 승인을 받은 뒤에만 배포·재검증한다.

## OPS-8 — 실제 서비스 비용·품질 근거 모으기

개인 식별자 없는 메타데이터에서 작업별 총 표본 수·성공/실패 수·토큰 미확인 건수, 입출력 토큰 중앙값/p95,
max_tokens 중단 비율, 응답 시간, 관찰 기간·모델·샘플률을 정리한다. 실패 표본도 포함한다.
표본 수가 적으면 p95나 낮은 실패율을 신뢰할 수 없음을 밝힌다. 30~50건을 충분성 기준으로 고정하지 않는다.
이번 2회는 작업별 1회이므로 개별 관측값만 적는다. p95·실패율·일반 품질·절감률 판단에 사용하지 않는다.
표본 총합을 청구액으로 쓰거나 누락 토큰을 0으로 간주하지 않는다. 실제 절감은 검증 전까지 주장하지 않는다.
현재 Worker는 자동 재시도와 재시도 연결 ID가 없으므로 사용자 재시도별 비용을 직접 계산할 수 없다.

일부 관측이 있어 한계를 분석할 수 있으면 자료 부족에 따른 유지 판단을 OPS-9에 넘길 수 있다.
관측 데이터가 전혀 없거나 접근할 수 없으면 OPS-8 데이터 대기다. 요약기·대시보드·추적 ID를 임의 추가하지 않는다.
데이터를 채우려 유료 호출을 늘리거나 사용자 요청 없이 모니터링을 예약하지 않는다.

## OPS-9 — 출력 한도는 이익이 있을 때만 변경

Astra high가 OPS-8 자료로 판단한다. 출력 상한은 선결제 토큰이 아니므로 같은 길이의 응답에는 절약이 없을 수 있다.
관측 근거가 부족하거나 순이익이 없으면 **두 경로 4096 유지**를 결정하고 이 단계는 완료한다.
이는 절감 성공 선언이 아니다. 자료가 없다며 OPS-7의 필수 실환경 검증을 생략해서도 안 된다.

변경 근거가 있으면 같은 합성 표본의 문항·수식 정확도, 출력 완전성, JSON 성공률, 실패 포함 비용과
잘림·재시도 위험의 비교 기준 및 허용 한도를 먼저 고정한다. Terra medium은 두 작업의 max_tokens만
분리·변경하고 quota·프롬프트·공급자를 동시에 바꾸지 않는다. 실호출은 승인 예산 안에서만 실행한다.
관련 Worker 회귀·실패 주입과 Sol medium의 독립 검토를 마친 뒤 기록한다. 이익이 사라지면 유지로 판단한다.

## OPS-10 — 공급자 판단과 비용 검증 마감

Astra high가 6A의 계약과 OPS-7~9 결과로 Gemini의 staging 연결 성공 여부, 제품 채택 근거와 미확인
품질을 분리한다. **2회 성공만으로 Gemini 우위·production 채택을 선언하지 않는다.** 근거가 부족하면
채택 보류·추가 비교에 필요한 자료/예산을 기록하고 비용 판단은 마감할 수 있다. 연결 구현을 반복하지 않는다.
아래 비교가 필요할 때만 별도 범위·예산으로 진행하며, 기존 2회/$1 승인을 추가 A/B 호출에 쓰지 않는다.

1. Astra high가 후보별 현재 계약·입력 보존·학습 이용·삭제·처리 위치 등 개인정보 적격성과 이미지 입력 지원을
   확인하고 동일한 합성/권리 확보 표본·정답·채점법·모델 ID·비교 예산을 설계한다. 적격 판정 전 개인 자료를 전송하지 않는다.
2. 후보/예산 승인 후 Terra medium이 정확도·JSON 성공률·속도·실패 포함 비용을 비교한다.
   가입·계약·키 발급·실호출을 승인 없이 수행하지 않는다. 채택 이득이 없으면 현 공급자 유지로 완료한다.
3. 이득과 적격성이 확인되고 사용자가 연결을 승인하면 Astra high가 Worker 내부 어댑터 하나의 경계를 설계하고
   Sol medium이 구현한다. 외부 JSON·인증·quota·안전 로그 계약 및 Anthropic 복귀 경로를 유지한다.
   자동 재시도·자동 fallback으로 복수 공급자 비용이 생기는 기능은 포함하지 않는다.
4. 구현자와 다른 검토 주체(Astra high 권장)가 관련 회귀·실패 주입과 복귀 경로를 독립 검토한다.
   실제 배포가 필요한 변경은 OPS-6·7의 대상 승인·검증 기준을 같은 레일에서 적용한 뒤 마감한다.

## REL-11 — 개인용 웹 제품의 약속부터 고정

감수서에 따른 **제안 범위**는 한국어 개인 교사의 문제집 편집·사진 인식·브라우저 인쇄/HWPX다.
학원/팀 협업·좌석, 다국어 완성, 문제은행은 제외 후보이며 실제 정책과 UI 반영 전에 확정한다.
`team`/`academy` 플랜 라벨만으로 협업 제품이 있다고 보지 않는다. 개인 사용자도 다중 기기 충돌은 보호해야 한다.
Typst 정밀 조판은 로컬 확장 기능으로 구분하고 웹 핵심 경로가 서버 없이 어디까지 되는지 표로 확인한다.
서버 조판 제공을 선택할 때만 폰트/템플릿 권리·격리·용량/시간 제한·배포비용을 별도 설계한다.
AI 문서 진입 UI는 기존 제외 결정을 보존한다. 완료 기준은 지원 환경·제외 기능·유료 약속을 한곳에 문서화하는 것이다.

## REL-12 — 데이터 손실 위험부터 줄이기

- `mergeSets`/`mergeMocks`의 클라이언트 시각 기반 전체 문서 선택을 개선한다. 서버 revision/CAS 등
  최소 충돌 검출과 충돌 사본·export를 설계한다. 시각만 서버로 옮기는 것은 충돌 해결이 아니다.
  두 기기 동시 수정, 시계 역전, 오프라인 재접속, 삭제 tombstone, 계정 전환을 검증한다.
- 문제집 문서는 현재 전체 problems 배열을 쓴다. 기존 저장 실패 안내·로컬 보존과 모의고사의 900KiB
  사전 검사부터 재사용한다. Firestore 크기 계산 여유를 둔 문제집 사전 차단·분할 안내·export를 마련하고
  경계 크기·이미지 이관 실패·배치 일부 실패에서 저장 완료로 오인시키지 않는지 확인한다.
- subcollection 전환은 필수 선결정이 아니다. 실제 대표 자료의 크기/쓰기량이 위 방어로 수용되지 않을
  때만 점진 이관·구버전 호환·rollback을 설계한다. CRDT/협업 전체 재설계도 이번 필수 범위가 아니다.
- 백업 복구를 격리 자료로 검증하고 RPO/RTO·책임자를 남긴다. 관련 회귀와 실패 주입·독립 검토 후 완료한다.

## REL-13 — 베타를 판단할 증거와 보안

기존 CI·회귀·HWPX JS/Python 대조를 먼저 재사용한다. 분석본에 없었다는 이유로 테스트를 새로 만들지 않는다.
실제 브라우저에서 로그인→저장→사진 AI→편집→인쇄/HWPX→재로그인/복구를 확인한다. 실제 Safari/iOS,
한글에서의 출력 확인, 글꼴 없는 환경과 CI의 visual/템플릿 검사 skip을 별도로 기록한다.
REV-075는 실계정 복귀 재현/미재현 근거로 처리하고, REV-074가 Git/CI를 막으면 같은 이슈에 근거를 갱신한다.

최소 제품 관측은 생성/가져오기·AI 결과·저장 실패/충돌·내보내기 성공을 대상으로 목적·보존·접근자를 먼저
설계한다. 원문·UID·토큰을 수집하지 않는다. 사용자 추적/외부 분석 SDK는 자동 추가하지 않으며, 리텐션이
필요하면 별도 개인정보 설계를 한다. 서비스 `ai_usage`만으로 제품 사용성·리텐션을 안다고 쓰지 않는다.

[보안 운영 체크리스트](SECURITY-OPERATIONS-CHECKLIST.md)의 미완료 게이트를 유지한다. staging에서
실제 App Check 토큰 발급→monitor 관찰→Worker/Firestore/Storage 각각 enforce와 정상/거절을 검증한다.
등록 화면만으로 완료 처리하지 않는다. production 보안 전환·호스트 이전은 별도 대상 승인까지 대기한다.
비공개 베타라도 실제 사용자 초대는 개인정보·지원·복구·비용 보호와 대상 승인을 확인한 뒤에만 한다.

## REL-14·15 — 결제 구현과 출시 판정

[결제 구조](BILLING-ARCHITECTURE.md)를 재사용하고 REL-11에서 확정한 개인 상품만 구현한다.
PG/사업 정보·가격·환불 정책처럼 사용자 결정이 필요한 항목은 임의 생성하지 않는다. 서명 검증·중복/역순
webhook·서버 금액 검증·구독 상태·해지/환불·권한 회수·토큰 갱신을 sandbox에서 검증한다.
저장량/좌석 한도를 판매한다면 서버 강제가 선행돼야 한다. 포털 URL·claim 라벨만 채워 결제 완료로 처리하지 않는다.
법무·지원 채널·예산 알림/실제 차단·장애/삭제 대응은 [출시 게이트](COMMERCIAL-LAUNCH.md)에 증적을 연결한다.

REL-15는 독립 검토자가 실제 release 산출물·환경과 코드 검사/콘솔 증적을 대조한다. production에 대해
미확인인 항목은 준비 완료로 표시하지 않는다. 현재 8개 `check:launch` 실패를 문구 삭제나 staging 설정
대입으로 숨기지 않는다. 검사가 초록이어도 운영 증적·결제/복구 E2E·독립 승인이 없으면 출시 불가다.
**production 배포·설정 변경·결제 공개는 이번 2회/$1 승인 밖이며 별도 승인까지 실행하지 않는다.**

## 완료·대기 기준

- 개발: 탐색 지도와 첫 경계의 구현·검토 또는 근거 있는 분리 보류 결정, 효과 비교·한계를 기록했다.
- 서비스: 승인된 환경에서 측정 검증과 설정 복원을 완료했고, 표본 분석과 출력 한도·공급자 유지/변경 판단이 끝났다.
- 선택한 변경은 필요한 회귀·독립 검토·승인된 배포 검증까지 끝나야 한다. 후보를 검토하지 않고 채택 완료라고 쓰지 않는다.
- 승인·환경·데이터가 없으면 **통합 완료가 아닌 해당 단계 대기**다. 완료한 부분·남은 조건·담당 모델을 현재 위치에 적는다.
  대기 중 독립적으로 준비 가능한 문서·분석만 진행하며, 뒤 단계의 선행 조건을 건너뛰지 않는다.
- DEV·OPS 조건 충족은 **비용 검증 구간 완료**이며 REL 출시 준비 완료와 구별한다.
- REL-11~15의 코드·운영 게이트와 독립 검토까지 충족해야 출시 준비 완료다. 미확인 승인/계약/환경은
  해당 단계 대기로 남긴다. 준비 완료도 production 공개 실행이나 비용 절감률 보장을 뜻하지 않는다.
