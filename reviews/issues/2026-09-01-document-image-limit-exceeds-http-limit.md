# 범용 문서가 허용한 큰 그림을 HTTP 상한이 거절한다

- ID: `REV-2026-014`
- 날짜: `2026-09-01`
- 보고자: `Codex`
- 상태: `resolved`
- 심각도: `P2`
- 영향 영역: `server`
- 관련 인계: `HANDOFF-2026-021`

## 요약과 영향

범용 문서 계약은 원본 그림을 최대 4MiB까지 허용하지만, `/document-hwpx`의 HTTP 본문 상한은
4MiB다. 그림은 base64라 약 4/3로 커지므로 약 3MiB를 넘는 정상 그림부터는 계약 검증을
통과해도 서버 입구에서 413으로 거절된다. UI와 계약이 약속한 최대 크기를 실제로 사용할 수 없다.

## 재현 절차

1. PNG 헤더가 유효한 4,194,304바이트 그림을 base64 인코딩해 `image` 블록에 넣는다.
2. `document_schema.validate()`를 실행한다.
3. `{ "document": … }`로 JSON 인코딩한 뒤 `/document-hwpx`에 POST한다.

## 기대 결과 / 실제 결과

- 기대: 계약이 허용한 최대 그림은 `/document-hwpx`로 전송·조판된다. 또는 계약 단계에서
  실제 전송 한도보다 큰 그림을 명확히 거절한다.
- 실제: 계약은 통과하지만 JSON 본문이 5,592,501바이트가 되고 `serve.py`의
  `MAX_BODY = 4 * 1024 * 1024`에 걸려 변환기 전 413이 된다.

## 근거

- `document_schema.MAX_IMAGE_BYTES`는 4,194,304이다.
- `serve.py`의 POST 공통 상한은 4,194,304이다.
- 2026-09-01 재현: 4MiB PNG 표본을 계약이 받아들였고, JSON 본문은 5,592,501바이트였다.

## 제안

`MAX_IMAGE_BYTES`를 JSON·문서 래퍼 오버헤드까지 고려한 약 3MiB 이하로 낮추거나,
`/document-hwpx`에만 제한된 상향 본문 상한을 둔다. 어느 쪽이든 경계 크기 통합 검사를 넣어
계약과 HTTP 경계가 다시 어긋나지 않게 한다.

    남겼다 — `MAX_BODY` 를 바꾸면 이 값도 함께 봐야 한다.

    잡힌다(413 이면 연결이 끊겨 Broken pipe 로 오므로, 그 경우도 원인을 밝히는 메시지로
    바꿔 잡는다).
  - **검증**: 상한을 4MiB 로 되돌려 검사가 실패하는 것을 확인한 뒤 원복했다.
