# 원격 데이터 삭제 실패 뒤에도 계정 삭제를 성공 처리함

- ID: `REV-2026-001`
- 날짜: `2026-08-27`
- 보고자: `Codex`
- 상태: `resolved`
- 심각도: `P1`
- 영향 영역: `index`
- 관련 인계: `HANDOFF-2026-001`

## 요약과 영향

Storage 목록 조회나 사용자 Firestore 문서 삭제가 실패해도 계정 삭제 절차는 Auth 계정을
지우고 성공 메시지를 띄운다. 남은 Storage 이미지나 구버전 `users/{uid}` 문서는 더 이상
사용자가 인증해 지울 수 없어, '계정과 모든 데이터를 삭제했다'는 약속과 달라진다. 다운로드
URL이 이미 외부에 남아 있다면 Storage 토큰 URL도 계속 유효할 수 있다.

## 재현 절차

1. 별도 Firebase 테스트 계정에 이미지와 문제집을 만든다.
2. 재인증 후 Storage의 `users/{uid}/images`에 대한 `listAll()`이 네트워크·권한 오류를
   내도록 만들거나, 사용자 문서 `users/{uid}` 삭제를 실패시킨다.
3. 데이터 관리에서 계정 삭제를 끝까지 진행한다.

## 기대 결과 / 실제 결과

- 기대: 원격 데이터 삭제가 완전히 확인되지 않으면 Auth 계정을 남기고, 실패 사실과 재시도
  방법을 보여 준다.
- 실제: `wipeStorageImages()`는 목록 조회 실패를 `-1`로만 돌려주고, 호출부는 `failed > 0`
  조건에서 이를 실패로 보지 않는다. 사용자 문서 삭제 오류도 로그만 남긴 뒤 Auth 삭제까지
  진행한다. 반환값 `imagesFailed: -1`은 UI에서 `> 0`이 아니므로 성공 메시지가 표시된다.

## 근거

- `index.html:2589-2601` — `listAll()` 예외를 `-1`로 변환한다.
- `index.html:2691-2709` — 그 반환값을 중단 조건으로 쓰지 않고 문제집·Auth 삭제를 계속한다.
- `index.html:2697-2698` — 사용자 문서 삭제 오류를 삼킨다.
- `index.html:2711-2712`와 계정 삭제 UI — `-1`은 실패 개수로 표시되지 않는다.

운영 데이터를 지우지 않기 위해 실제 계정 삭제는 실행하지 않았고, 위 예외 경로를 코드로
추적해 재현했다.

## 제안 (선택)

계정 삭제에서는 Storage 목록 실패, 개별 이미지 삭제 실패, 사용자 문서 삭제 실패를 모두
치명적 실패로 취급해 Auth 삭제 전에 예외를 던진다. `-1` 같은 숫자 sentinel 대신
`{listed:false, failed:n}`처럼 상태를 분리하면 성공 처리 실수를 막을 수 있다. 문제집 전체
삭제도 최소한 '이미지가 남았다'는 성공 아닌 결과를 분명히 보여야 한다.

  실제 Firebase 계정·Storage 삭제는 사용자 데이터를 보호하기 위해 실행하지 않았다.
