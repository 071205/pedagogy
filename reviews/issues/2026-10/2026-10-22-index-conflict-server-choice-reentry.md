# 서버본 선택 뒤 재진입하면 저장 보류와 초안 사본이 다시 생긴다

- ID: `REV-2026-138`
- 날짜: `2026-10-22`
- 보고자: `Codex`
- 상태: `resolved`
- 심각도: `P1`
- 영향 영역: `index`
- 관련 인계: `HANDOFF-2026-196`

## 요약과 영향

다른 충돌 초안 사본이 앞에 삽입되어 원래 권의 로컬 index와 서버 order가 달라지면, **계정 저장본 쓰기**가 성공한 뒤에도 재진입 때 같은 권이 no-base 보류로 돌아가고 새 사본이 생긴다. 원본 유실은 확인되지 않았지만 사용자가 완료한 선택이 유지되지 않고 사본이 누적된다. 최초 다섯 no-base 발생 원인 전체를 이 결함으로 단정하지 않는다.

## 재현 절차

1. 두 권의 충돌을 만들고 앞 권의 초안 사본 때문에 뒤 권의 로컬 순서가 서버 order와 달라지게 한다. 사본은 운영 확인과 같이 계정 ACK까지 완료한다.
2. 뒤 권에서 확인한 **계정 저장본 쓰기**를 선택한다. 화면에서는 해당 보류가 해제된다.
3. 로컬 본문/동기화 메타데이터를 다시 읽고 서버 snapshot 병합·기준 복원·저장을 수행한다.
4. 수정 전에는 뒤 권이 다시 보류되고 사본이 중복 생성된다.

## 기대 결과 / 실제 결과

- 기대: 사용자가 선택한 서버 본문과 기존 초안 사본을 보존하고, 재진입 후에도 선택 완료가 유지된다.
- 실제: 운영에서 보류 3→2→1→0을 확인한 뒤 새로고침하자 같은 세 권이 다시 보류됐다. 전체 권 수는 23→26, 초안 사본은 5→8이 됐다. 새 세 사본에는 **이 기기에만 보존됨**이 표시됐다.

## 근거

- `index.html`의 `chooseServerVersion()`은 선택한 서버본을 현재 index에 두고 index/order가 다르면 영속 `setSyncBase`를 삭제했다. 재진입 후 순서가 다른 권은 새 ACK 기준을 복구하지 못해 `writeCloudSnapshot()`에서 no-base로 분류된다.
- `scripts/check-set-revision-cas.mjs`의 `B4 다른 충돌 사본이 순서를 밀어도 서버본 선택 뒤 재진입에 재충돌하지 않는다`가 수정 전 실제 브라우저에서 실패했다. 초기 하네스는 앞 사본 삽입 후 기존 사본의 순서 ACK를 생략해 별도 사본 충돌도 만들었다. 운영 전제처럼 사본 모두 ACK한 재현으로 보정한 뒤 표적 방어 제거로 원래 권의 재충돌을 다시 확인했다.
- 운영 현재 상태: 원의 방정식/도형의 이동/집합 세 권 보류, 26권. 원래 초안 다섯 JSON은 다운로드 폴더에 보존, 원래 계정 사본도 유지했다. 재현을 위해 기존 운영 코드에서 선택을 반복하지 않는다.
- 세션 자료: `/private/tmp/rev137-fix-2026-10-22/rev138-{baseline-red,cas-normal-red,mutation-control}.log`, `rev138-operational-holds.png`. 임시 자료는 정리될 수 있으므로 재현 검사와 인계를 영구 근거로 삼는다. 사용자 본문/계정 식별자는 저장소에 넣지 않았다.
