# tombstone만 남은 경우 오래된 로컬 문제집이 다시 저장될 수 있음

- 상태: `resolved`

- 관련 인계: `HANDOFF-2026-001`

## 요약과 영향

클라우드에 삭제 tombstone만 있고 이 기기에 오래된 로컬 사본이 있는 경우, 초기 병합은 올바르게
빈 결과를 내지만 `loadSets()`가 이를 '클라우드가 비었다'고 간주해 오래된 로컬 사본을 다시
불러온다. 초기 snapshot이 오기 전에 사용자가 수정하면 로컬 수정 시각이 tombstone보다 새로워져
삭제 방어가 풀리고, 이후 저장이 tombstone을 일반 문서로 덮어쓴다.

## 재현 절차

1. 기기 B에 문제집 A의 오래된 로컬 사본을 둔 채 오프라인으로 둔다.
2. 기기 A에서 '모든 문제집 삭제'를 실행해 A에 대해 `deleted:true` tombstone만 남긴다.
3. 기기 B를 온라인으로 전환해 로그인한다. Firestore 읽기는 tombstone을 받지만 병합 결과는
   빈 배열이다.
4. 기기 B에서 초기 `onSnapshot` 콜백 전에 A를 열어 수정·저장한다.
5. 수정 시각이 tombstone보다 새로워져 삭제 콜백이 A를 지우지 않고, 저장 경로가 A를
   `deleted:false` 문서로 다시 쓴다.

## 기대 결과 / 실제 결과

- 기대: 성공한 클라우드 읽기에서 tombstone을 확인했다면, 오래된 로컬 사본을 UI나 저장 경로에
  다시 넣지 않는다.
- 실제: `mergeSets()`는 tombstone으로 로컬 사본을 제외하지만, `merged.length === 0`이면
  `loadSetsLocal()`이 이전 사본을 그대로 복원한다. 이 상태에서 새 수정 시각을 찍으면
  `watchCloud()`의 tombstone 제거 조건도 통과하지 못한다.

## 근거

- `index.html:2071-2090` — tombstone이 로컬 사본을 병합 결과에서 제외한다.
- `index.html:2137-2158` — 병합 결과가 비면, 성공한 클라우드 읽기 뒤에도

- `index.html:2170-2201` — tombstone은 로컬 수정 시각이 더 최신이면 제거하지 않으며,
  첫 snapshot 전에는 UI가 이미 오래된 사본을 보여 줄 수 있다.
- `index.html:2408-2438` — 새 로컬 변경은 삭제된 문서를 다시 일반 문서로 저장할 수 있다.

## 제안 (선택)

성공한 클라우드 읽기에 tombstone이 하나라도 있으면, 병합 결과가 비어도 그것을 권위 있는
상태로 처리한다. 이 경우 관련 로컬 사본을 즉시 제거·저장하고, 빈 라이브러리를 보여 준다.
클라우드 문서가 정말 하나도 없는 새 계정일 때만 기존 로컬 사본을 업로드 후보로 삼는다.
이 시나리오를 두 탭/두 로컬 캐시로 고정한 회귀 검사도 추가한다.
