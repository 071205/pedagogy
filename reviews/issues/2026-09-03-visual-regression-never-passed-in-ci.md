## 요약과 영향

`npm run test:visual` 은 `index.html` 의 인쇄 결과를 기준 시각본과 픽셀로 견준다.
기준본은 **맥에서** 만들어 커밋돼 있고 CI 는 **리눅스**다. 글리프 래스터화가 OS 마다
달라 쪽 전체의 **1.843%** 가 다르게 나온다 — 허용치 0.5% 를 넘는다.

그래서 이 검사가 들어온 `8d89d53`(2026-08-28) 이후 **CI 19회가 모두 실패**했다.
한 번도 초록불이 된 적이 없다. 결과적으로 아무도 CI 를 보지 않게 되는 상태였고,
`verify` 작업이 실패로 끝나 그 뒤 단계(Firebase 규칙 검사·serve.py 문법·공백 검사)는
**아예 실행되지 않았다.**

그리고 더 나쁜 것이 있다. 허용치를 넘긴 것과 별개로, **이 검사는 정작 잡아야 할 것을
잡지 못한다.** A4 한 쪽은 대부분 흰 여백이라 국소 변화가 전체 비율에 묻힌다.

## 재현 절차

```bash
gh run list --workflow=Verify --limit 40 --json conclusion | jq '[.[]|select(.conclusion=="success")]|length'
# → 0
gh run download <run-id> -n visual-regression-diff
```

같은 쪽으로 직접 재어 본 값(맥 기준본 기준):

|---|---|

| 본문이 3px 밀렸을 때(진짜 배치 회귀) | 1.492% |
| 본문이 1px 밀렸을 때 | 1.343% |
| **글줄 하나가 통째로 사라졌을 때** | **0.038%** |
| 낱말 하나가 사라졌을 때 | 0.006% |

## 기대 결과 / 실제 결과

- 기대: 인쇄 결과가 달라지면 빨간불, 아니면 초록불.
- 실제: **환경이 다르면 늘 빨간불**(1.843% > 0.5%)이고, **글줄이 사라져도 초록불**
  (0.038% < 0.5%)이다. 잡음이 신호보다 크다.

## 근거

- `scripts/visual-regression.mjs` 의 판정은 `pixelmatch` 가 센 '다른 픽셀 수 ÷ 쪽 넓이'
  하나뿐이고 허용치는 0.5% 였다.
- 타일별 최댓값으로 바꿔도 마찬가지다(플랫폼 잡음 25.1% vs 글줄 사라짐 5.6%) —
  글자 하나하나가 달라지는 차이는 **어떤 픽셀 비교로도** 내용 변화와 갈라낼 수 없다.
- CI 아티팩트의 차이 그림을 보면 상자·괘선·단 구분선은 그대로이고 **글자만 전부**
  붉게 칠해져 있다. 배치가 아니라 래스터화 차이라는 뜻이다(먹 픽셀 총량 차 0.80%,
  글줄 위치 차 ≤2px).

## 제안 (선택)

두 가지를 나눠 봐야 한다.
1. **같은 OS 끼리만 견줄 수 있다.** 기준본을 OS 별로 두고, 그 OS 의 기준본이 없으면
   건너뛴다(없는 것을 있는 척 재지 않는다). 저장소가 `test:hwpx-parity` 를 CI 에서
   뺀 것과 같은 결정이다.
2. **판정 기준을 바꿔야 한다.** 쪽 전체 비율 대신 **가로줄마다 글자가 얼마나 있는지**를
   견주면 국소 변화가 묻히지 않는다.
