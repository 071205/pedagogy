# 인쇄의 선지 넘침 보정이 **재는 대상이 틀려** 한 번도 걸리지 않는다

- ID: `REV-2026-104`
- 날짜: `2026-09-22`
- 보고자: `Claude / Opus 5`(다른 세션의 에이전트 신고에서 출발 — 실측으로 재확인)
- 상태: `resolved`
- 심각도: **`P1`** — 사용자에게 **잘린 시험지**가 그대로 인쇄된다
- 영향 영역: `index.html`(`fitPrintDoc` · 선지 CSS)
- 관련: `REV-2026-078`(넘치는 표 — **같은 종류의 결함**, 그때는 표만 고쳤다)

## 요약

`fitPrintDoc()` 의 **(1) 가로 선지 넘침**과 **(1-b) 개별 선지 축소**가 **둘 다** 한 번도
발동하지 않는다. 배치를 빠뜨려서가 아니라 **재는 대상이 틀려서**다.

```js
// index.html:8014 — (1)
const s0=slotOf(ch);
return ch.getBoundingClientRect().right > s0.getBoundingClientRect().right+1;
```

`.choices.horizontal` 은 `grid-template-columns:repeat(5,minmax(0,1fr))` 이고
`.choices .choice{min-width:0}` 이다. **`minmax(0,…)` 와 `min-width:0` 은 "칸보다 커지지
말라" 는 뜻이므로 컨테이너는 slot 을 절대 넘지 않는다.** 실제로 넘치는 것은 셀 안의
`.choice .text` 이고, 그것은 `index.html:1090` 의 `overflow-x:hidden` 이 **조용히 잘라낸다.**

(1-b) 도 같은 이유로 죽어 있다. `.choice` 의 `scrollWidth` 를 보는데, 그 안의 `.text` 가
`overflow-x:hidden` 인 flex 아이템이라 **자동 최소 크기가 0** 이 되어 눌린다 — 그래서
`.choice` 역시 자기 칸을 넘지 않는다.

⚠️ 소스 주석은 **"새 배치를 여기 빼먹지 말 것 — 넘쳐도 보정이 안 걸려 조용히 잘린다"**
고 적고 있다. 경고는 맞았지만 **원인이 배치 목록이 아니었다.** 목록을 아무리 늘려도
판정이 컨테이너인 한 전부 false 다.

## 재현 — 실측

수식 선지(`$\dfrac{3\sqrt2}{4}(a^2+b^2)$` 류) 5개 × 10문항을 5열로 두고 실제 인쇄 경로
(`buildPrintDoc` → `#printDoc.measuring` → `fitPrintDoc`)를 태웠다.

| 재는 것 | 넘쳤다고 판정한 수 |
|---|---|
| **현행 (1)** — `.choices` 컨테이너 vs slot | **0 / 10** |
| **현행 (1-b)** — `.choice` 의 `scrollWidth` | **0 / 50** |
| 제안 — `.choice .text` 의 `scrollWidth` | **10 / 10** |

보정 전 잘린 선지 **50개 → 보정 후 50개** · `choices--wrap` 적용 **0건**.
(다른 세션의 보고자도 자기 집합에서 42 → 42 · 0건으로 같은 값을 얻었다.)

## 배치별 실측 — '한 단계' 로는 지면이 낭비된다

같은 표본을 배치만 바꿔 다시 쟀다(`.pq` 안, 인쇄 단 폭 기준).

| 배치 | 남은 잘림 | 선지 블록 높이(중앙값) |
|---|---|---|
| 5열 (현행) | 50 | 44px |
| **`choices--wrap`** (지금 유일한 완화 수단) | 0 | **130px** |
| 3열 (`cols3`) | 5 | **87px** |
| 2열 (`cols2`) | 0 | 130px |
| 세로 (`vertical`) | 0 | 217px |

⚠️ **`choices--wrap` 은 2열과 정확히 같은 높이를 낸다.** `repeat(auto-fit,minmax(34mm,1fr))`
인데 2단 시험지의 한 단이 84.5mm 라 **항상 2열로 떨어지기 때문**이다. 즉 지금 설계는
"3열이면 충분한 문항" 을 위한 자리가 **아예 없다** — 3열이면 블록당 **43px** 를 아낀다.

## 함께 드러난 것 — 두 가지

⚠️ **`paired` 는 어느 보정도 받지 못한다.** (1) 의 선택자 목록에는 들어 있지만
`.choices.paired` 는 **`display:flex;flex-direction:column`** 이라
`choices--wrap` 의 `grid-template-columns` 가 **아무 일도 하지 않는다.** (1-b) 는
`.choice` 를 찾는데 `paired` 에는 `.choice` 가 없다(`.pair-row`/`.pair-cell` 이다).
**다만 넘침 자체를 재현하지 못했다** — 긴 적분식 12칸을 넣어도 최대 **68.2px 여유**로
전부 들어갔다(`pairs-2` 의 `1fr` 트랙이 넉넉하다). **재현이 없으므로 이번에 고치지 않는다.**
소스 주석의 "`paired` 는 가로로 넘치기 더 쉽다" 는 **근거 없는 통설**이다.

⚠️ **그림 선지(`.choice--img`)는 사다리에 넣어도 무해하지만 넣을 필요가 없다.**
`.choice--img .text img{width:100%}` 라 칸에 맞춰 줄어들고 `overflow-x:visible` 이라
잘리지도 않는다 — 구조적으로 가로 넘침이 없다.

## 고침 설계 (합의됨 — Claude ↔ Codex 1왕복)

### ① 판정 대상을 셀 내용으로 옮긴다

```js
const cellsOf = ch => [...ch.querySelectorAll(".choice:not(.choice--img) .text")];
const over = el => el.scrollWidth - el.clientWidth > 2;   // 허용오차 2px
```

⚠️ **(1-b) 의 축소율도 `.choice` 가 아니라 그 `.text` 로 계산해야 한다** — 위와 같은
이유로 `.choice` 의 `scrollWidth` 는 언제나 `clientWidth` 와 같다.

### ② `choices--wrap` 한 단계 대신 **사다리**로 내린다

사용자가 저장한 배치를 **출발점**으로 삼고 **열 수만 줄인다. 절대 늘리지 않는다.**

| 저장된 배치 | 내려가는 길 |
|---|---|
| `horizontal`(5열) | 5 → `cols3` → `cols2` → `vertical` |
| `cols3` | 3 → `cols2` → `vertical` |
| `cols2` | 2 → `vertical` |
| `vertical` | 그대로 — 넘치면 ③ 개별 축소만 |
| `paired` | **사다리에 넣지 않는다**(구조가 다르고 재현도 없다) |

⚠️ **새 CSS 가 없다.** 이미 있는 배치 클래스를 인쇄본에서 갈아 끼우는 것뿐이다.
⚠️ **`choices--wrap` 클래스는 지운다** — 2열과 같은 결과를 내면서 `cols2` 와 달리
칸 수가 단 폭에 따라 흔들린다. 사다리가 그 자리를 정확히 대신한다.

### ③ 그래도 넘치면 지금의 개별 `scale()` 축소 (변경 없음, 측정 대상만 `.text`)

### ⚠️ 읽기·쓰기 분리를 깨지 말 것 — 사다리는 **요소별이 아니라 단계별**이다

이 저장소는 "요소마다 읽고 쓰기를 번갈아 하면 300문항에서 1.6초" 를 이미 실측했다.
**블록 하나를 사다리 끝까지 끌고 내려가면 안 된다.** 단계마다 전부 읽고 전부 쓴다:

```
[모든 5열 읽기] → [넘친 것만 한꺼번에 3열로 쓰기]
[모든 3열 읽기] → [넘친 것만 한꺼번에 2열로 쓰기]
[모든 2열 읽기] → [넘친 것만 한꺼번에 세로로 쓰기]
[모든 .text 읽기] → [축소를 한꺼번에 쓰기]
```

강제 레이아웃이 **문항 수가 아니라 사다리 높이(4)에 비례**한다.
⚠️ **한 시점에 배치 클래스는 하나만 남겨야 한다** — `vertical` 과 `horizontal` 이 함께
붙으면 CSS 선언 순서상 나중 규칙이 이겨 조용히 틀린 배치가 된다.
⚠️ 구현 뒤 **300문항으로 `fitPrintDoc` 시간을 다시 재서** 같은 환경의 변경 전과 견줄 것.
과거 265ms는 참고 측정값이지 모든 환경의 절대 합격선이 아니다.

### 저장 데이터·화면은 건드리지 않는다

`choices.layout` 은 그대로 두고 **일회용 `#printDoc` 복제본의 클래스만** 바꾼다.
미리보기도 그대로다. 이것은 사용자의 선택을 고치는 것이 아니라 **내용 유실을 막는
출력 안전장치**다(`normBlock` 이 배치를 건드리지 않는다는 규칙과 충돌하지 않는다).

## 검사 (깨보기 포함 — 필수)

⚠️ **이 결함 자체가 "항상 통과하는 검사" 의 사례다.** 새 검사는 반드시 일부러 깨서
빨간불을 확인할 것.

1. 수식 선지 5열 표본으로 `fitPrintDoc` 전후 **잘린 `.text` 수가 줄어드는지**
   — 보정 후 0 이어야 한다.
2. **3열로 충분한 표본이 2열로 내려가지 않는지**(지면 낭비 회귀).
3. 사용자가 `cols2` 를 고른 블록이 **5열로 올라가지 않는지**.
4. 한 블록에 배치 클래스가 **둘 이상 붙지 않는지**.
5. 깨보기 — 판정을 `.choices` 컨테이너로 되돌리면 1번이 빨간불이 되는가.
6. 깨보기 — 사다리를 요소별 루프로 되돌리면 읽기·쓰기 교차 검사가 빨간불이 되는가.
   300문항 전후 시간도 함께 기록하되 시간 변동만으로 구조 깨보기 성공을 판정하지 않는다.
