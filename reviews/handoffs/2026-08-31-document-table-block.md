# 변경 인계 — 범용 문서 HWPX에 표 블록 추가

- ID: `HANDOFF-2026-019`
- 날짜: `2026-08-31`
- 작성자: `Claude`
- 상태: `ready-for-review`
- 영향 영역: `server`, `tests`, `docs`
- 관련 이슈: `없음`
- 관련 인계: `HANDOFF-2026-018`(범용 문서 베타의 "표·그림... 지원하지 않는다"를 일부 해소)

## 변경 내용

`HANDOFF-2026-018`이 명시한 미지원 목록 중 **표**를 추가했다. 그림·각주·사용자 고정
양식은 이번 범위에 없다(아래 '하지 않은 것' 참고).

- `document_schema.py`: `table` 블록 — `rows`(행렬, 최대 40행×12열, 칸 최대 500자) ·
  `header`(참/거짓, 기본 참). **표 칸에는 수식(`$...$`)을 넣을 수 없다** — 조판기가 칸
  하나에 글 하나만 넣어서, 허용하면 `$`가 조용히 문자 그대로 찍히는데 사용자는 렌더된
  줄 착각한다. 그래서 칸 글에 `$`가 있으면 거절한다. 빈 칸은 허용한다(문단·제목의
  `_text()`는 빈 글을 거절하지만, 표 칸은 빈 칸이 정상이라 `_cell_text()`를 따로 뒀다).
  들쭉날쭉한 행(열 수가 다른 행)도 거절한다 — 조판기가 병합 칸을 지원하지 않는다.
- `pedagogy_hwpx.py`: `HwpxDocument.append_table()`. `<hp:tbl>`의 XML 모양은 **지어내지
  않았다** — 실물 표가 든 HWPX 참고 파일이 없어서, HWPX를 검증하는 외부 라이브러리
  (jakal-hwpx)가 실제로 만드는 구조를 참고해 옮겼다(의존성으로 다시 들여오지 않았다 —
  구조만 격리된 venv에서 확인하고 우리 엔진에 손으로 옮겼다).
  ⚠️ **표 칸 안 문단(`<hp:p>`)은 본문 문단과 별도로 전체 문서에서 유일한 id가 필요하다.**
  참고한 라이브러리가 문서 전체를 훑어 다음 번호를 매기는 이유가 그것이다. 우리 엔진의
  본문 문단은 섹션마다 0부터 다시 매기므로, 칸 문단에 같은 번호를 주면 겹친다. 절대
  겹치지 않는 자리(900000번대)에서 따로 센다.
- `document_to_hwpx.py`: `emit_table()` — 빈 문단(`para_table` 역할, 앞뒤 여백만 담당)을
  하나 만들고 그 문단에 표를 붙인다(`emit_display_equation()`과 같은 방식). 머리글 행과
  본문 행은 다른 글자 모양(`char_table_header`/`char_table_body`)을 쓴다.
- `serve.py`의 `/document-hwpx`는 **고치지 않았다** — `document_schema.validate()`를
  그대로 통과시키는 구조라, 표를 스키마에 추가하는 것만으로 엔드포인트도 저절로 받는다.
  실제로 그런지 `test_document_endpoint.py`에 표 요청을 추가해 확인했다.

## 하지 않은 것 (의도적)

**그림은 이번에 넣지 않았다.** `_document_hwpx()`의 기존 주석이 "이 경로는 파일 경로나
임의 XML을 받지 않는다"를 이 엔드포인트의 보안 전제로 명시하고 있다. 그림 블록은 본질적으로
경로(`src`)를 나른다 — 모의고사 쪽(`/hwpx`)처럼 파일 경로로 받으면 그 전제를 깨고, 안전하게
하려면 base64로 통째로 실어 보내야 하는데 그건 그 자체로 크기 상한·검토가 필요한 별도
결정이다. `document_schema.py`의 모듈 docstring에 이유를 남겼다.

**칸 안 수식도 넣지 않았다.** 조판기의 칸 채우기가 텍스트 하나만 받는 경로라, 수식을
넣으려면 칸 안에서도 `emit_rich()`처럼 조각을 나눠 잇는 로직이 새로 필요하다. 지금은
`$`가 들어오면 거절해 "조용히 글자로 찍히는" 상태를 막는 선에서 멈췄다.

## 위험과 검토 요청

- **아직 실물 한글로 확인하지 못했다.** 나(Claude)는 한글 프로그램을 열어 볼 수 없다.
  `HANDOFF-2026-018`이 남긴 것과 같은 한계다 — XML 파싱·문단 id 유일성·글자 모양 분리는
  코드로 확인했지만, **표가 실제 한글 화면에서 어떻게 나오는지는 사람이 열어 봐야 안다.**
  사용자에게 표·수식·목록·인용문이 모두 든 예시 문서(`out/이차함수-학습정리.hwpx`, 저장소
  밖 스크래치 경로로 전달)를 보냈다 — 열어서 깨진 곳이 있으면 알려 달라고 했다.
- `append_table()`의 문단 id 오프셋(900000)은 "절대 안 겹친다"는 가정에 기댄다. 본문
  문단이 90만 개를 넘는 문서는 없다고 보지만, 더 안전하게 하려면 두 카운터를 하나로
  합치는 리팩터가 맞다 — 지금은 기존에 검증된 `append_paragraph()` 경로를 건드리지
  않는 쪽을 택했다.

## 검증

- 실행한 명령:
  - `python3 experiments/hwp-export/test_document_export.py` — 표 XML 구조(행·칸 개수,
    앞뒤 문단 순서 보존, 문단 id 유일성, 머리글/본문 글자 모양 분리), 계약 거절 5종
    (들쭉날쭉한 열·칸 안 수식·빈 rows·열 초과·행 초과), 빈 칸 허용 확인.
  - `HWPX_PYTHON=<venv> HWPX_REQUIRE=1 npm run test:hwpx` — 9건 전부 통과(표 검사 포함).
  - `HWPX_PYTHON=<venv> npm run check:fast` — 전체 통과.
  - 직접 만든 예시 문서(제목·소제목·본문 인라인 수식·별행 수식·표·글머리표·번호목록·
    인용문 전부 포함)를 `document_to_hwpx.py` CLI로 빌드 — 문서 11블록·수식 7개·경고 0개,
    `lxml`로 세 파트(section0/header/content.hpf) 모두 파싱 확인.
- **일부러 깨뜨려 확인**(전부 원복 후 재통과):
  - 칸 문단 id를 전부 `"0"`으로 고정 → `문단 id가 겹칩니다` 로 실패.
  - 머리글 글자 모양을 본문과 같게 함 → `머리글 행과 본문 행이 같은 글자 모양을 쓰면
    안 됩니다` 로 실패.
- 아직 실행하지 못한 검증:
  - **실물 한글에서 표 화면 확인.** 위 '위험' 참고.

## 뒤이어 발견된 것 (`REV-2026-012`)

사용자가 이 인계의 예시 파일을 한글에서 열었더니 **"파일을 읽거나 저장하는데 문제가
있습니다"** 로 열리지 않았다. 원인은 표가 아니라 **빈 문서 골격에 참조 표
(`fontfaces`·`borderFills`·`tabProperties`)가 통째로 없던 것**이었다 — 표 없는 문서도
열리지 않았으므로 이 인계 이전부터 깨져 있었다. `REV-2026-012` 에서 고쳤고, 그 과정에서
`reference_validation_errors()` 가 실제 id 참조를 세도록 만들어 같은 종류가 다시
조용히 지나가지 못하게 했다.

이 인계가 남긴 "실물 한글 확인이 안 됐다" 는 위험이 **바로 그 자리에서 터진 사례**다.
밑바닥에서 만드는 HWPX 는 XML 문법이 완벽해도 열리지 않을 수 있다.
