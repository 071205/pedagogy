## 변경 내용

`HANDOFF-2026-018` 이 남긴 미지원 목록 중 **그림**을 추가했다. 표에 이어 두 번째다.

### 파일 경로가 아니라 base64 다

`serve.py` 의 `_document_hwpx()` 주석은 "이 경로는 파일 경로나 임의 XML 을 받지 않는다"
를 이 엔드포인트의 **보안 전제**로 명시하고 있다. 그림은 본질적으로 경로를 나르므로,
경로를 받기 시작하면 그 전제가 깨진다. 그래서 base64 로만 받는다.

모의고사 경로(`/hwpx`)와 다른 점이다 — 그쪽은 서버가 허용한 `work/` 안 파일만 읽는다
(`REV-2026-007`). 두 경로의 전제가 다르므로 규칙도 다르다.

### 형식은 이름이 아니라 바이트로 판정한다

⚠️ 확장자나 사용자가 준 이름을 믿지 않는다. `image_size()` 가 PNG/JPEG 헤더를 직접 읽어
크기를 얻고, 못 읽으면 거절한다. **이름만 그림인 파일이 HWPX 안에 들어가면 한글이 문서를
아예 열지 못한다** — 조용히 통과시키면 안 되는 종류다.

### 높이는 원본 비율로 계산한다

폭(mm)만 받고 높이는 원본 픽셀 비율로 정한다. 아무 값이나 주면 그림이 늘어나거나 눌리는데
**눈으로 보기 전엔 모른다.** 그래서 검사가 XML 의 실제 `width`/`height` 비를 잰다.

### 제한

`document_schema.py`: 원본 4MB · 폭 5~170mm(A4 본문 폭) · PNG/JPEG 만.

### 곁들여 정리한 것

`image_size()` 와 `MM_TO_HWPUNIT` 을 `mock_to_hwpx.py` 에서 **엔진(`pedagogy_hwpx.py`)으로
옮겼다.** 시험지 경로와 범용 문서 경로가 같은 것을 쓰는데, 한쪽에만 있으면 다른 쪽이
베껴 쓰게 된다(이 저장소가 이미 여러 번 겪은 문제다).

## 위험과 검토 요청

- base64 는 원본의 약 4/3 크기다. 상한은 **디코드한 원본 바이트** 기준으로 걸었다
  (`MAX_IMAGE_BYTES`). 요청 본문 자체의 상한은 `serve.py` 의 `MAX_BODY` 가 따로 건다 —
  둘의 관계를 한 번 봐 달라.
- `document_schema.py` 가 이제 `pedagogy_hwpx` 를 import 한다(`image_size`). 계약 모듈이
  엔진에 의존하게 된 것인데, 형식 판정을 계약 단계에서 해야 조판기까지 잘못된 바이트가
  가지 않으므로 이 방향이 맞다고 봤다. 다른 의견이 있으면 검토해 달라.

## 검증

- `python3 test_document_export.py` — 그림이 `BinData/` 에 들어가는지, `<hp:pic>` 로
  나오는지, 앞뒤 문단 순서가 보존되는지, **XML 의 실제 크기 비가 원본(400×300)과 같은지**.
  계약 거절 6종(파일 경로·base64 아님·PNG/JPEG 아님·너무 넓음·너무 좁음·width 가 숫자 아님)
  과 width 기본값도 확인.
- `python3 test_document_endpoint.py` — 그림이 **HTTP 경로로도** 들어가는지, 그리고
  **파일 경로를 준 그림 블록을 서버가 400 으로 거절하는지**.
- **일부러 깨뜨려 확인**(둘 다 원복 후 재통과):
  - 높이를 폭과 같게 만듦 → `그림 비율이 원본과 다릅니다: 1.000 (원본 0.750)` 로 실패
  - 계약에서 형식 판정 제거 → `'PNG/JPEG 아님' 를 거절해야 합니다` 로 실패
- **실물 한글에서 눈으로 확인**: `npm run test:hwpx-opens` 통과 후 화면에서 그림이
  가운데 정렬로, 비율 유지된 채, 앞뒤 문단 사이에 정상 표시되는 것을 확인했다.
- `npm run check:fast` 전체 통과(HWPX 9건 포함).
