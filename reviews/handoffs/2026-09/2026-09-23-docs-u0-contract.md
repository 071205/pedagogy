## 변경 내용

[U0 계약 초안](../../../docs/PRODUCT-UX-U0-CONTRACT.md)을 작성했다. HANDOFF-162 Q1~Q3에
답변하고 ID 대응·꼬리표/검토 상태·부분 채택·재진입·원문/결과 수명·D3 한도 집행 경계를 제안했다.
독립 사본과 작업 종료 시 원문 삭제는 권장 가정이며 사용자 승인으로 바꾸지 않았다.
레일·RAIL-ORDERS·INDEX의 다음 위치는 **Claude Opus 5 계약 독립 검토·연결 시안**이다.

## 위험과 검토 요청

- IDB와 localStorage/Firestore 사이 비원자적 채택, 쓰기 뒤 장부 기록 전 종료, 여러 탭의 오래된
  배열 덮어쓰기, 이미 생성한 권의 편집/삭제를 자동 재생성으로 훼손하지 않는 계약을 확인할 것.
- `normProblem`의 새 필드 제거와 구버전 편집기 호환, 공통지문/배치 묶음 구분, 원문 삭제 뒤
  결과 그림 보존, 원장 성공 잠금과 결과 유실 안내가 기존 계약을 바꾸지 않는지 확인할 것.
- 저장 계약 §3-4 제목 48시간/본문 7일 문구 차이는 초안 §5에 기록했고 원문은 수정하지 않았다.
- D1/D2/D4 미결과 D3 운영 수치 대기를 유지. **U0 전체 완료 아님**. B3 코드 승인·실제 배포
  미완료·플래그 0 유지. B5 독립 진행과 B4/B6 선행 조건을 뒤집지 않음.

# 독립 검토 결과 (Claude / Opus 5 · 2026-09-23)

계약 §1~§7을 제품 요구·저장 계약과 대조하고 **주장마다 코드로 확인**했다.
문서끼리만 대조하면 '문서가 문서와 일치한다'만 확인된다.

## 판정

**계약의 사실 주장 다섯은 전부 맞다.** 설계 방향도 기존 불변조건과 충돌하지 않는다.
다만 **계약에 없는 실패 방향 하나를 재현**했고(`REV-2026-108`), 계약 서술 두 곳이
**구현자를 잘못 인도할 수 있어** 보강을 제안한다.

### 확인한 주장 (근거 = 실제 코드)

| 계약의 주장 | 확인 | 근거 |
|---|---|---|
| `normProblem()`이 새 필드를 소실시킨다 | **맞다** | `pedagogy-normalize.js:284` 가 고정 객체 리터럴을 반환한다 |
| Rules `hasOnly`는 최상위만 본다 → 문항 내부 메타데이터는 Rules 변경 불필요 | **맞다** | `firestore.rules:55` 최상위 11키만 검사. `problems`는 `is list` + `size()<=20000` |
| `saveSets()`는 예약일 뿐이다 | **맞다** | `saveSets`(`index.html:4899`) → `persistLocal`(`:3741`) 150ms 디바운스 → `flushLocal` |
| 기존 로컬 경로는 **전체 배열 한 번 쓰기**라 권별 원자 저장이 아니다 | **맞다** | `writeLocalNow`(`:3753`)가 `JSON.stringify(sets)` 전체를 한 번에 쓴다 |
| 저장 계약 §3-4 제목 '48시간' ↔ 본문 '7일'이 어긋난다 | **맞다** | §3-4 제목은 `(다) 48시간 후 재실행 허용`인데 §3-3은 `completed` **7일**이다. 48시간은 `DailyQuota` 수명이다. **원문을 고치지 않고 기록만 남긴 판단에 동의한다** |

### 검증 경계 — 확인할 수 없었던 것

⚠️ **"B3 실제 배포 미완료"는 저장소에서 확인할 수 없다.** 확인한 것은
`firestore.rules`에 **전환 Rules가 쓰여 있다**는 것(`:76~119`)과
`service-config.js`의 `setRevisionSchema: 0`뿐이다. 배포된 규칙을 읽는 CLI가 없으므로
(CLAUDE.md) **파일 상태와 배포 상태는 다른 사실**이다. 계약의 서술은 기록과 일치하지만
이 검토가 배포 상태를 확인해 준 것은 아니다.

## 발견 1 (P2 · 재현됨) — 지문 묶음이 위치로만 정해진다 → `REV-2026-108`

계약 §3은 지문을 **"묶음 단위 이동"**과 **"분리 시 지문 동반 검증"**으로만 다룬다.
그런데 `computeNums()`(`pedagogy-print.js:96`)는 끝 문항을 **위치로만** 고른다 —
`res[Math.min(i+span-1, res.length-1)]`. 구성원의 신원을 확인하지 않고 경계만 자른다.

세 모듈을 Node로 그대로 불러 재현했다:

| 상황 | 결과 |
|---|---|
| `P1(span3) P2 P3 Q4` 에서 **P2 제외** | 범위가 `[01~03]`으로 남아 **무관한 Q4가 흡수** |
| **P1만 다른 권으로** → `X1 P1 Y2 Y3` | `[02~04]` — 목적지의 **Y2·Y3가 흡수** |
| **P2·P3만 다른 권으로** | 범위 없음 — **지문이 조용히 사라짐** |

⚠️ **셋 다 오류가 나지 않고 인쇄물만 틀린다.** 이 저장소의 반복 실패 1번이다.
그리고 문항 삭제 핸들러(`index.html:6244`)는 **바로 그 줄에서 `paired`는 보정한다** —
`groupSpan`만 빠져 있어 의도가 아니라 **누락**으로 보인다(가설).

▶ 계약 §3에 **목적지 쪽 흡수**를 추가하고, 채택 시점에 `groupSpan`을 **실제 배치된 연속
구성원 수로 다시 쓴다**고 명시할 것. 첫 줄(제외)은 **U0와 무관하게 지금 제품에서 재현**되므로
별도 수정 묶음이 필요하다.

## 발견 2 (계약 서술) — 권별 상태표와 단일 배열 쓰기의 맞교환이 안 적혀 있다

계약 §4의 상태표는 권마다 `로컬 저장 실패` / `로컬 성공, cloud pending`을 구분한다.
그런데 로컬은 **전체 배열 한 번 쓰기**다(위에서 확인). 그러면 권별로 다른 로컬 상태는
**한 번의 쓰기로는 생기지 않는다** — 권마다 `flushLocal`을 돌려야 생긴다.
그 경우 5권이면 **전체 배열을 5번 직렬화**한다.

계약은 "권별 원자 저장이라고 주장하지 않는다"까지만 적고 **그래서 어떻게 하라**를 안 적었다.
B6 구현자가 표만 보면 없는 원자성을 가정하기 쉽다.

▶ §4에 한 줄 추가 제안: *"권별 로컬 상태는 권마다 `flushLocal`을 돌려야 관측된다.
한 번에 쓰면 전부 성공이거나 전부 실패다. 권수만큼 전체 배열을 다시 직렬화하는 비용을
감수할지, 표를 '전체 로컬 성공/실패'로 줄일지 B6에서 정한다."*

## 발견 3 (계약 서술) — `lossless`가 새 필드를 지켜 준다고 읽힐 수 있다

계약 §3은 "외부 500문항 방어를 `lossless`로 무조건 우회하지 않는다"고 적어 `lossless`를
**개수** 맥락에서만 다룬다. 확인해 보니 `lossless:true`는 **길이·개수 상한만 푼다**
(`normProblem` `:281~283`) — **모르는 필드는 lossless에서도 똑같이 사라진다.**

B6 구현자가 "클라우드 경로는 lossless니까 새 메타데이터도 보존되겠지"라고 읽을 위험이 있다.
▶ §3에 *"`lossless`는 길이·개수만 푼다. 필드 보존과 무관하다"*를 명시할 것.

## 시안에서 계약대로 그린 것

- 권별 결과(화면 5)는 `클라우드 3 / 이 브라우저만 1 / 저장 실패 1`을 각각 세고
  **'5권 저장 완료'를 쓰지 않는다.**
- 크기 초과 권은 **그 권만** 클라우드에서 빠지고 로컬·편집은 살아 있다(§1-3).
- 충돌(화면 8)은 네 선택지를 **지속 상태**로 두고 시각을 '설명용'이라고 못박았다.
- 재개(화면 9)는 삭제된 권을 되살리지 않고 '확인 필요'에서 **멈춘다**.
- 성공 잠금 중 자동 재호출을 하지 않고 **7일 기준**으로 말한다(§5의 판단을 따랐다).
- 원문 삭제 뒤에도 **결과와 그림은 남고** '원문 보기'만 이유를 표시한다.

## 미결로 남긴 것

- **D1 · D2 · D4**는 권장안을 승인으로 쓰지 않았다. 시안은 가정으로 그렸고
  다른 값을 고르면 바뀌는 화면을 시나리오 문서 §4에 적었다.
- **D3 숫자는 쓰지 않았다** — 시안에 `C2 측정 대기`만 뒀다.
- **사용성은 검증하지 않았다.** 여섯 과제 관찰표는 **비어 있다**. 시안을 그린 것이
  확인한 것이 아니다.
- **저장 불변조건 변경은 제안하지 않았다** — 발견 1~3은 전부 계약 서술·기존 결함이고
  불변조건을 바꾸지 않는다. 따라서 Astra high로 돌릴 항목은 **없다**.
  단 **D1에서 ②공용 풀·③혼합을 고르면** 지문 공유 방식이 바뀌므로 그때는 영향 경계 재설계가 필요하다.
