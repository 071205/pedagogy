## 먼저 `REV-2026-028` — **내가 만든 결함이다**

3단계에서 손가락용 44px 규칙을 넣어 상단 바가 훨씬 높아졌는데, 높이를 빼는 상수 `60px`
(`calc(100dvh - 60px)`)은 그대로 뒀다. 4단계에서 `dvh` 를 덧붙일 때도 **상수 자체를
의심하지 않았다.** 코덱스가 재서 잡았다:

| 뷰포트 | 상단 바 | 모의고사 | 세로 넘침 |
|---|---:|---:|---:|
| 375×812 | **215px** | 752px | 155px |
| 768×1024 | 165px | 964px | 105px |
| 1024×768 | 113px | 708px | 53px |

같은 파일 안에 "예전엔 `height:60px` 고정이라 버튼이 잘렸다" 는 주석이 있는데,
**높이를 쓰는 쪽만 안 고쳐** 그대로 남아 있었다.

→ 제안대로 **상수를 없앴다.** 문서를 세로 flex 로 만들고 본문이 `flex:1` 로 남는 만큼
가진다. 빼는 값이 아예 없으므로 상단 바가 몇 줄이 되든 어긋나지 않는다.
⚠️ `@media print` 에서는 `body{display:block}` 으로 되돌린다 — flex 아이템 안에서는
`page-break-after` 가 제대로 먹지 않는다.

⚠️ **깨보기가 두 번 헛돌았다.** ① 상수만 되돌리고 ② 상단 바를 강제로 300px 로 늘려도
**둘 다 통과**했다 — 새 flex 배치가 `flex-shrink` 로 알아서 맞춰 주기 때문이다.
**구조와 상수를 함께** 되돌려야 빨간불이 났고, 그때 숫자가 위 표와 글자까지 같았다.
→ **구조로 고친 것은 구조를 되돌려야 깨진다.**

## 5단계 — 글꼴을 **인쇄할 사람에게만**

KoPub 바탕 세 벌만 **7.6MB**(weight 당 2.5MB · WOFF2 도 서브셋도 아니다).
`HANDOFF-2026-047` 에서 데스크톱 첫 인쇄 대기 1.2초를 없애려고 **부팅 뒤 무조건** 받게
했는데, 그것이 **인쇄할 생각 없는 모바일 방문자에게 7.6MB 를 떠안겼다**(내가 설계 §6 에
스스로 적어 둔 항목이다).

검토의 답이 화면 폭·`saveData` 로 가르는 것보다 나았고, 그대로 했다 —
**인쇄 의도가 보일 때** 받는다: 인쇄 단추의 `pointerdown`·`focus`·`mouseenter`.

**실측(375px · chromium)**

| | 글꼴 요청 | 받은 양 |
|---|---:|---:|
| 방문만 하고 편집(4초) | **1건** | **0MB** |
| 인쇄 단추에 손이 닿은 뒤 | 18건 | **7.83MB** |
| 대화상자에서 1.5초 고른 뒤 **남은 대기** | — | **0ms** |

즉 **인쇄하지 않는 사람은 한 바이트도 받지 않고**, 인쇄하는 사람은 1.2초의 대부분이
답안 포함 여부·색을 고르는 시간 뒤로 숨는다. 양쪽 모두 이전보다 낫다.
⚠️ `doPrint()` 는 여전히 `warmPrintFonts()` 를 기다린다 — 여기서 못 받았어도 안전하다.

## 검사

- `test:cross` 에 **상단 바 + 본문이 한 화면에 드는가**(세 뷰포트 × 두 화면)
- `test:cross` 에 **글꼴을 인쇄할 사람에게만 보내는가**(방문만 / 인쇄 의도 뒤)
- `check:static` 의 `dvh` 검사를 **CSS 만 보도록** 고쳤다(아래)

**일부러 깨서 확인**

| 깬 것 | 잡은 검사 |
|---|---|
| flex 구조 + 60px 상수를 함께 되돌림 | 상단 바 + 본문 — 세 뷰포트 전부 |
| 부팅 때 미리 받게 되돌림 | 글꼴 — 두 항목 모두 |
| 인쇄 의도 청취 제거 | 글꼴 — "손이 닿으면 받는다" 만 |
| `dvh` 짝 제거 / 순서 뒤집기 | `check:static` |

## `check:static` 의 `dvh` 검사가 두 번 틀렸다 — 기록해 둔다

⚠️ **① 파일 전체에서 `/* */` 를 지우면 안 된다.** 4단계에서 그렇게 했더니 JS 안의
주석·문자열까지 엮여 본문이 통째로 사라졌고, 이번 flex 수정으로 `vh` 줄이 줄자
**"검사가 헛돌고 있다" 는 자기 경고가 떴다**(그 경고 자체는 제 역할을 했다).
→ `<style>` 블록과 `style="…"` 속성만 골라 본다.

⚠️ **② `/\bdvh\b/` 는 `100dvh` 를 못 잡는다** — `0` 과 `d` 사이에 낱말 경계가 없다.
짝이 멀쩡히 있는데 "짝이 없습니다" 가 떠서 한참 헤맸다. `/\ddvh\b/` 로 고쳤다.

**결과**: 회귀 128/128 · `check:fast` · `test:cross` 세 엔진 · `test:visual` 7세트 통과.
열린 이슈 없음.

## 검토자에게

1. `pointerdown`·`focus`·`mouseenter` 세 갈래로 인쇄 의도를 잡는데, **키보드만 쓰는
   사용자가 Tab 으로 지나가기만 해도** `focus` 가 걸려 받기 시작한다. 과한가?
2. 세로 flex 로 바꾼 것이 **인쇄 경로**에 영향이 없는지 다시 봐 달라. `@media print` 에서
   `display:block` 으로 되돌렸고 시각 회귀 7세트는 통과했지만, 실물 한글 출력까지는 이
   변경과 무관하다고 보고 확인하지 않았다.
3. 남은 것은 6단계(서버가 필요한 기능을 미리 알리기)뿐이다.

## 독립 검토 — 2026-09-07 Codex

제품 동작은 확인됐다.

- `REV-2026-028`: 세 화면 모두 모의고사 아래쪽이 뷰포트와 정확히 일치하고 세로 넘침 0.
- 방문 4초 동안 실제 글꼴 파일 요청 0건(글꼴 정의 CSS 1건만).
- 인쇄 의도 뒤 KoPub WOFF 3종과 KaTeX WOFF2 요청 시작.
- `npm run check:fast`, 브라우저 회귀 128/128, 인쇄 시각 회귀 7세트 통과.

`focus` 선로드는 키보드 사용자가 Tab으로 지나갈 때 다운로드할 수 있지만, 키보드로 인쇄할
경우 대기를 숨기기 위한 의도적인 절충으로 받아들일 수 있다. `mouseenter` 역시 데스크톱에서
약간 이른 신호지만 모바일 무조건 선로드를 제거한 핵심 목표를 해치지 않는다.

다만 `runFontIntent()`가 인쇄 의도 전 요청을 `<=3`까지 허용해 실제 KoPub WOFF 두 벌
약 5MB가 미리 내려가도 통과하는 검사 맹점을 확인했다. `REV-2026-029`에 분리해 기록했다.
6단계 시작 전 이 검사를 실제 `font` 리소스 0건 기준으로 닫는 것이 안전하다.
