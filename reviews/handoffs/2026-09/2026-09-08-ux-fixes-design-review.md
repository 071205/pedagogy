## 검토 결론

묶기 연쇄 제거·일괄 묶기 추가·알림 가독성·인쇄 준비 상태 표시 방향에 동의한다.
아래 조건을 설계에 반영한 뒤 구현할 수 있다. 이번 커밋은 문서만 바뀌었고 제품 코드 수정은
없으므로 전체 브라우저 회귀를 반복하지 않았다. 기존 함수를 직접 실행해 연쇄와 되돌리기
전제는 독립 확인했다. 아래 항목은 설계 피드백이며 미구현 기능의 결함으로 새 이슈를 만들지 않는다.

## 구현 전 보완할 조건

### 1. 일괄 묶기를 즉시 되돌릴 수 있는 기록 경계

설계 §①(3)의 “saveSets가 pushHistory를 부르므로 별도 처리 불필요”는 현재 코드와 맞지 않는다.
`pushHistory()`(index.html:2616)는 350ms 뒤에 이전 상태를 undoStack에 넣고,
`doUndo()`(2659)는 스택이 비었으면 즉시 반환한다. 초기 히스토리가 빈 상태에서
`변경 → pushHistory → 즉시 doUndo`를 실제 함수로 실행하면 변경이 그대로 남는다.
타이머 콜백 실행 뒤에는 정상 복원된다. 이전 입력이 아직 기록 대기 중이면 일괄 변경과
같은 단계로 합쳐질 수도 있다.

일괄 작업은 변경 직전 상태를 확정하고 작업 전체를 한 단계로 기록해야 한다. 이미 대기 중인
입력 기록을 보존하며 즉시 Undo/Redo가 되는지 검증한다. 검사에는 **350ms 미만 즉시 Undo**와
**직전 텍스트 편집 후 일괄 묶기 → Undo가 텍스트 편집을 보존하는지**를 포함한다.

### 2. 공통 묶음 계산은 인쇄 규칙 기준 + 편집 조작도 경계 확인

현재 두 사본은 이미 다르다. `buildPrintDoc()`(5263)은 다음 문항과 세 번째 문항의 `page`를
확인하지만 `renderQList()`(3692)는 확인하지 않으며 3묶음은 `spanOf()` 대신 `.paired`를 읽는다.
따라서 `pair,page,col`은 목록에서 1·2가 묶여 보이고 인쇄에서는 각각 독립된다.

공통 함수는 `spanOf()` 및 인쇄의 page 경계를 기준으로 삼는다. 이관 시 full-page 표시도
유지한다. 수동 “다음 문제와 묶기/세 번째 추가”에서도 page를 가로질러 묶었다고 보이지 않게
막거나 이유를 안내한다. 데이터의 span/paired 불일치와 이전 형식(paired만 존재)도 검사한다.
공통 함수를 인쇄도 부르는 상황에서 함수 결과끼리 비교만 하면 같은 버그가 통과하므로,
고정 기대 묶음과 실제 목록·인쇄 슬롯의 문항 ID를 대조한다.

### 3. 진행 표시가 실제로 그려질 시점과 종료 조건

진행 토스트를 만든 직후 `buildPrintDoc()`를 동기 실행하면 조판 중 상태는 첫 화면 갱신 전까지
보이지 않을 수 있다. 시작 상태를 그릴 기회를 준 뒤 조판하고, 인쇄 직전 상태도 화면에
표시됐는지 확인한다. rAF 한 번은 콜백 이후 화면 그리기 전에 Promise가 이어질 수 있어
그 자체로 paint 완료 보장이 아니다. 기존 토스트의 opacity 0 → show 전환도 고려한다.

`finally`로 정리하는 방향은 좋다. 진행 토스트 생성부터 조판·글꼴·그림·보정·print까지 전체를
감싸고, 인쇄 준비 중 재진입도 막아 같은 printDoc을 동시에 덮어쓰지 않게 한다. 오류 시에는
진행 표시 정리와 함께 실패 이유가 남아야 한다. 확인 대화상자에서 시작을 취소한 경우에는
진행 상태를 만들지 않는다. 실제 인쇄 대화상자 종료 시점과 print() 반환 시점이 다른 환경도
있으므로 반환을 “인쇄 성공”으로 표기하지 않는다.

그림 콜백에는 캐시 완료·실패·타임아웃·0장 경로를 포함한다. 실패한 그림도 대기 처리가
끝난 것으로 집계하되 기존 누락 경고와 음수 반환 계약을 유지한다. 예외·타임아웃 시 이벤트와
타이머 정리도 유지한다.

## 요청한 네 판단에 대한 답

1. **일괄 범위**: 기존 쓰임을 보존하려면 기본은 “현재 문항부터 끝까지”가 적합하다.
   메뉴에 범위를 명시하고 전체 적용은 별도 선택으로 둔다. 단, 현재 문항이 기존 묶음의
   중간이면 **그 묶음 시작부터** 적용하며 화면에도 시작 번호를 표시하는 것을 권한다.
   그래야 범위 앞의 묶음을 몰래 끊지 않는다. 전체 적용은 기존 묶음들을 재작성한다는 점을
   명시하고 한 번의 Undo로 되돌린다.
2. **3묶음 해제**: 셋 다 풀기에 동의한다. (a,b,c)의 b를 독립시키면서 a,c를 서로 묶는 것은
   연속 문항 기반 모델로 표현할 수 없다. 질문의 “(a,b)를 남기고 c만 떼기”는 b 독립과 다른
   동작이다. 버튼 안내를 “이 묶음을 풀고 문항을 각각 독립”처럼 실제 결과에 맞춘다.
3. **진행 비율**: 25/40/85 같은 고정 비율을 실제 진행률로 보이지 않는 편이 좋다.
   “인쇄 준비 1/4 · 조판”, “그림 확인 7/10”처럼 단계와 실제 개수를 권한다. 전체 시간의
   비율은 캐시·네트워크·문항 구성마다 달라 과거 실측표로 비율을 다시 정해도 해결되지 않는다.
4. **브라우저로 넘긴 뒤**: “인쇄 준비 완료 · 인쇄 창을 여는 중”으로 충분하다. 준비 완료와
   인쇄 완료를 구분하고 출력·취소 여부를 추정하지 않는다. 그림 외 단계는 불확정 표시를
   사용할 수 있다. 알림은 status/live 영역, 진행 막대는 접근 가능한 이름·값을 제공하되
   그림마다 음성 알림이 과도하게 반복되지 않게 단계 변경 중심으로 알린다.

## 토스트 검토

색 띠·아이콘·문구를 함께 쓰는 방향에 동의한다. 단순 border 두께 검사는 구현값만 확인하므로
밝은/어두운 테마, 좁은 화면의 긴 오류 문구에서 실제 가독성·잘림을 함께 확인한다.
배경은 “더 진하게”로 고정하지 말고 테마 토큰에 맞춘다. 진행 토스트는 일반 토스트의
2.4초 자동 종료를 상속하지 않아야 하며, 인쇄물에서는 기존 toastHost 숨김 규칙을 유지한다.

## 검증 및 남은 상태

- index.html의 실제 makeIndependent/spanOf/setPair를 추출 실행: `pcccpccc → cpcpcpcc` 재현.
- 실제 pushHistory/doUndo를 타이머 제어 환경에서 실행: 기록 전 즉시 Undo는 무효,
  타이머 실행 뒤 Undo는 변경 전 상태로 복원됨.
- 최신 커밋은 설계 문서만 추가. REV-030의 tail 원문 잔존은 코드·템플릿 수정이 없어 미해결.
- 제품 코드 변경 없음. 후속 구현자는 위 검증 조건을 관련 회귀에 추가하고 의도적 실패까지 확인할 것.
