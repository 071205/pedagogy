## 결론과 평가 범위

기능은 상당히 갖춰져 있고 입력 이스케이프·계정별 Rules·토큰 서명·원자적 사용량 예약 같은
기본 방어도 존재한다. 그러나 **계정 전환, 저장 완료, 삭제와 복구, 동시 변환**처럼 상태가
바뀌는 순간의 보장이 약하다. 이번 독립 분석에서 **새 결함 9건(P1 7건, P2 2건)**을 재현했다.
특히 이전 계정 데이터가 새 계정의 로컬 칸에 들어가는 경로와 AI 비용 한도 초기화 경로는
공개 사용 확대 전에 해결할 우선 항목이다.

숫자 점수나 “보안 통과”로 표시하지 않는다. npm 공개 취약점 조회 0건·기존 회귀 128/128
(최신 재검사 136/136) 통과와 아래 결함들이 동시에 성립한다. 기존 검사의 상당수는 단일 요청·정상 순서의 결과를
보며, 실패·응답 역전·삭제 후 복구를 충분히 다루지 않는다.

- 기준 코드: **cbd951e9aeb73446814302527b0ae8917a7c4a49**를 git archive로 격리한 사본.
- 분석 도중 Claude가 **11ef093**을 커밋했다. 변경은 브라우저 시험지 틀 모듈·그 검사·문서·
  package 설정이며, 이번 9건의 해당 제품 코드에는 변경이 없음을 파일 diff로 확인했다.
- 최종 확인 시 HEAD는 **ae5740e**다. 최신 코드에서 재현 도구 4개를 다시 실행해 **9건 모두
  같은 결함이 남음**을 확인했고 브라우저 회귀는 **136/136** 통과했다. 추가된 UX의
  historyStep은 일괄 묶기 Undo 개선이며 이미지 원본 수명 문제(034)는 해결하지 않는다.
  도중 추가된 브라우저 시험지 emitter/ZIP 변경 전체를 새로 감사한 것은 아니다. 035는
  Python 서버 경로에서 입증한 결함이며 브라우저에도 같은 버그가 있다는 주장은 하지 않는다.
- 미커밋 구현 작업을 가져와 덮어쓰거나 고치지 않았다. 분석 문서·독립 재현 도구만 추가한다.
- 검토 대상: index.html, document-editor.html, mock-exam-editor.html, Worker/auth/quota,
  serve.py, Firestore/Storage Rules, 내부 HWPX 변환 상태·입력 계약, CI/출시 설정.
- 운영 Firebase·Cloudflare 계정, 실제 사용자 자료, 실결제·실AI 호출은 사용하지 않았다.
- 외부 조회는 npm 의존성 이름·버전에 대한 공개 advisory 조회만 수행했다.
- 이전 리뷰의 결론을 통과 근거로 삼지 않았다. REV-030은 중복 등록하지 않고 기존 열린 이슈로
  별도 유지한다. 이번 분석의 9건에는 포함하지 않는다.

## 수정 설계: 기능별 땜질보다 먼저 확정할 계약

### A. 계정과 비동기 작업의 수명

`SessionContext = { uid, epoch }`를 만들고 인증 전환 때 epoch를 증가시킨다.
읽기·저장·이미지 업로드·AI 생성은 시작 시 context를 캡처한다. 종료 시 context가 같을 때만
화면·전역 상태·현재 캐시를 바꾼다. 네트워크 abort는 자원 절약이고, 결과 폐기가 정확성의
최종 조건이다. A→B→A처럼 uid가 다시 같아져도 이전 A 작업이 살아나면 안 된다.

캐시 키 계산을 완료 시점의 currentUser에 맡기지 않는다. 이전 계정 dirty 버퍼는 전환 전에
이전 key에 저장하거나 별도 미저장 복구본으로 보존한다. 새 계정 로드와 이전 계정 로드가
같은 sets를 경쟁적으로 갱신하지 않게 적용 단계를 한곳으로 모은다.

### B. 저장 상태를 명시적으로 표현

문제집마다 최소한 `revision / localPersistedRevision / cloudAckRevision`을 구분한다.
서버로 전송한 payload와 지문은 immutable이어야 한다. 전송 중 새 revision이 생기면 ack는
전송 revision까지만 진행하며 후속 저장이 남는다. 실패가 성공 표시나 clean으로 바뀌면 안 된다.

동일 문제집 동시 편집은 별도 계약이다. 문서 단위 last-write-wins를 유지한다면 충돌 시
원래 로컬본을 복구 사본으로 남기고 덮어쓴 사실을 보여준다. 서버 revision/CAS를 도입할 경우
원격 충돌 응답 → 양쪽 사본 보존 → 사용자의 병합 선택까지 설계한다. 클라이언트 timestamp만
더 세밀하게 바꾸는 것으로 충돌 유실이 해결되지는 않는다.

### C. 삭제·Undo·백업은 같은 데이터 수명 정책

이미지는 본문에 주소가 없어졌다고 즉시 삭제하지 않는다. 원본과 참조를 asset ID로 연결하고
삭제 후보/유예 기간/참조 확정/물리 삭제를 나눈다. 복제본·다른 기기·히스토리·복구용 백업에서
원본이 필요한 기간을 정의한다. 편집기에서 원격 파일을 즉시 지우는 여러 호출부를 단일 정책으로
모으되, 제품 계정 삭제의 영구 삭제와 일상적인 편집 Undo는 서로 다른 동작으로 유지한다.

### D. 인증과 비용 제어의 분리

CORS는 다른 웹페이지의 접근을 제한하는 브라우저 정책이지 인증된 사용자의 악용을 막는
비용 제어가 아니다. 일반 토큰 소유자가 카운터를 지울 수 있는 권한부터 제거한다.
계정 삭제 워크플로에는 서버에서 확인할 수 있는 상태가 있어야 하고, 클라이언트의 “삭제 중”
플래그를 신뢰하지 않는다. 재인증 후에도 같은 사용자가 초기화할 수 있다면 우회는 그대로다.

그 다음 전체 예산 경보·사용자 동시 작업 제한·공급자 호출 deadline·입력 전체 바이트 상한을
보완한다. 공급자 호출이 실제로 시작된 뒤 timeout이 났을 때 quota를 무조건 환급하면 비용
한도를 다시 우회할 수 있으므로 현재 “호출 시작 전 확정” 원칙은 유지한다.

### E. 데이터 계약과 출력 엔진

저장·읽기·수동 입력·JSON 가져오기·AI 출력에 공통 schema version을 둔다. validate와
normalize/migrate를 구분하고 migrate가 콘텐츠를 버리면 원본 보존 및 경고가 필수다.
“보안을 위해 자르기”는 자기 작업물이 손실되는 읽기 경로의 해결책이 아니다.

HWPX 서버 변환은 우선 build 전체의 동시 진입을 제한한 뒤 모든 가변 상태를 BuildContext로
이동한다. Claude의 브라우저 이식에서 전역 상태까지 그대로 복제하지 않도록 이 설계를
먼저 공유한다. 공통 엔진과 화면의 데이터가 같아도 실행 중 상태가 공유되면 경쟁은 남는다.

## 효율성·유지보수 평가

측정 표본은 한 문항당 본문 1,000자인 합성 자료이며 최초 기준 코드의 실제 브라우저에서
snapshot() 15회 실행한 값이다. 이미지·수식 DOM·클라우드 직렬화 전체를 포함한 end-to-end 수치는 아니다.

| 문항 수 | snapshot 문자 수 | 중앙값 | 최대 |
| --- | --- | --- | --- |
| 100 | 106,493 | 0.10ms | 0.40ms |
| 500 | 532,493 | 0.40ms | 0.80ms |
| 2,000 | 2,130,993 | 1.40ms | 4.60ms |

최신 ae5740e의 재실행 중앙값은 각각 0.10/0.30/3.50ms, 최대는 0.60/1.20/5.60ms였다.
동시에 다른 작업도 진행 중인 단일 환경이므로 이 차이를 커밋에 의한 성능 퇴행으로 판정하지 않는다.

이 컴퓨터의 텍스트 표본만으로 심각한 속도 문제라고 판정할 근거는 없다. 다만 pushHistory는
디바운스를 예약하기 **전에** sets 전체 snapshot을 만든다. 입력마다 전체 라이브러리 직렬화가
일어나므로 base64 이미지·여러 문제집이 커지면 비용이 커질 구조다. 실제 기기 프로파일을 얻은
뒤 dirty 문제집 단위 기록이나 변경 revision 기준으로 전환한다. 정확성 수정과 같은 단위로
묶을 수 있지만, 성능 때문에 복구 범위를 줄여서는 안 된다.

다음 개선 후보는 번호 조회 map, 목록 가상화/점진 렌더, 이미지 decode·캐시 수명 제한이다.
현재 buildPrintDoc와 renderQList의 문항별 nums.find 반복은 O(n²) 조회가 된다.
파일을 작게 나누는 것 자체보다 세션·저장 큐·스키마·이미지 수명·빌드 상태를 분리하는 것이
먼저다. 약 6천 줄 HTML을 한 번에 재작성하는 방식은 추천하지 않는다.

## 테스트를 보완할 방식

1. **상태 전환 검사**: A/B 인증과 네트워크 응답 순서를 의도적으로 뒤집는다.
2. **실패 주입**: 저장소 quota 오류, 배치 commit 지연/실패, 업로드 중 계정 전환을 만든다.
3. **불변 조건**: 미전송 revision은 synced 불가, 다른 epoch는 현재 상태 변경 불가,
   Undo 가능한 asset은 물리 삭제 불가, 동시 출력은 단독 출력과 동일.
4. **계약 round-trip**: 유효 입력 → 저장 → 읽기 → 내보내기 → 다시 읽기에서 내용 동일.
5. **실제 경계 검사**: Worker+실제 DailyQuota 조합을 사용한다. 기존처럼 quota만 검사하면
   정상적인 purge와 외부 DELETE를 연결했을 때의 비용 우회가 보이지 않는다.
6. **브라우저 결과 확인**: DOM 정상뿐 아니라 캐시 소유자·버전·다운로드 실제 문서까지 검사한다.

동봉된 재현 도구는 **결함이 발생했음을 입증하는 도구**다. 정상 제품의 성공 회귀 검사와
반대되는 assert가 포함돼 있으므로 CI에 그대로 연결하지 않는다. 수정할 때 기대 결과를
안전한 상태로 뒤집고, 의도적으로 수정 전 동작을 넣으면 실패하는지 확인한다.

## 운영·공급망에 남는 검증

- `npm audit` 0건은 lockfile 의존성의 현재 공개 advisory 결과다. CDN 런타임 버전,
  공급망 변조 가능성, 앱 고유 취약점까지 포함한 보증이 아니다. 런타임 SBOM을 별도로 만든다.
- GitHub Actions는 read 권한이지만 액션 참조는 major tag다. 검증된 commit pin과 자동 갱신
  정책을 함께 검토한다. 변경 없이 최신 버전으로 일괄 올리는 방식은 피한다.
- check:launch는 실제로 실패했다. 현재 서비스는 자체 게이트 기준 상용 출시 준비 완료가 아니다.
  결제하지 않는 서비스라면 billingPortal 필수 여부부터 제품 정책에 맞게 조정해야 한다.
- 해당 출시 검사에서 PLAN_DAILY_LIMITS_JSON은 주석 문자열만 있어도 존재로 판단한다.
  설정 파일을 파싱해 활성 값·타입을 검증하도록 보완할 후보이며 실제 요금제 배포 검증은 별도다.
- Firebase Rules 에뮬레이터, 운영 권한·App Check enforcement, 버킷 삭제 복구 정책,
  실제 Firebase 토큰 폐기, 운영 로깅, 배포 보호·백업 복원 훈련은 이번에 확인하지 않았다.
- 브라우저 문서 초안은 버튼 검증 시 저장되며 자유 편집의 autosave·계정 전환 정책이 명확하지
  않다. 로그인 문서의 격리 기대와 게스트 초안 유지 기대를 정한 후 UI/저장 설계에 반영한다.
