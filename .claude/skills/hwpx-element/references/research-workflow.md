# 한글 분석을 조판 개선으로 연결하기

## 질문과 재개 기록

질문 하나마다 기존 H1 결과 문서에 다음을 적는다. 별도 기록 파일을 매 호출마다 만들지 않는다.

| 필드 | 남길 내용 |
| --- | --- |
| questionId·질문 | 한글의 어떤 입력/출력 차이를 설명할지 |
| 대상 | 앱 버전/빌드, 원본·분석 사본 SHA-256, 아키텍처 |
| 분석 | 공급자/버전, 시작 문자열/주소, Evidence ID, 본 범위·미해결 호출 |
| 표본 | 생성기 해시, 정상/변형 관계, 변경 파트·XML 속성, 각 파일 해시 |
| 판정 | 열기·내용·저장/재열기·PDF 각각 pass/fail/skip/unknown, 정상 대조군 유효성 |
| 상태 | 완료/부분, 중단 종류, 남은 질문, 다음 도구/시험·담당 에이전트 |
| 채택 | 실물 관찰/정적 가설/생성기 정책 구분, 적용 계약으로 넘겼는지 |

새 빌드가 설치되면 과거 실물 결과를 지우지 않고 버전별로 기록한다. 기존 분석 스냅샷의
대상/공급자/profile이 일치할 때만 재사용하고, 임시 원문이 사라져도 공개 기록으로 시작점을 복구한다.

## 최소 표본 만들기

같은 표본에 여러 원인을 동시에 바꾸지 않는다. 경로 변경에 따라 필요한 참조를 함께 갱신하는
것은 일관된 실험이지만, 일부 참조를 남겼다면 그 조건도 표본 이름·mutation에 적는다.
변경 파트 목록뿐 아니라 **변경하려던 속성/순서가 실제로 달라졌는지** 검사한다.
다른 파트 바이트는 동일해야 하며, 앞뒤 정상 대조군은 동일 입력이다.

현재 로컬 도구:

```bash
HWPX_PYTHON=<lxml 있는 Python> HWPX_REQUIRE=1 npm run test:hwp-research
<같은 Python> scripts/build-hwp-research-fixtures.py --output <새 패키지 디렉터리>
<같은 Python> scripts/build-hwp-section-fixtures.py --output <새 구역 디렉터리>
<같은 Python> scripts/build-hwp-equation-fixtures.py --output <새 수식 디렉터리>
node scripts/check-hwpx-opens.mjs --report <새 JSON> <manifest 순서의 파일들>
```

앞뒤 대조군 실패는 실험 무효, 환경/권한 오류는 unknown, 미시도는 skip이다.
거부 표본이 포함되면 CLI exit 1이 예상될 수 있다. 성공 개수만 합산하지 않는다.
생성한 두 구역 대조군은 실물 열기와 서로 다른 두 표식의 PDF 출력으로 유효성을 먼저 확인한다.
출력에는 이전 텍스트를 보여 주는 Preview 캐시가 있을 수 있으므로 그것을 본문 oracle로 사용하지 않는다.

## 내용·왕복·지면 판정

- 원래 입력과 각 출력의 내용을 각각 비교한다. 혼합 본문 순서, 수식 자리와 내용,
  표의 행/열, 머리말·각주 같은 별도 scope, 그림 바이트를 비교한다.
- 재저장은 원본과 다른 새 경로를 쓴다. 기존 창을 닫고 저장본을 디스크에서 재열기해
  옛 창을 다시 보는 일을 막는다. ID·시각·ZIP 정규화와 의미 변경을 구별한다.
- PDF는 모든 쪽의 크기·본문·시각 결과를 본다. 폰트 환경이 다른 결과는 픽셀 일치를
  일반 기준으로 쓰지 않는다. 수식은 텍스트 추출만으로 빠짐/정상 판정을 내리지 않는다.
- 이미지가 같아도 입력이 잘못된 표본이면 성공 증거가 아니다. 표본 격리 검사와 연결한다.
- 확인하지 않은 층은 unknown으로 유지한다. 단일 빌드·표본의 성공은 전체 한글 호환성 승인이 아니다.

## 연구 규칙을 적용할 때

규칙마다 지원 입력·단위/계산식·ID/스타일 scope·warning/거절 정책·영향 파일·정상/반례/red·
Python/JS parity 신호·실물 빌드·이전 입력 호환을 짧은 적용 계약으로 정한다.
모순된 관찰이 남으면 그 규칙은 가설이며 새 생성 정책이나 강제 validator 오류로 채택하지 않는다.
사용자가 승인한 스킬/검사 개선은 진행하되, 새 제품 블록은 기존 레일의 범위 판단을 따른다.

블록 추가는 SKILL의 다섯 경계를 모두 대조한다. 패키지 validator만 바꿀 때는 실제 영향 경계를
지목하고 불필요한 UI 작업을 만들지 않는다. 검사는 이전 정책 또는 실패 주입에서 해당 이유로
빨간불이어야 한다. 코드 개수/문구 존재만 확인하는 검사를 동작 증거로 대신하지 않는다.

구역 수가 작으면 열리고도 본문 일부가 빠질 수 있다. 따라서 “열렸으니 참조/개수는 무시해도 됨”을
결론으로 삼지 않는다. 두 표식 순서·누락을 확인한 다음 여러 구역/다른 빌드로 확장한다.

현재 구역 조사 API는 Python `section_package_diagnostics()`와 JS `sectionPackageDiagnostics()`다.
기본 `inspect`는 일반 파일 조사용이며 별칭·ID 이름만 일치하는 리소스를 우리 출력 미지원 경고로 구별한다.
`pedagogy-export`는 현재 canonical 편집/출력 지원 범위를 강제하며 save/toBlob에서 오류를 차단한다.
이를 한글의 보편 거부 규칙으로 설명하거나 경고를 없애려고 입력을 자동 수정하지 않는다.
정확한 code/profile/루트·참조 범위는 docs/HWP-SECTION-DIAGNOSTIC-CONTRACT.md,
정상/반례·Python/실제 DOM 대조는 `test:hwpx`와 `test:hwpx-sections`에 있다.

현재 수식 실물 관찰은 H1-equation-03에 있다. 고정/zero geometry의 동일 출력과 저장 정규화는
단일 Mac 빌드 근거이며, 긴 수식은 본문 폭을 넘었다. 출력 생성과 지면 품질 판정을 나누고
임의 상수 교체·자동 축소를 채택하기 전에 별행/다단/폰트·폭 진단 계약을 정한다.

정적 참조가 같은 단어여도 번호 매김/메타데이터 처리일 수 있다. 본문 수식의 속성 reader,
제어 dispatch, 공유 측정 루틴, 미해결 인터페이스를 나눠 기록하고 false lead를 재분석하지 않는다.
선택 경로에서 조건을 못 찾았다는 결과를 프로그램 전체의 부재로 확대하지 않는다.

한글 재저장 geometry와 seed를 구별한다. 사용 가능한 폭은 해당 구역의 활성 쪽/단·문단/상자에서
구하며, 미지원 설정은 unknown이다. 실제 폭이 줄 상한 이하여도 인라인 남은 폭 fit을 보장하지 않는다.
다른 입력 해시의 실측을 자동 전용하지 않는다. 새 seed 변형은 별도 측정/정체성 확인이 필요하다.
구체 경계는 docs/HWP-EQUATION-LAYOUT-CONTRACT.md를 따른다.

## 사이트 모의고사/문제집으로 적용하기

사이트 화면/지면/인쇄에도 적용하는 요청은 docs/HWP-WEB-TYPESETTING-DESIGN.md의 H1-e~h를 따른다.
한글에서 얻은 fontRef·장평·자간·탭·수식/행 배치 규칙을 출력별 프로필/관찰과 연결한다.
브라우저의 요청 font-family·fonts.ready/check를 실제 사용 글리프/한글 측정의 증거로 쓰지 않는다.
현재 첫 결함은 측정 DOM의 CSS 컨텍스트129·글꼴 준비 전 payload130이다. 실제 출력과 같은
컨텍스트에서 재고, 폰트/이미지/입력 revision이 달라졌으면 낡은 배치·높이를 재사용하지 않는다.
기존 단폭/가공 폰트/보정 계수는 시험지 계보·엔진·폰트 정체성을 맞춘 실물 근거가 있을 때 조정한다.
